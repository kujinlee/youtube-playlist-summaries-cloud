## The product vision (user clarified 2026-07-10 — I had it wrong first)
NOT "cloud replaces local." **One codebase, two coexisting apps switched by `STORAGE_BACKEND`:**
- **Local app** — single user, filesystem (outputFolder, folder picker, Obsidian vault). KEEP.
- **Cloud app** — multi-tenant, Supabase, auth-gated per owner.
- **Sync bridge** — download cloud→local and upload local→cloud: files (summary/deep-dive MD+HTML), video
  metadata (ratings/notes/archived/scores), configs. Conflict rule: **newer version wins** per video.
So the `serveLocal`/`serveCloud` dual-branch pattern is a first-class feature, not legacy.

## Settled decisions (user-confirmed via AskUserQuestion, 2026-07-10)
- Audience = **multi-user / open signup**. Auth = **Google OAuth only** (signInWithOAuth → `/auth/callback`).
- Library nav = **playlist sidebar + video list**. Build = reuse presentational components + their tests; build
  the cloud shell ALONGSIDE local; do NOT delete local UI. Ordering = cloud first, sync later.
- **Sync comparator = lexicographic (docVersion primary, updatedAt tiebreak).** `docVersion{major,minor}` is
  stamped on (re)generation + HTML render, not by rating/note/archive edits; `updatedAt` bumps on every write
  (cloud stamps DB-clock server-side). A doc regenerated by an OLDER generator is still older. 2a added
  `updatedAt` so Stage 3 needed no backfill.
- Archive in cloud = an **archived flag** via `updateVideoFields`, not a file move.
- Annotation writes use a dedicated `update_video_annotations` RPC (SECURITY INVOKER, `auth.uid()` owner,
  key allowlist), never the shared `merge_video_data` (callers write JSON null as set-null).

## B1 — Blocking

**Claim:** The one thing v3 ships — *"generated by default"* — has **no activation path**. The
instruction lands in a document that is not loaded at session start and whose stated read-trigger is a
gate, while N1 says there is no gate; the skill's own trigger metadata is never specified; and the
kill condition cannot tell *"generated and useless"* from *"never generated"*, so the spec's own
evaluation will return a false negative.

**The chain, each link verified.**

1. The rule is routed to `docs/process-checklists.md` — spec:353: *"short section: generate an
   explainer before opening a code PR"*.
2. `CLAUDE.md` is three lines (verified in full):

   ```
   @AGENTS.md
   @docs/dev-process.md
   @docs/plugins.md
   ```

   `docs/process-checklists.md` is **not** @-included. It is loaded only when someone opens it.
3. `docs/dev-process.md`'s read-trigger table says to read `process-checklists.md` *"when you are
   working a gate — per-task list, post-plan gate, TDD policy, spec contents"*. Spec:52 (N1) says
   **"Not a gate. Nothing blocks."** So the document's stated read-trigger is a condition this
   mechanism asserts never applies to it.
4. `docs/dev-process.md` is deliberately **"Not touched"** (spec:355-356). The reasoning given is
   sound about the specific table it names — *"v2 proposed a pointer row in* What is mechanically
   enforced*, and nothing here is mechanically enforced, so the row would have been false."* But the
   consequence is that **no always-loaded document mentions the explainer at all**.
5. The skill file itself is specified as one table row — spec:351,
   `.claude/skills/explain-diff/SKILL.md`, *"new — the adapted skill, crediting Litt"*. **No
   frontmatter is specified**: no `description`, no `disable-model-invocation`, no `user-invocable`.
   Compare `.claude/skills/zoom-out/SKILL.md:1-5`, which sets `disable-model-invocation: true`
   precisely because that field decides whether an agent can fire the skill on its own. For a spec
   whose *entire* deliverable is one skill file, the field that decides whether it ever runs is absent.
6. The project already owns a hook at the exact moment the trigger describes.
   `.claude/settings.json` → `PreToolUse` / matcher `Bash`, `if: Bash(git push*)` →
   `.claude/hooks/block-default-branch-push.sh`. That is the machine-observable boundary immediately
   before a PR is opened. A *reminder* there would not violate N1 (a reminder blocks nothing). The
   spec never considers it, and `docs/process-checklists.md:191` requires this be answered with a
   `file:line`, not skipped.

**Failure scenario.** The skill merges. Over the next seven weeks eleven code PRs are opened; the
instruction lives in a file nobody opened, because opening it is triggered by working a gate and this
is not one. On 2026-09-30 the kill condition (spec:311-316) is applied: no explainer produced a seam,
an ADR, a corrected belief or a missed defect — because zero explainers were produced. The recorded
conclusion is *"the idea did not earn its keep"*. The measured fact is *"it never ran."*

**Why Blocking rather than High.** Not because the skill might go unused — N1 accepts that. Because
the spec's only evaluation instrument **passes in both worlds**, and it is the instrument that makes
shipping on an admittedly-unmeasured premise defensible (spec:35-37). Shape 2 on the standing list,
applied to the spec's own retire criterion.

**Anchor:** spec:8-9, spec:52, spec:133-137, spec:311-316, spec:351, spec:353, spec:355-356;

Both fields are written by the agent that wrote the explainer. Nothing counts files; nothing compares

## M4 — Medium

**Claim:** The **blind baseline** — the one recorded fix that is presented as *"runnable, unlike v2's
'answer with the explainer closed'"* — is calibrated to the wrong taker, and by construction cannot
catch the failure Codex M1 measured.

**Failure scenario.** Spec:92-94: *"a third agent given only the questions — no code, no explainer —
answers them. If it scores ≥ 4/5, the quiz tests recognition rather than understanding and is
rejected."*

Two problems, opposite directions:

- **Too strict.** A frontier model answering four-option questions about software behaviour scores far
  above the 25% chance baseline from plausibility priors alone — distractors that are *wrong* are
  usually also *implausible*. The reject threshold therefore measures the agent's general competence,
  not whether this quiz is passable without this explainer. That is Codex Medium 2's shape
  (*"reject legitimate comprehension questions"*) arriving by a second road, now aimed at the whole
  quiz instead of one option.
- **Too permissive, on the exact case it was aimed at.** The baseline agent is given **no code**. A
  question answerable by `grep`-ing the diff (Codex Medium 1) scores *low* blind — so it **passes** the
  baseline and remains answerable by diff search at quiz time. The one recorded runnable instrument is
  blind to the one measured defect it does not otherwise fix.

**Premise tag — unverified.** I did not run an agent against a synthetic question set. The
above-chance claim is a reasoned expectation about model behaviour, not a measurement, and the finding
should be read as *"this instrument has not been calibrated"* rather than *"it fails at threshold N"*.
That is itself the point: the spec presents it as runnable and does not say what a passing baseline
score looks like or against which model.

**Anchor:** spec:89-97; `docs/reviews/understanding-gate-spec-v2-codex.md` M1, M2.

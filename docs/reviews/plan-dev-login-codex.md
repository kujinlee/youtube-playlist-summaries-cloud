**Findings**

**Blocking — `NEXT_PUBLIC_SUPABASE_URL` makes the server gate build-time, not reliably runtime.**  
The plan gates `/dev-login` with `process.env.NEXT_PUBLIC_SUPABASE_URL` in [docs/superpowers/plans/2026-07-24-dev-login-13.md](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/plans/2026-07-24-dev-login-13.md:391), and the spec explicitly chooses that signal in [docs/superpowers/specs/2026-07-24-dev-login-design.md](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/specs/2026-07-24-dev-login-design.md:51). Next 16 docs say `NEXT_PUBLIC_*` references are replaced with the value from `next build` and frozen afterward. This repo already documents the same production issue in [Dockerfile](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/Dockerfile:27) and [fly.toml](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/fly.toml:18). Therefore a production artifact built with `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321` can carry an open `/dev-login` page and client bundle even if runtime prod env points at hosted Supabase. That violates the invariant.

**Blocking — the proposed `/dev-login` page is likely statically/prerender-time gated unless forced dynamic.**  
The planned page only reads env and returns JSX/notFound in [docs/superpowers/plans/2026-07-24-dev-login-13.md](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/plans/2026-07-24-dev-login-13.md:390). It does not call a request-time API such as `connection()`, `cookies()`, or `headers()`. Next docs state static components can be prerendered at build time, and env vars are safely runtime-read on the server only during dynamic rendering. So this is not truly “server-side per request” as claimed in [docs/superpowers/specs/2026-07-24-dev-login-design.md](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/specs/2026-07-24-dev-login-design.md:73). Fix should force request-time evaluation, e.g. `await connection()` from `next/server`, and avoid literal `NEXT_PUBLIC_*` for the server gate.

**High — `/dev-login` being public means gate removal becomes a full unauthenticated prod exposure.**  
Current middleware redirects any unauthenticated authenticated route to `/login` in [middleware.ts](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/middleware.ts:43). The plan adds `/dev-login` to `PUBLIC_EXACT` in [docs/superpowers/plans/2026-07-24-dev-login-13.md](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/plans/2026-07-24-dev-login-13.md:161), bypassing that protection globally. Exact matching in [lib/supabase/route-categories.ts](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/lib/supabase/route-categories.ts:14) avoids sibling prefix bugs, so this is not a path traversal issue. The risk is ordering: once public, the route’s entire safety depends on the page gate. If the gate is build-time-flipped or removed, middleware will intentionally allow unauthenticated users to reach and use the form.

**High — tests do not exercise a real built Next app, so they miss the main prod-leak scenario.**  
The critical test directly imports and calls `DevLoginPage()` while mutating `process.env` in Jest at [docs/superpowers/plans/2026-07-24-dev-login-13.md](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/plans/2026-07-24-dev-login-13.md:353). That can mutation-test the source `if`, but it cannot catch Next’s build-time inlining, static prerendering, or client bundle freezing. Same issue for `/login` link tests at [docs/superpowers/plans/2026-07-24-dev-login-13.md](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/plans/2026-07-24-dev-login-13.md:436). Add a build-level test or script: build once with local public URL and prod runtime URL, start the standalone app, assert `/dev-login` is still 404. That test should currently fail under this design.

**Medium — the plan’s “hosted prod always uses supabase.co” assumption is documented but not enforced.**  
The spec relies on “Hosted prod always uses the `…supabase.co` URL” in [docs/superpowers/specs/2026-07-24-dev-login-design.md](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/specs/2026-07-24-dev-login-design.md:56). The current Fly config does set the hosted URL in [fly.toml](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/fly.toml:24), but the invariant says structurally impossible, not “configured correctly today.” A safer design needs an explicit production kill switch or deploy-time assertion that refuses production builds/deploys when the dev-login gate would evaluate true.

**Medium — `notFound()` itself is fine, but only after the earlier dynamic/build issues are fixed.**  
Next docs say `notFound()` throws and terminates rendering of the route segment, so a request-time server component gate would prevent the form from rendering. The proposed direct `notFound()` usage in [docs/superpowers/plans/2026-07-24-dev-login-13.md](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/plans/2026-07-24-dev-login-13.md:391) is not the problem. The problem is whether that branch is decided at build/prerender time with a frozen public env value.

**Low — the Supabase cookie assumption is mostly correct, but only tested with mocks.**  
`createBrowserClient` defaults `persistSession: true` and uses document cookies in browser mode, so `signInWithPassword` should write the session through the same storage path as OAuth. That aligns with [lib/supabase/client.ts](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/lib/supabase/client.ts:14). But the planned component test mocks `signInWithPassword` and never verifies cookies or middleware recognition. Keep the mock unit test, but add the manual/live check from [docs/superpowers/plans/2026-07-24-dev-login-13.md](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/plans/2026-07-24-dev-login-13.md:532) as an automated or documented required verification.

**Bottom Line**

I would not implement this plan as written. The single biggest flaw is using a literal `NEXT_PUBLIC_*` value as the security gate while also claiming request-time server protection. For this invariant, the gate should be server-only, request-time, and impossible to inline: for example, force dynamic rendering and read the Supabase URL through a computed server env helper, plus add a production build/deploy assertion that fails if the dev gate would be open.

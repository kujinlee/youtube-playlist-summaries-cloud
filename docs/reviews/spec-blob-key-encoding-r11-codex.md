Failure scenario:

A local doc-version bump re-summarizes an existing video at the same stable key. Today `LocalFsBlobStore.promote` overwrites via `renameSync`, so the regenerated paid summary becomes the live blob. Under R1's required `link` + `unlink` create-if-absent contract, the final already exists, the staged regenerated bytes are discarded or left unpromoted, and `summary-handler.ts:179` still stamps the row as `promoted` at the current doc version. The same applies to local re-dig of an existing section key. A paid artifact is replaced in metadata but not in bytes; future serve reads stale content while the system claims the new artifact was promoted.

Proposed fix:

Do not change `BlobStore.promote` globally. Add a separate create-if-absent primitive for the additive-copy protocol, for example `promoteIfAbsent(ref): 'created' | 'already-exists'`, and make R2 use that primitive plus final read-back. Leave existing overwrite callers on `promote`, or rename the current overwrite primitive to make the distinction mechanical. If the design still wants `promote` itself to become create-if-absent, then the spec must also require migrating every overwrite caller above to an explicit overwrite path (`put` of verified staged bytes or an overwrite-promote primitive) before R1 lands.

Failure scenario:

On an APFS receiver, video A has a paid model at stored path `models/<NFD base>.json` and its envelope says `sourceMd: "<NFD base>.md"`. A separate corrupt or legacy row for video B reaches Class-A transfer with `winnerVideo.summaryMd = "<NFC base>.md"` where the two bases are filesystem aliases. `companionTransfer` derives `base` from B's winner key, reads `models/<NFC base>.json`, receives A's envelope through the alias, sees `sourceMdHash` present and different from B's `winnerMdHash`, and calls `delete(models/<NFC base>.json)`. APFS resolves that delete to A's directory entry and unlinks A's paid model.

This is not closed by "base derives from the summary the transfer has just made authoritative"; that statement identifies B's intended address, not the owner of the model bytes found at the receiver's alias class. The model bytes themselves already state their owner in `sourceMd`, and the design does not require consulting it.

Proposed fix:

Extend the R3 record/ownership check to writer 3 before any ship or delete decision. For a receiver envelope read from `models/${base}.json`, require `canonicallyEqualName(receiverModel.envelope.sourceMd, `${base}.md`)` and, when available, require it to match the loser's record key being overwritten. If the envelope's `sourceMd` names a different logical key, refuse as `destination-exists`/occupied and leave the model untouched. Add a behavior covering the APFS alias case: model envelope `sourceMd` does not canonically match the transfer base ⇒ no delete.

## Checked Non-Findings / Follow-Ups

R3 call-site scope: the spec says both call sites already hold the loser's record. Current calls are `transferClassA(localSide, cloudSide, lv, id)` and `transferClassA(cloudSide, localSide, cv, id)` at `lib/cloud-sync/sync-run.ts:782` and `:793`; both branches also have `cv`/`lv` in scope at `:612-613`, and after cloud base relocation `cv` is re-read at `:765`. The signature change is mechanically feasible, but the spec should show the exact new calls: `transferClassA(localSide, cloudSide, lv, cv, id)` and `transferClassA(cloudSide, localSide, cv, lv, id)`.

R2 byte-identical residual: produced summaries include `video_id` frontmatter (`lib/ingestion/summary-core.ts:101-103`), and orphan adoption requires `video_id` (`lib/pipeline.ts:147-149`), so two different videos should not produce byte-identical full Markdown unless provenance is corrupt or duplicated. The serial uniqueness premise is weaker than §3.6.4 implies because there is no DB unique constraint on JSON `serialNumber`, but the frontmatter makes the optional escape hatch a hardening measure rather than required for normal produced summaries.

R2 read-back cost: it is one extra `tryGet`/download on additive creates that write an MD. On timeout/unreadable, R2 says refuse; `runSync` catches per-video errors at `lib/cloud-sync/sync-run.ts:812-814` and advances no baseline. That is an availability cost, not a paid-artifact loss. It should be documented in the runbook, but I do not rate it Blocking.

P3: I did not find another non-test direct Supabase Storage write beyond `SupabaseBlobStore`. The non-test storage write surface I found still routes through `BlobStore` (`summary-handler`, `copyAdditiveVideo`, `transferClassA`, `writeDigSectionBlob`, `writeModelEnvelope`, `writeArtifact`).

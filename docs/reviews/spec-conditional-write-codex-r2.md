1. [docs/superpowers/specs/2026-08-04-cas-fence-persist-summary-design.md:340](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/specs/2026-08-04-cas-fence-persist-summary-design.md:340) — re-address `promote(ref)` can silently keep the old blob bytes, then advertise new metadata.

Concrete case:
- Existing row after A3: `serialNumber: 3`, `summaryMd: "003_alpha.md"`, artifact status `promoted`.
- Existing blob `003_alpha.md` contains old relocated summary `OLD`.
- Worker has just generated new summary bytes `NEW` from the same job.
- CAS rejects stale `(7, "007_alpha.md")`; §6 re-address attempt stages `NEW` at final key `003_alpha.md`.
- §6 says `promote(ref)` before metadata persist.

But [SupabaseBlobStore.promote](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/lib/storage/supabase/supabase-blob-store.ts:90) is create-if-absent/idempotent: if final exists, it removes temp and returns at [lines 93-97](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/lib/storage/supabase/supabase-blob-store.ts:93). It does **not overwrite** `003_alpha.md`. Then §6 persists the new summary scalars as `promoted` at [spec:342](/Users/kujinlee/code/agentic-ai-docs/youtube-playlist-summaries-cloud/docs/superpowers/specs/2026-08-04-cas-fence-persist-summary-design.md:342). Result: row metadata says the newly generated summary landed, but the durable blob still contains old content. This is worse than the original promoted-status inheritance bug because it produces a green promoted row with wrong bytes.

Crash subcase: if process dies between `promote()` and `persistSummary('promoted')`, the state may be recoverable by retry only if the final bytes are actually the worker’s bytes. On Supabase they often are not, because final existed and promote skipped. The established committed step exists to publish “metadata points to staged/committed work, promotion still pending”; §6 removes that breadcrumb for re-address attempts.

Ordering in current handler:

Case:
- Row before job: `serialNumber: 7`, `summaryMd: "007_old-title.md"`, promoted.
- New job payload title: `"New Title"`.
- Handler’s line 84 read sees `expected_summary_md = "007_old-title.md"`.
- Line 96 computes `baseName = "007_new-title"`.
- Payload wants to write `"007_new-title.md"`.
- Guard `v.data->>'summaryMd' is not distinct from p_expected_summary_md` passes, and update writes a different key.

That is valid if this is intentional re-summarize behavior, but §4/§6 currently describe the second conjunct as guarding the slug half of the address. It actually guards “row did not change since line 84,” not “payload key equals current key.” The spec needs to state this explicitly and test it. If an implementer instead sources `p_expected_summary_md` from the payload key, this exact legitimate re-summarize fails closed: row has `"007_old-title.md"`, expected is `"007_new-title.md"`, guard rejects forever.

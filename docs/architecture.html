System architecture

YouTube Playlist Summaries — one app, two runtimes

The same Next.js app runs in two interchangeable modes, chosen by STORAGE_BACKEND. Your browser is the single front-end for both — point it at your own machine (local mode, filesystem) or at Fly (cloud mode, Supabase). Both runtimes call out to Gemini & YouTube; the local machine is a runtime peer of Fly, not a separate front-end. Cloud Sync bridges the two stores.

01 · BROWSER

The single front-end

One UI serves both modes — you just point it at a different runtime: localhost:3000 for local, the Fly URL for cloud.

Only the cloud path carries a Supabase session cookie (sb-…-auth-token) → JWT. Local mode needs no auth; it's your own machine.

02 · TWO RUNTIMES, ONE CODEBASE

Switched by STORAGE_BACKEND

Local (=local, default) — runs on your machine, stores to the filesystem, generates inline (no queue).

Cloud (=supabase) — runs on Fly.io as web + worker, stores to Supabase, generation goes through a job queue.

The same routes resolve either the filesystem stores or the Supabase stores (lib/storage/resolve.ts). So your machine plays the same role Fly plays — a runtime, not a front-end.

EXTERNAL · APIs

Both runtimes call out

Gemini and YouTube are reached by whichever runtime is generating — the local runtime does it inline on your machine; on Fly the worker generates and web renders at serve time.

This is the edge the earlier diagram missed: local generation is a direct call from your machine to Gemini/YouTube — it does not route through Fly or Supabase.

03 · SUPABASE

The cloud store (source of truth for cloud mode)

Auth issues JWTs; Postgres holds metadata, the jobs queue, and the money tables (spend_ledger) with RLS enforced; Storage holds the blobs.

Two credentials cross in: web/browser uses your JWT (RLS-scoped); worker uses service_role (bypasses RLS).

04 · CLOUD SYNC

The bridge between the two stores

A CLI on your machine that reconciles local files ↔ Supabase directly — newer-wins, additive (adds propagate both ways; deletes don't, yet).

Sync is the only path between the two worlds, and it does not go through Fly — it talks straight to Supabase's DB + Storage.

Three environments, not two. ① local files (the local runtime's store), ② a local Docker Supabase for dev/testing cloud mode, and ③ prod Supabase (shown above). The diagram's cloud side is the prod path; the local Docker one is the same shape pointed at localhost.

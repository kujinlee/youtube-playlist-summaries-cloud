1. What the loosening HOLD is, and why it exists

The gate cannot read intent. So any PR that removes or rewrites a line near a failure path in a gate file is held until a reviewer says, line by line, that the branch still refuses everything master refused.

  • A gate file is any script: GATE_CODE matches scripts/*.{py,sh,ts,js,…}, scripts/ci/… and .claude/hooks/… (check-merge-ready.py:683).
  • A failure path is a line matching FAIL_PATH (:670): FAIL, failure, return 1, exit 2, sys.exit(…) other than 0, raise, assert, deny; Node adds throw and non-zero process.exit.
  • "Near" is within FAIL_WINDOW = 5 old-file lines (:841). failure_path_removals (:866) collects every removed code line in that window, except a line re-added identically (a move) or one whose only change is a rising self-test count.

Why the reviewer judges, not the gate. The detector is syntactic: if bad: return 1 → if bad or other: return 1 refuses more, and → if bad and False: return 1 refuses less, and both look the same to it. The comment above VERDICT_DIR (:918–931) records the measurement that moved the judgment: of 21 loosening HOLDs judged in writing, 19 were judged FALSE by the PR's own side and 2 real (PRs #400–#519). Before backlog #508 the PR's author judged its own HOLD. You moved that to the reviewer on 2026-11-05 (card A).

2. How an answer is recorded and checked today

  1. Each flagged line gets an id: flag_id (:949) is a hash of file path + the removed line's text + which occurrence. It is not tied to a tree: the same removed line on the same file keeps its id across rounds and merges.
  2. The final round's prompt carries the list (flagged_block, :972; check-merge-ready.py --pr N --flagged-block prints it). The reviewer ends its review with: 
    ## Loosening answers
LOOSENING-CHECK fb89f268396d: not a loosening
LOOSENING-CHECK 712c0aacc4cf: finding: <what the branch now lets through>
    Any other line in that section makes the whole section a finding.
  3. The answers go into the verdict file docs/reviews/verdicts/<subject>-r<N>-<half>.verdict.json, parsed by ONE parser (codex-review.py:896 loosening_answers). The verdict also records head (the commit reviewed) and dirty (any uncommitted files the reviewer was handed, codex-review.py:1005 reviewed_state). A Claude half's verdict is written by record-review-verdict.py from the filed review.
  4. At merge time, review_answers (:1060) reads every verdict the branch adds. It keeps one only if the gate ran, it names a 40/64-hex head, and tree_matches (:1003) says the reviewed tree IS the tree being merged: every path of both trees, apart from the round's own records (REVIEW_RECORD), must be identical.
  5. The same-half rule (standing_findings, :1024): a finding answer counts from a verdict on ANY tree, and is retired only by a later round of the same subject and the same half answering that id not a loosening on the tree being merged. The other half's assent never retires it.
The binding in step 4 is the whole story of backlog #544. Its comment (:933–934) reads: "What may differ between the reviewed tree and the merging one: the round's own records. Nothing else — a docs edit after the round also voids its answers (owner: the EXACT tree)."

5. What A newly lets through — the honest residual

The real gap: a change to a DIFFERENT file that changes what the flagged line MEANS. The flagged line if not proof_ok(x): return 1 sits in scripts/gate.py. A reviewer answered that its rewrite is not a loosening. Later, master merges a change to scripts/helpers.py making proof_ok return True in a new case, or changing a constant gate.py imports. A keeps the answer, because gate.py's blob did not change. C would have voided it and forced a re-read. This is by design: A binds to the file, not to what the file depends on.

How big is it?

  • Changes on the PR's own branch after the final round are still caught elsewhere. check-review-recorded.py:104 fails a branch whose every recorded round has guarded code committed after it. Backlog #426 exempts only code that arrived through a merge of master. So the residual is limited to changes arriving from master (inferred from those two sources; not exercised here).
  • Changes from master were reviewed in their own PRs, but against master, not against this PR's rewrite. Nobody re-judges the interaction. That is the accepted bound.
  • The detector already has a larger blind spot that A does not touch: it flags only removed or rewritten lines. An inserted early return 0 above a check removes nothing and is never flagged, under A or C. inferred from failure_path_removals' docstring

How to narrow it, if you want to: bind each answer to the blobs of the flagged file and its import closure, the gate scripts it loads. The scoped mutation sweep already computes such a closure for its manifest selection (backlog #330, extended by backlog #498 to modules loaded by filename). Reusing it would void an answer when helpers.py changes, while still surviving a docs merge or an unrelated script. Cost: more voids than A; it is still far fewer than C. a proposal, not built

You asked · answered 11-08 19:40

“A file staying the same doesn't guarantee its imported files stay the same. If we follow every import as a tree, can we determine there is no hidden ripple effect? And if we treat the same version of an external import as the same, we only need to examine the internal imports. Is this thinking sound?”

Yes, it is sound, and it is the standard answer. With two catches, both measured here.

The idea is a content-addressed build. It is how Bazel and Nix decide whether a cached result still holds. Hash the file together with everything it transitively loads. If that hash is unchanged, the answer still holds. Your shortcut also matches practice: an external package at the same pinned version counts as the same, as a lockfile treats it. The Python standard library is pinned by the Python version, and CI already pins that (check-python-pin.py). So only the repo's own files need walking. It is also the "How to narrow it" proposal just above, which needed a tree, and you have just described the tree.

Catch 1: in this repo, the tree cannot be found by reading import lines. Take the gate itself, scripts/check-merge-ready.py.

  • Its import lines (lines 47–60 on master) name only standard-library modules.
  • Its repo-internal dependencies are all dynamic. It loads 2 sibling scripts by file path through _import_sibling (check-dashboard-entry.py and check-plan-code.py). It also runs 3 more as subprocesses: check-dashboard-entry.py, check-review-recorded.py and check-review-rounds.py.
  • A walker that reads import statements would find 0 of those 5 edges, and would say "no ripple" exactly where the ripple is.
  • The pattern is common: 32 files under scripts/ load code with _import_sibling or importlib.

The repo has already paid for this lesson. The mutation sweep's manifest selection (backlog #330) had to be extended by backlog #498 to follow modules loaded by filename, because import-only reachability missed them. So the tree must be built by the same rules as that selector, or traced by running the gate, not parsed from imports. A tree that misses an edge fails toward "safe", which is the dangerous direction.

Catch 2: the tighter the binding, the more often an answer is voided. Measured on master from 11-01 to now:

  • 71 merges in total.
  • 8 touched check-merge-ready.py itself (≈11%). That is how often today's option A voids an answer about that file.
  • 47 touched anything under scripts/ (≈66%). That is the most a crude "all of scripts/" closure could void. The old exact-tree rule voided on 100%.

A precise closure would void somewhere between 11% and 66% for this file. I have not measured the exact figure; it needs the closure built first.

What it still would not prove. Even a perfect closure only tells you that nothing the line depends on changed. When something did change, it tells you to re-read the line; it cannot tell whether that change matters. So it narrows the residual; it does not remove it. The remaining blind spot (§5, third bullet) is separate: the detector flags only removed or rewritten lines, so an inserted early return 0 is never flagged at all.

My recommendation. Keep option A for now. File "bind to the traced closure" as the next step, reusing the sweep selector's reachability so the two can never disagree about what a file depends on. It is filed as a backlog row in the next docs batch. Changing what binds stays your call (backlog #544 was your card).

You asked · answered 11-08 20:00

“So, as a heuristic, check only the immediate file, not related files (internal imports)?”

Yes. Option A is exactly that heuristic, and the measured reason is that one hop already costs almost as much as everything.

Option A binds an answer to the flagged file alone. I checked the middle ground you are implicitly asking about: the file plus its direct internal dependencies, one hop. For the gate, those are the 5 edges above. Merges to master since 11-01, out of 71:

  • Immediate file only (check-merge-ready.py): 8 (≈11%).
  • File plus one hop (adding check-dashboard-entry.py, check-plan-code.py, check-review-recorded.py and check-review-rounds.py): 37 (≈52%).
  • Anything under scripts/: 47 (≈66%).

Why one hop is so expensive: 34 of those 37 are check-plan-code.py alone. It is the mutation harness, and almost every scripts PR touches it. So the cost of a closure is set by its most-changed member, not by its size. One busy file pulls the "safer" option almost all the way to "void on every scripts merge".

Why the immediate-file heuristic is acceptable here, not merely cheap. What it gives up is the interaction case: a dependency changed on master and quietly changed what the flagged line means. Three things bound that case.

  • The dependency change had its own review and gates when it merged.
  • The merged tree still runs the full CI, including the mutation sweep. A dependency change that broke the flagged line's tested behaviour goes red there.
  • A line edited on the PR branch after the last review is still caught by check-review-recorded.py.

What remains is an untested change in meaning, arriving through a dependency, on a line whose own file did not change. ⚠ I have not measured how often that happens; it is inferred to be rare, not shown. If it ever bites, the tool to reach for is the traced closure, with check-plan-code.py handled specially, for example by binding to the one function the file uses rather than the whole file.

You asked · answered 11-08 20:10

“I also asked if a periodic (or rule-based) full sweep without the cache can be a safety net (insurance) to detect a false verdict.”

Yes, and for mutation verdicts that insurance already runs, and it fired this morning. For loosening answers, a sweep cannot catch a false one, but a periodic AUDIT can.

Mutation verdicts: the safety net exists and is uncached.

  • A pull request runs only the manifests its diff selects.
  • Every push to master runs the full sweep, every manifest. A daily schedule (cron: '23 7 * * *', .github/workflows/ci.yml) runs it again even when nothing merges. A red result opens a sweep-red issue.
  • Nothing in it is a reused verdict. Each mutant runs in its own fresh process, so the caches can never hand a mutant the unmutated answer (§5 of the CI sweep-speed page).

Evidence that it works: the scheduled run at 11-08 14:21 UTC on 311d3631 went red. That red is how the 120-second limit problem was found; it was fixed in PR #538. Every master push since (4d7766f8 through b15e4f96, five runs) is green. The sweep-red issue #499 is still open and should be closed against those runs; I'll do that in the docs batch.

Loosening answers: a sweep is the wrong tool. A loosening answer is a reviewer's judgement about what a line means ("the branch still refuses everything master refused"), not a test result. Re-running tests cannot falsify it. If a test could detect the loosening, the mutation sweep would already be the gate, and the HOLD exists precisely for lines where tests cannot tell stricter from looser.

But your insurance idea does fit the residual here, as a rule-based audit rather than a gate.

  • The audit: after each merge, for every not a loosening answer the merge relied on, check whether any file in the flagged file's closure changed between the commit the answer was given on and the merged commit.
  • If none changed, there is nothing to do. If one did, list it for a re-read.
  • It costs only git log arithmetic, with no reviewer, and it never blocks a merge.

That gives the closure's coverage without its 52% void rate. The immediate-file rule stays the merge gate, and the closure check becomes the insurance that catches the interaction case after the fact. ⚠ After the fact means the line is already on master when the audit flags it. The fix then becomes a follow-up PR, not a blocked merge. That is the trade, and it is the same one the daily full sweep makes.

Recommendation: file this audit as the concrete form of the backlog row from the first answer. It replaces "bind to the closure", which costs 52%, with "audit against the closure", which costs no merges. It goes in the next docs batch, and building it is your call.

The re-read itself can be exactly as strict as C. What differs is WHEN it happens and HOW OFTEN, and C wins only on timing.

Both are the same instrument: a review round answers LOOSENING-CHECK <id> for the flagged line, read on the new tree. If the audit's re-read uses that same protocol, as I would build it, the strictness of each read is identical. The comparison is about everything around the read:

So, strictly: C is safer on two counts. It catches the problem before it lands, and it does not depend on the closure being right. The audit gives up both in exchange for not re-reviewing on every merge. Where the closure is complete, the two catch the same set of meaning changes. C's extra triggers, from files outside the closure, cannot change what the line means; they only cost rounds.

Is "after the fact" acceptable here? For these gates, I think yes, with one condition.

  • A loosening in a merge gate is a gate that briefly lets more through. It is not a production defect.
  • Its exposure window is the time until the audit runs plus one follow-up PR. That is about the same window the daily mutation sweep already accepts for untested code.
  • The condition: the audit must fail loudly when it cannot compute a closure, reporting CANNOT RUN, never silence. Otherwise a closure that silently comes back empty turns "insurance" into a check that cannot fire.

⚠ The exposure window is inferred from how the sweep behaves; the audit is not built, so nothing about it is measured yet.

If you want C's timing without C's cost, there is a middle variant. Run the same closure check before merge, inside check-merge-ready.py, but only for answers whose closure changed. That is A plus closure binding, the 52% option from the second answer: pre-merge timing, paid only when the closure moved. I have added this to backlog #580 as its alternative, so the choice between "after the fact, nearly free" and "before merge, ≈half the rounds" is yours when it is built.

6. What stays fail closed

A changes ONE comparison: the whole tree becomes the flagged file. Everything else in the HOLD stays as it is (per the build brief; verify against the shipped code once it lands):

  • an id with no answer stays HELD;
  • an answer from a verdict whose gate did not run, that names no head, or that is not JSON does not count;
  • a dirty: null record (the wrapper could not describe the tree) does not count (tree_matches' "not a dict" rule);
  • a reviewed head that cannot be read here does not count;
  • a finding answer from ANY verdict stands until a later round of the same half clears it;
  • the flagged file renamed or deleted in either tree does not count;
  • the other HOLD reasons are untouched: a falling self-test count, a dropped gate invocation, pin falls, deploys, NO-REVIEW:.

And the merge itself stays yours to see: a HOLD the gate cannot clear is still verified line by line before any merge.

§1Background — what a deploy claim is, and who checks it

The skippable version

This project keeps a long file called docs/roadmap-to-launch.md. Near the bottom it carries a line that says which build of the application is running in production:

docs/roadmap-to-launch.md:1239unchanged context
- **Deployed: release v7, 2026-08-18 04:35Z** (`fly status`: web + worker both v7). Shipped the #36

That line is a claim about the world, and it lives in a document. Documents do not update themselves. So the interesting question is not whether the line is currently right — it is what would ever tell you it had gone wrong.

The project has a family of small Python scripts it calls ratchets, which run in CI and fail the build when a document contradicts something. There are ten of them in scripts/. Every one of them compares a document to another document, or to the source tree. Not one of them opens a network connection to production.

The narrow prerequisites

Three facts do the work in this change. Each was checked by a command, not recalled:

FactHow it was established
check-roadmap-consistency.py compares the roadmap to itself Its only input is ROADMAP = "docs/roadmap-to-launch.md" (scripts/check-roadmap-consistency.py:69); it checks that the “next actions” prose does not name work whose own checkbox is already ticked. Both operands come from one file.
The deployed image carries no commit identifier grep -E 'GIT_SHA|COMMIT|BUILD_ID|SOURCE_SHA|VERSION' Dockerfile fly.toml → exit 1, zero matches. The Dockerfile’s only build args are the two public Supabase values (Dockerfile:37-38).
Fly knows a digest, not a commit flyctl image show returns sha256:a654eb22… and a deployment tag. Nothing in that output, or in flyctl releases, references git.

§2Intuition — two different drifts wearing one word

Say the roadmap claims “Deployed: release v7”. There are two entirely different ways that sentence can be false, and they need different instruments.

Version drift is the easy one: the roadmap says v7 and production is actually running v6. Both numbers are readable — one from a file, one from a CLI — so a person or a script can put them side by side. This is the drift that has actually bitten, twice: production once ran eight days behind on a migration while every file on disk looked correct, and on the morning of 2026-08-18 a merged money-path fix sat undeployed because merged had been read as shipped.

Commit drift is the hard one: production really is on v7, and v7 really is the newest release — but the image that became v7 was built from a stale tree. Every visible number agrees. The claim “v7 is live” and the claim “v7 contains commit 7cb22de” look like one sentence and are two, and only the first has anything that could contradict it.

The claim chain. PR #111 wires up the right-hand half: flyctl releases against the roadmap line. The left-hand half is not merely unchecked — the information required to check it was never recorded at build time. Backlog #53 is that gap, written down.

Why nothing caught it

The project’s own process document requires three layers to agree — git, the files on disk, and the running system. The instruments only ever covered two of them:

git historywhat was committed check-test-countscheck-arch-findings
files on diskroadmap, backlog, ADRs, specs check-docscheck-roadmap-consistencycheck-producer-enumeration

Three layers, and what looks at each. The third lane was reachable — flyctl is installed, and check-deployed-bundle.ts already reads the live server — but no step told anyone to look. Production was in fact checked during both of 2026-08-18’s briefings, purely because a saved memory said Session Resume must read the running system. A memory is not a step list.
The pivot, in the reader's own words

The change exists because of a question asked from a previous briefing page: “how did you find the roadmap is out of sync? if you can find it whenever you need to know, that may be just enough.”

That question dissolved the script that was about to be written. The answer was: one command. The capability was never missing. Only the trigger was.

§3Boundaries touched

This is a documentation change, so it crosses no module boundary — no function signature, no type, no storage seam moved. What it does cross is the boundary between what a document asserts and what a system is, which in this project has been the more expensive kind. Four rows, and the fourth is the one that would have bitten silently.

BoundaryWhat crosses it What each side may assumeWhat happens when that assumption is violated
new /brief skill ↔ Fly production Two strings: the live release version from flyctl releases, and the roadmap’s Deployed: release … line. Skill side: flyctl is installed and already authenticated for this app.
Fly side: assumes nothing — it is a read.		 If flyctl is missing or unauthenticated the command errors and the step is skipped. Per the project’s own rule — “cannot run” is a failure, never a pass — that must be reported as NOT RUN, not omitted. The skill text does not say this in so many words; it inherits it from CLAUDE.md. See §6.
roadmap prose ↔ live release version The claim v7. Roadmap: may assume it is read by a human who trusts it.
Reader: may not assume it is fresh — it is hand-maintained.		 The reader plans against a production that does not exist. Measured twice: eight days of an unapplied migration, and a merged-but-undeployed money-path fix. Nothing failed; things were simply believed.
absent image digest ↔ commit SHA Nothing. There is no crossing — that is the finding. Fly: a digest identifies bytes, and it never claimed to identify a commit.
Everyone else: assumes, without evidence, that the newest release was built from the newest tree.		 A release built from a stale tree looks completely healthy: right version number, right timestamp, matching roadmap line. Nothing anywhere says otherwise. This is backlog #53, and it is deliberately not fixed.
docs/backlog.md ↔ check-docs.py The single new table row, as text. Row: must be | N | …, must have a unique N, and — if its Status cell contains ✅ — must not lead with a bare severity marker. A duplicate id or a closed-but-still-red row fails CI. Row #53 leads with 🟢 and its status is OPEN, so the marker rule does not fire. This is the row’s real contract, and it is enforced by a script added one PR earlier (#109) that found three violations a careful hand pass had missed.
The invariant worth writing down

A version number and a commit are different claims about a deploy, and only the first is currently checkable. Any future statement of the form “production has fix X” is an inference, not an observation — unless someone has separately re-run the behaviour against the live URL, which is exactly what was done for backlog #36 on 2026-08-18.

§4Decisions this change encodes

D1 — The missing thing was a trigger, not a capability

The detection was always one command away. What did not exist was a moment at which anyone was told to run it. So the fix is a step inside a skill that already runs at precisely the right moment — when a briefing is being written, which is when someone is about to trust the roadmap.

The rule this yields

docs/dev-process.md says: “Before adding a rule here, ask whether it can be a script.” This change produces its complement:

Before adding a script, ask whether the check already exists and merely lacks a moment to run.

D2 — Rejected: check-deploy-freshness.py

The obvious move was a new ratchet. It was rejected on two independent grounds, both of which the project has paid for before:

ObjectionWhy it is fatal here
It needs a hand-recorded deploy SHA A script cannot derive the deployed commit today (§2), so the roadmap would have to carry it, written by a human at deploy time. That is the “someone remembers to write state down” class — the same class that produced three stale-state defects on 2026-08-17/18, two of which a careful hand pass missed entirely.
It fires on every docs-only commit Any “has master moved since the deploy?” check goes red the moment a README changes. A gate that cries wolf gets disabled — and worse, it teaches people to ignore the gates next to it, which are load-bearing.

D3 — Filed with a trigger, not a date

Backlog #53 is not scheduled. It names two conditions instead:

docs/backlog.md:68 — row #53, excerptadded
BUILD IT WHEN either
  (a) commit drift actually occurs — a release demonstrably built from a
      stale tree, which has never yet happened
  or
  (b) the Dockerfile/deploy path is being changed anyway, making the
      build-arg nearly free.

Until then the residual risk is: a deploy runs from an unexpected tree
and nothing says so.

Condition (b) is the honest one — a build arg costs three lines if you are already editing the Dockerfile, and a great deal of ceremony if you are not. The shape of the eventual fix is named too, so nobody redesigns it: embed the SHA as a Docker build arg, serve it from the app, and let a check derive both sides. scripts/check-deployed-bundle.ts already reads the live server over the network, so it is the natural home.

D4 — Record the rejected alternative inside the entry

The ⛔ paragraph in row #53 is not commentary; it is the deliverable. A backlog item that says only what to build invites the next reader to re-derive the cheap version and ship it. This project has a measured price for that: backlog #36 spent thirteen review rounds rediscovering a decision that was already written down in three places.

ADR candidates

None. ADRs here record architecture decisions, and nothing structural moved. D1–D4 are process, and the repo has a home for exactly that.

But D1 is a genuine candidate for docs/portable-practices.md — the project’s second deliverable, the measured and project-independent subset. It qualifies on both counts: it was measured (a script was designed, costed, and dropped), and it names no part of this codebase. It is currently recorded only as a blockquote inside one skill file, where it will be read by whoever next edits that skill and nobody else.

Inferred, not measured

  • That the ratchets are blind to production. I read the entry points of check-roadmap-consistency.py and check-docs.py and found no network call, and the other ratchets are described as document checks. I did not audit all ten line by line.
  • That flyctl is authenticated for every future reader. It is authenticated here — that is how v7 was read. Someone cloning this repo has neither the CLI nor the account, and the skill step does not say what they should do.
The limit that deserves its own paragraph

Row #53’s trigger (a) says build it when commit drift actually occurs. But commit drift is, by this entry’s own argument, the thing with no detector. The trigger is partly self-referential: it would fire only if the drift surfaced some other way — a bug that master had already fixed reappearing in production, say — which is detection by consequence, after the cost.

This does not make the deferral wrong. Trigger (b) — “the deploy path is being touched anyway” — is observable and unambiguous, and carries the decision on its own. But the entry currently reads as if it has two independent triggers, and it has roughly one and a half. That asymmetry is not stated in the row.

Not checked at all

  • Whether any past release was in fact built from a stale tree. This is unknowable with the information recorded — which is the entire subject of the entry, and the reason the “0 commit-drift incidents” figure in the stat strip is an absence of observation, not a clean bill of health.
  • The /brief skill step has not been run under failure — no one has confirmed what the briefing does when flyctl is absent or unauthenticated. Reasoning about it is in §3, row 1; observation of it is not.

§7Conclusion

Recommendation — merge as-is; it is already merged, and it was the right call

The pair does what a good deferral looks like: it closes the drift that has actually happened, names the one it has not, and records the cheaper alternative with the reasons it was rejected so the next reader does not re-derive it. There is nothing to change in the diff.

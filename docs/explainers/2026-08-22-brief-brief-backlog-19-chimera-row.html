What is actually wrong

persist_summary merges a worker's result into a video row field by field. Layer (1) is the payload, layer (2) is || (v.data - 'artifacts') — the existing row wins back — and layer (3) re-applies exactly twelve summary-owned fields, but only those the payload actually provides: jsonb_strip_nulls turns an absent key into "no write".

The cloud worker supplies ten of those twelve. The two it never supplies are mdGeneratedAt and mdCorrectionsHash — precisely the two that say which document the row is describing. They are written only by lib/pipeline.ts:271–272 and the regenerate route, and that route is filesystem-only, so on cloud those fields can only ever have arrived from a sync write.

So when a sync transfer and a worker persist interleave, the surviving row is a chimera: quick-view scalars from one document, provenance stamps from another. Neither writer is wrong. A per-field merge simply has no concept of "these fields describe one artifact".

Asked on this page · answered 2026-08-22

Do the sync transfer and the worker persist try to write into the same slot (generation)?

Yes — and more sharply than that: there is only one slot, and no generation dimension exists at all. Both writers contend at both levels:

  • The row. videos is primary key (playlist_id, video_id) — one row per video per playlist, with the whole Video object in a single data jsonb. Both writers UPDATE that same row. They do not write the same fields, and that is the crux: overlapping-but-different field sets into one jsonb, merged per field.
  • The blob. The transfer writes winnerVideo.summaryMd; the worker writes ${padSerial(serial)}_${slugify(title)}.md. When the bases agree those are the identical string — literally the same object. That is why the worker's promote finds the key occupied and discards its own bytes.

The confirming measurement: generation_id / generationId appears in zero shipped .sql or .ts files — only in docs/. The generation dimension exists on paper and nowhere else.

Your question is precisely the one ADR-0006 was written to change the answer to. Under it the address is <tenantId>/videos/<videoId>/<generationId>/…, so two writers get two different addresses and never contend for one object; publication becomes a conditional update of a single pointer, and "which document do these fields describe" is answered by the address itself. This defect exists because today the answer is yes, one slot — and ADR-0006 is still status: proposed, parked since 2026-08-11.

Asked 12:10 · answered late, 2026-08-22 — see the note below

If generation ids are unique (the destination is unique), can interleave still happen?

Yes. Unique destinations remove the collision, not the concurrency. Both runs still overlap in time, both still finish, and both still want the video to point at their result. What is left is a publication race — who becomes current — instead of a destruction race — whose bytes survive. That is a far better failure: the loser's work still exists and is still addressable, so resolving it is a policy choice rather than data loss.

The sharp part, and exactly why §5.2 is load-bearing: uniqueness has to cover everything a run produces, not just the bytes. Generation-scope the body but leave the card in one mutable slot on videos.data, and the card is still a shared destination even though the bodies are not — interleaving there still destroys. That is the whole content of §14 q8, and it is why a unique generation id alone would have left #19 alive.

The spec's round 4 goes further still: both writers append a generation row and there is no loser at all — publication becomes append-then-resolve, not compare-and-swap with a retry.

Asked 16:25 · answered 2026-08-22

Show me an example. I am not clear why a unique destination can still have multiple competing writers.

They are not competing for the destination. They are competing for the reference. Unique addresses mean nobody overwrites anybody's bytes. But a video can only display one summary, so something must answer "which generation is current?" — and there is exactly one of that answer, however many blobs there are. N unique blobs, one shared pointer. The blobs do not race. The pointer does.

The familiar version: git objects are content-addressed and can never collide, yet two people pushing still race — on refs/heads/master. Same shape.

The worked case — one video, a worker job W generating a fresh summary and a sync run S transferring the local body up, each writing its own generation. ⚠ Read this table as the naive publication model — a plain UPDATE of a mutable pointer. It is not what the design specifies; see the correction directly below it.

Worker WSync Scurrent →
t0—— gen-0
t1starts; ~3 min in Gemini starts; reads local bodygen-0
t2writes gen-A blob ✓ reads current → sees gen-0gen-0
t3reads current → sees gen-0 writes gen-B blob ✓gen-0

That is a plain lost update on one mutable cell. The write is unique; the decision is shared. Both writers checked the pointer before the other moved it, so both concluded correctly from a fact that had already stopped being true.

Asked 16:38 · correction to the table above

At t4, W changes current without checking the blob is already updated to gen-B. Shouldn't W compare-and-swap? And S doesn't seem to CAS at t5 either.

Right on both counts — and the conclusion is not "add CAS". It is that the table above models a mutable pointer the design does not have. I introduced a current → cell that two writers overwrite. That is my error, and it is a documented one: the spec caught the same mistake in its own §9 table.

"⟳ ROUND 4 (Codex #12) — the table was still selling a CAS the design had already deleted. … There is no conditional write on the manifest and there is no one row: §5.1 is append-only and current is a view. A planner following the old table would have built a CAS-and-retry protocol against a table that cannot lose a write."

Three publication models, and only the last one is the design:

ModelWhat happens at t4 / t5Status
Plain UPDATE of a pointer Both writes land. Lost update — the table above. Nobody proposed this. My illustration only.
Conditional update (CAS) t4 succeeds (current is still gen-0); t5 fails — current is gen-A, not the gen-0 S read. S re-reads and re-decides on true information. An earlier draft of the spec. Deleted in round 4 — it left "what re-runs the loser?" open as M4.
Append-only, current is a view Neither writes a pointer at all. Both append their generation row. Nothing is overwritten, so there is nothing to lose and nothing to retry. The actual design (§5.1).

The spec's own words on why the third is not just a safer second: "Under append-only there is no race to arbitrate. Both rows land, both are kept, and current is computed by ranking them whenever anybody asks. The winner stops being the outcome of an interleaving and becomes the result of a query, which is a property of the set and therefore identical for every reader, on every replica, forever. M4 is not answered; it stops being a question."

On the literal question — should W check the blob? No, and deliberately not. A blob existing does not mean a generation is complete or publishable: a crashed or abandoned run leaves bytes behind too, and storage cannot tell you which it is looking at. This project has already paid for that inference — the serve path treated an RLS denial as proof of absence and double-charged. Publication has to be a claim someone records, never something inferred from a listing. Under append-only the claim is the row, and the row only lands once the run finished.

Worth noting where this leaves the rest of this page: my earlier answer quoted backlog #17 saying "publication is a conditional update on one row". That row is stale in exactly the way round 4 fixed — it is still describing the CAS design. Flagging, not filing.

Delete the shared mutable cell and the last race goes with it.

Three claims in the filed row that do not hold

"A worker persist can clobber a just-transferred winner body." Backwards on the common path — the transfer clobbers the worker, via a create-if-absent promote.

"The next sync re-compares and re-converges." The inherited stamps are durable and they feed the next decision. Without the race a cloud row has no mdCorrectionsHash, so copyToCloud wins deterministically. With it, the cloud row inherits local's hash, falls through to the recency tiebreak, ties on the inherited timestamp — and newer is a strict >, so it returns false and the answer inverts to copyToLocal. Permanently, with needsRegen: false. With real corrections in play that is user content destroyed silently — the exact outcome the WB-B1 guard was written to prevent, reached by a path it does not cover.

"Extend the fence to a content identity (mdHash / mdGeneratedAt)." Cannot work as written: the worker never sends mdGeneratedAt, so there is no content identity in the payload to fence on.

The decision

Revised after the second question on this page. "Write a spec" is off the table: the fix already has one, closed by your own decision on 2026-08-05. Writing a second design for a defect that already has a design is the two mechanisms for one concern failure this repo has measured before.

Recommendation — measure it, re-file it, do not spec it

Write the interleaving test, run it, and put the output in the backlog row. Then re-file #19 from "pending — needs spec" to "designed away by spec §5.2; blocked on the parked slice" — which moves it to a different queue and makes it visible to the unpark decision instead of sitting in a spec-needed list it does not belong in. Total cost: an afternoon, no design, no migration.

The strongest argument against

A test that proves a defect nobody will fix for months becomes a red suite or a skipped one, and both rot — this project keeps a "known-red: none" line precisely because that decay is real. Worse, running it means standing up the integration stack for a result whose only consumer is a backlog row that could just cite the trace on this page.

Why the recommendation still stands

Because it is not committed. The test is run once, its output pasted into the row as evidence, and the file left uncommitted until the slice that fixes it ships — no red suite, no rotting skip. And the evidence is worth having: the unpark decision for the blob-addressing slice currently rests on a spec that has never converged. A measured, reproducible user-facing defect that the slice provably closes is the strongest input that decision can get — and right now #19's contribution to it is a paragraph of reasoning in an eighteen-day-old table.

Considered and rejected — the interim guard

Extending the in-flight-job probe to cover transferClassA is a two-line change. It only narrows the window (reconcile-serial.ts:231-238 already documents why for A3), and it adds a coordination mechanism the manifest is designed to delete. That is exactly the shape that produced the #17 reservation mess.

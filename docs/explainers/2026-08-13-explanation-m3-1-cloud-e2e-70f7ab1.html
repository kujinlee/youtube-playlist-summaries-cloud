1Background

The skippable version

This repo contains two applications behind one URL. Visiting / runs a server component that reads STORAGE_BACKEND at request time and renders either LocalApp (the original single-user tool, reading the filesystem) or CloudApp (Supabase, auth, a job queue). The existing Playwright suite only ever exercised the local one.

M3 is the acceptance milestone. Its second half, 3.2, was a manual pass against the deployed release — it passed, and found two real defects. Its first half, 3.1, asked for the same journey automated.

The narrow prerequisites

The plan already existed, and had for months. tests/e2e/cloud-library.spec.ts is a describe.skip whose header names exactly what was missing:

tests/e2e/cloud-library.spec.ts:17unchanged — the standing plan
*   1. A SECOND Playwright web server running the dev server with
*      `STORAGE_BACKEND=supabase` on a distinct port, plus a `projects: [{ name:'cloud',
*      use:{ baseURL } }]` entry in playwright.config.ts. (The default project runs the
*      LOCAL app; without this the spec would hit LocalApp, not CloudApp — plan T16/H4.)
*   2. An authenticated browser session: seed a user + playlist + videos via the admin
*      client, sign in via Supabase to obtain the session cookies, and inject them into
*      the Playwright context so middleware.ts admits the cloud routes.
Why "against the deployed URL" could not be done

The roadmap says 3.1 runs against the deployed URL. It cannot, and the reason is a security property working as intended: /dev-login returns 404 in production — a gate that requires both DEV_LOGIN_ENABLED and a local Supabase URL, failing closed on either — and Google OAuth cannot be driven by Playwright. Automating against prod would mean either opening that gate or hand-refreshing a captured session forever. Split into A (this, unattended, local) and B (a prod read-only smoke, deferred), by decision.

2Intuition — the journey, and the leak

The suite is a ladder. Each rung is one test, they share a page, and they run in order — because rung 3 asserts something about the state rung 2 left behind.

The leak

The header of the spec file said, in capitals, that no money was spent. Then rung 4 failed on an assertion about the seeded prose, and the document that came back contained this instead:

what the server actually returnednot the seeded text
Encoder (2:12–2:20) This section outlines the initial setup for the
end-to-end journey within the encoder component. The prose provided
serves as the starting point for the entire end-to-end journey…

The seed said Seeded prose for the e2e journey. What came back is a paraphrase of it — a language model had rewritten it. The serve path had called Gemini. The ledger confirmed it:

spend_ledger, local stackduring the build
    day     | reserved_cents | actual_cents |          updated_at
 2026-08-13 |             12 |            0 | 2026-08-13 22:06:35+00
⚑ The point, and it is not "there was a bug"

The claim was written from intent and nothing checked it. It could have stayed false indefinitely: the suite would have gone green on every run while quietly spending, and the only witness was a paraphrase that happened to look wrong to a human reading the failure output.

So the fix is not "seed the model and move on". The fix is that rung 6 now reads spend_ledger before and after the journey and fails if it moved. Verified: 24¢ before a full run, 24¢ after. A cost claim nothing measures is a wish.

Five beliefs the build corrected

Each was held confidently, each was wrong, and each was corrected by running something rather than by re-reading.

Two dev serversNext refuses two next dev servers in one project directory, whatever ports they are given. The obvious one-config-two-servers shape fails outright.
Cookie injectionHand-writing the @supabase/ssr session cookie asserts a format, not a behaviour. Sign in through /dev-login instead and let the app write it.
The env loadersupabase status -o env emits quoted values; the shared loader kept the quotes. Invisible to jest forever, because next/jest loads .env.local first.
Node 20No native WebSocket, so supabase-js dies inside a constructor with a message that reads like a library bug. CI already pinned 22.
"Absent" playlistsA pre-seeded playlist is not absent from the sidebar — it lists them all at mount. The first rung 3 asserted an absence that was never true.

The suite → spend_ledger

Serve path: materialises a magazine model on first view, by design — the owner-pays-once contract. 12¢ per run, silently. deliberately indirect		 A real form submission at /dev-login, not a fabricated cookie. Test: may assume only that a browser which submits valid credentials ends up signed in. App: owns the cookie's name, chunking and encoding entirely — @supabase/ssr has changed all three across versions. tests/integration/setup.ts → any runner

Loader: assumed it was the only source, and assigned gap-fillingly (!process.env[k]). jest: silently loads .env.local first via next/jest, so the loader's values never won and never had to be correct. 4Decisions this change encodes

1 · Two configs, because one cannot work

Decided: a separate playwright.cloud.config.ts, mirroring the existing jest.config / jest.integration.config split. Rejected: one config with two webServer entries — tried first, and it fails outright: Next refuses two next dev servers in the same project directory whatever ports they are given. Splitting makes the conflict impossible rather than intermittent.

2 · The cost claim is a test, not a comment

Decided: rung 6 reads spend_ledger before and after. Rejected: seeding the model and restoring the "no money" sentence — which would have left the property true and unguarded, exactly as it was when it was false.

ADR CANDIDATE:

Hard to reverse (removing it returns the file to an unverified promise), surprising without context (a UI test asserting on a billing table looks like a category error), and a real trade-off (the assertion couples the e2e suite to the money schema, so a ledger refactor breaks a browser test). Worth an ADR if a second suite adopts the pattern — the general rule being a test that claims to be free must prove it against the thing that would charge.

3 · Rung 4 is skipped for a cost, not a defect

The setup pre-seeds models/{base}.json so the resolver should find one, and the blob is written — confirmed in storage.objects. It still regenerates. Each guess at why costs 6–12¢, and today's debugging put 24¢ through the ledger before this was understood.

Decided: stop, and write the reason into the skip. Rejected: tuning the envelope until it goes green — trial and error on a money path is the wrong way to learn a contract, and each iteration bills.

The contract, now read rather than guessed

Written after the skip: serve-doc.ts:78 calls readFreshMagazineModel({…, titles}), and read-model.ts:37 gates on isFresh(existing, titles). The comment at read-model.ts:45 is explicit that sameTitles compares the envelope's sourceSections against the caller's titles. The seed sets sourceSections: ['2. Encoder']; the resolver's titles almost certainly differ in the numeric prefix. So un-skipping is now a named, bounded edit rather than an open question — which is what a skip should leave behind.

4 · One request is faked, and only one

POST /api/jobs is intercepted in rung 3, because a real one calls the YouTube Data API and enqueues paid work. The id it returns belongs to a row that genuinely exists, created moments earlier — so the refetch, the API response and the render are all real. Rejected: a real ingest (network-dependent and billable) and a fully mocked sidebar (which would test nothing about #37).

6Assumptions and limits

Verified by reading the code

  • The md path never resolves a model — serve-summary-core.ts:28, stated as a requirement.
  • Freshness compares sourceSections to titles — read-model.ts:37,45.
  • /dev-login requires both the flag and a local Supabase URL, failing closed — lib/supabase/dev-login.ts:9-16.
  • The standing harness plan, unchanged since Stage 2a T16 — tests/e2e/cloud-library.spec.ts:17.
  • next/jest loads .env.local — jest.config.ts:1, jest.integration.config.ts:1, which is why the quote bug stayed invisible.

Verified by running something

  • Full suite: 7 passed, 2 skipped.
  • Ledger unmoved across a full run — 24¢ before, 24¢ after, read directly from Postgres.
  • The leak itself: 12¢ appeared at 22:06:35 during a single earlier run.
  • The model blob is written — storage.objects lists …/models/e2emss2nfxy.json.
  • tsc --noEmit clean; 2703 unit / 267 suites unaffected.
  • Node 22 has native WebSocket, Node 20 does not — checked directly before pinning.

Not verified

  • The rung-4 root cause is INFERRED. The sourceSections/titles mismatch is the best reading of read-model.ts; nothing has been run to confirm which value the resolver derives. Labelled as such in the skip.
  • The suite has never run in CI, and is not wired there — it needs a live Supabase stack, the same reason test:integration is absent. So "runs unattended" means "runs unattended on a laptop".
  • Rung 7's sign-out uses a fallback selector chain (.catch() onto a second locator). It passes, but a chain that tries two selectors can pass for the wrong reason, and it has not been mutation-checked.
  • No adversarial review round has run on this branch. Every other change this week went through at least one; this one has had none.
  • The middleware deprecation is unaddressed — Next prints "The middleware file convention is deprecated, use proxy" on every start, and AGENTS.md says to heed deprecation notices. Out of scope here, unfiled at the time of writing.

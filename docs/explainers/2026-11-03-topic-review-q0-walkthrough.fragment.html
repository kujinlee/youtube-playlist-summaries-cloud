The problem in one paragraph

Every review question in review-method.md section 0 asks how much adversarial review to run — one round or many, both reviewers or one, when to stop. None of them asks whether reading the diff is the right kind of check for this change. Some changes go wrong in ways a reviewer reading a diff is bad at finding: a design that fights itself, a parser meeting inputs nobody imagined, a guard that can never go red. Backlog #177 (the open item "the review INSTRUMENT is never chosen, only its dosage") proposes a question asked first — Q0 — that picks the check by the kind of change.

The repo's own one-line justification, quoted in the draft from scripts/check-vocabulary-collisions.py:

“every gate this project owns asks 'is this correct?', which is a LOCAL question and can always be answered yes by patching. A duplicated mechanism is never locally incorrect.”

One section per kind of change

1 · The change moves a seam

Seam here means a boundary in the design: a new module, a change to who owns what, a new protocol or a new vocabulary (the wording is taken from process-checklists.md → A side job inherits NO design approval).

Instrument: an architecture review before building — the review dev-process.md calls Phase 6. Then the normal loop on what gets built.

Evidence: the decision-card-soundness branch is the repo's labelled example: it showed two of the four "this is a seam problem, not a logic problem" signals — three synonyms hid a trigger (two names for one concept), and four designs that were each locally correct never converged (fixes locally correct but non-terminating). Source: the velocity spec §2 and docs/superpowers/specs/2026-09-25-decision-card-soundness-design.md. A more recent case: docs/reviews/architecture-review-2026-11-02-spec-status-facet.md found that later review rounds attacked numbers typed into a spec rather than its design.

2 · Logic inside an existing seam

Instrument: the normal loop — Q1 onward, unchanged. This is most code changes. Q0 adds one line to the round-1 record and nothing else.

3 · A parsing surface

Surface means code that reads open-ended input — a parser, matcher or classifier — where the risk is inputs nobody thought of.

Instrument: a corpus run over real, unseen inputs. Review still checks the claims made about the code.

Evidence (docs/memory/dual-review-what-it-catches.md, the closing-table guard work): six review rounds yielded about seven lexical edge cases; one corpus run over 5,287 unseen inputs produced 456 fires and 2 discrepancies — both of which turned out to be bugs in the ground-truth rule, not in the code. The same note records what review caught that the corpus could not: a safety property stated in a comment and never tested. Hence "review for claims, corpus for surfaces".

4 · A guard

Guard means a check, gate or test whose job is to go red when something is wrong.

Instrument: the mutation sweep (scripts/check-plan-code.py --mutate: deliberately break the code and confirm a named test goes red), including mutating the call site, not only the functions. Review reads what the sweep cannot reach.

Evidence (docs/memory/unit-coverage-does-not-compose.md, finding R9-1 on scripts/check-closing-table.py): a mutation that reverted the whole change at the only place it took effect survived with the suite at 151/151 green. It was found by mutating, and the note says it could not have been found by reading.

5 · Prose only

Instrument: Q1's one round, inside the round cap (Q4c: from round 4, findings are filed, not fixed, unless a blocker). Stop at the "prose floor" — when findings shift from this cannot work to this is under-specified, the section Non-convergence means different things on a DOCUMENT and on CODE already says to stop reviewing and build.

Evidence: the round-cap measurement already in Q4c (over the 14 days to 2026-10-31, rounds 1–3 caught 83% of the fixed Blocking/High findings).

A change of more than one kind takes every instrument it earns, and a seam goes first because the rest review what it settles. A side job that turns up mid-slice re-asks Q0 — the process-checklists.md rule already says "When backlog #177's Q0 lands in review-method.md §0, this is the moment that re-asks it", so that rule's dangling pointer is closed by this draft without editing it.

Half of Q0 is judged, half is meant to be automatic — and that half is not built

You decided Q0's form on 2026-09-24: HYBRID (recorded in the velocity spec's Decisions of record, item 2). The entry — which kind is this change? — is judged, because no definition of "seam" exists that a script can read. The escalation — has this branch started behaving like a seam problem? — is meant to be mechanical, over four signals: fixes locally correct but never ending; each fix adds code; machinery that manages a problem instead of doing work; two names for one concept.

The automatic half is not in this draft. The spec (§3) requires a calibration run first — apply the four signals to finished branches and see whether they separate the ones that thrashed — and that run has not started. Until it reports, the draft says to read the four signals by hand each round, and Q5 (thrashing → architecture review) stays the trigger. If calibration comes back negative, Q0 stays judgement-only, which the spec calls a result, not a failure.

How we would know Q0 chose wrong

The repo's gate rule asks every rule to name the observation that would show it failed. The draft's:

  • a change Q0 sent to the normal loop later shows Q5's thrashing shape, or two or more of the four signals, in a component Q0 did not call a seam;
  • a corpus run or mutation sweep finds a class of defect on a change Q0 sent to review alone;
  • a round-1 coordinator document with no Q0 line — Q0 was not asked.

Either of the first two is recorded in that round's document as "Q0 chose wrong".

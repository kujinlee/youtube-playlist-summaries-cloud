The one thing that reframes this

The corpus did not drain by neglect. It was drained on purpose, eleven days ago, by a decision you took — and the code was left behind. Plan mode is not a feature we forgot to use. It is the residue of a supersession that was carried out deliberately and never finished.

Answered: what plan mode was for, and how it became residueyour question

You asked: “what was the original purpose of the plan mode and why it has become residue” — highlighting the line where I set that reading aside. Fair; here it is, from the tool’s own first commit rather than from the shape of the code.

It was built to stop a planning document lying about its own verification

The very first docstring of check-plan-code.py states the reason, and it is specific:

WHY THIS EXISTS. Three adversarial review rounds on the project-dashboard plan each
found that its stated evidence was wrong, and each found it BY HAND:

  r2  a transcription silently dropped one word from an assertion, and the
      coordinator reported 55/55 against a test it had weakened.
  r3  the plan's blocks did not assemble at all — no import block for one file, no
      `__main__` dispatch for the other, three functions present only as prose. Every
      earlier reviewer had injected the missing pieces into a private harness, so the
      hole survived two rounds. The plan's own evidence read `19/19 mutations caught`
      while a mutation it NAMED survived, and `33 symbols byte-identical` against
      files nobody else could open.

The diagnosis is the round-3 reviewer’s sentence, quoted in that same docstring: “everything the plan says about CODE reproduced exactly; everything it says about its own VERIFICATION did not.” Prose about a measurement is not the measurement.

So the mechanism: a plan tags its code blocks with <!-- file: … -->, the tool assembles them into real files, runs their suites, applies the mutations the plan declares, and generates the evidence block that gets pasted back into the plan. Typed evidence became generated evidence. That is the whole idea, and it was a good one.

Why it became residue — and it is not because it failed

Plan mode was a CI dependency for three hours and eighteen minutes. It arrived at 14:19 on 2026-08-29 (56201500, PR #174) and was superseded at 17:37 the same afternoon (da5cd27e, PR #176). It has since absorbed four full adversarial review rounds and 568 lines of maintained code.

What went wrong was not the guarantee but its route. Making the plan the subject meant the document and the shipped code had to stay byte-identical, and PR #176 measured that tax exactly: 1,551 lines coupled, where “the first bug fixed in either turns CI red until the identical edit lands in the plan and its evidence is regenerated.” Every commit paid it.

The supersession kept the guarantee and deleted the copy. Mutating the delivered scripts directly gives you “the mutation evidence describes the code that ships” without a second copy to keep in sync — strictly stronger, because a copy asserted to match is exactly the thing that had been lying. In the commit’s own words: “Byte-identity with a document was the route, and a poor one.”

So plan mode did not decay. It succeeded, and the fix that superseded it removed its subject. There is no longer a plan-copy of the code that could lie about itself — which is precisely why nothing exercises the mode, and why every defect four rounds found is real but unreachable.

That is also why option B is the weak one: feeding plan mode a corpus means reintroducing the plan-copy whose existence was the original problem. You would be rebuilding the liar in order to keep the lie detector.

“Did the new code take over its purpose, making it obsolete?” — nearly, and the gap mattersyour question

Yes to the guarantee; no to the scope. Plan mode’s job had two halves, and --mutate . inherited only one of them:

Plan mode did thisWho does it now
Prove the mutation evidence describes the code that ships --mutate . — and better, because it reads the delivered files instead of a copy asserted to match them
Prove a plan’s embedded code actually assembles and runs nobody — and nothing needs to, because no plan embeds code any more

So the second half was not taken over. It was dissolved. The question it answered — “is the code in this document real?” — stops having a subject once documents stop carrying code. That is a cleaner outcome than a handover, and it is why I would call plan mode obsolete rather than replaced.

⚠ But it is obsolete on a CONDITION that nothing enforces. Measured just now: scripts/check-plan-code.py is the only file in the repository that looks for <!-- file: … --> tags, and CI invokes it only as --mutate . and --self-test — neither of which reads a plan. So if someone embeds code in a plan tomorrow, nothing notices: not CI, not a gate, not a reviewer’s checklist.

Today that gap is harmless, because the practice stopped. But “obsolete as long as nobody does X, enforced by nobody remembering X” is a convention, and this project’s recorded position is that a convention is what fails quietly. It does not change the recommendation; it adds one line to it.

Amended option A: retire the mode and leave behind a five-line gate that fails if any document under docs/ acquires a <!-- file: … --> tag — with an error that says “plan mode was retired on <date>; this document expects a checker that no longer exists.” That converts the condition from something assumed into something asserted, costs almost nothing, and is the difference between deleting dead code and creating a silent hole where a guard used to be.

But four rounds is a lot of scrutiny for a 16% slice with no callers.

Why the Phase 6 trigger didn’t fire — briefly, since it’s adjacent

Our rule sends four inconclusive rounds to a design review. Round 3 pre-registered a sharper test so it couldn’t be argued after the fact: “if round 4 also produces a self-contradicting artifact, the finding is that the block has no single producer for ‘what was this run about’.”

Round 4 did produce a self-contradicting artifact — so the trigger fired on its literal terms. But the cause that rule named was measured false: evidence(), verify_evidence() and main() now all derive their mode from the same flag and agree. Round 4’s High is one number with two increment sites, not two sentences from two variables. review-method.md says read the trigger off the cause, so I did not convene Phase 6 on evidence() — and escalated this instead, which is the question a design review would actually be worth holding.

Three options

A — Retire plan modemy recommendation

Delete extract, check, evidence, pasted_evidence, verify_evidence, compare_delivered, unsafe_tag and the CLI paths that reach them. Finish what PR #176 started.

Removes: 568 lines (16%), 20 of 44 mutation entries, ~73 self-test cases. Breaks: nothing measured — the only two external importers (check-selftest-counts.py, begin-plan.py) take count_drift, which is module-level and survives. --mutate . shares no function with plan mode. Costs: one slice with its own review round; EXPECTED_MUTATIONS falls, so the ratchet needs a deliberate, documented decrease — this project treats a shrinking count as a red flag, correctly.

Why I lean here: the supersession was already decided and justified in writing. Keeping the code preserves an option nobody has exercised in eleven days while charging review attention at four rounds and counting. Deleting it is the cheapest way to stop paying.

B — Give it a real exerciser

Make at least one living plan carry <!-- file: --> blocks and a mutations declaration, and put a gate on it, so the mode has a corpus that fails when it breaks.

Buys: the four rounds’ findings become defects that matter rather than defects that would matter. Costs: reintroduces exactly the coupling PR #176 removed — that commit measured it at 1,551 lines coupled, where “the first bug fixed in either turns CI red until the identical edit lands in the plan.” Ask yourself first: what would the plan-embedded copy prove that --mutate . over the delivered scripts does not? I could not construct an answer, which is the strongest argument against B.

C — Leave it, and stop reviewing it

Keep the code, mark it explicitly dormant, and exclude it from review scope until something needs it.

Buys: zero work now. Costs: the failure mode this project keeps recording — a comment saying “dormant” is a claim with no falsifier, and the next reviewer has no way to know the scope note exists. It also leaves 568 lines that look live to anyone reading the file. If you pick C, the honest form is a gate that fails if a plan ever starts using the mode, so dormancy is asserted rather than assumed.

  • One branch, one slice: delete the seven functions and their CLI paths, delete the 20 mutation entries and ~73 cases with them.

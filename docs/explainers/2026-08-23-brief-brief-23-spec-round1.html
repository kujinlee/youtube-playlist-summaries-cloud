The decision

You chose "no lease, meter through the ledger" on two facts I gave you. Both were wrong: there is no bound, and there is no meter. So the decision has to be made again on real ones.

Recommendation — capping and metering fixSummary becomes in-scope work, then re-ask the lease

You cannot put an uncapped, unmeterable paid call in an HTTP route — not in this codebase, where every other paid call is bounded and every reservation is a proof. So adding maxOutputTokens, thinkingBudget: 0 and a billing latch to fixSummary stops being a requirement the spec asserts and becomes a task the plan contains. Once the call is genuinely bounded, the lease question can be asked against a real number instead of my guess.

The strongest argument against

It grows a slice that was chosen for being small, and it reaches into lib/gemini.ts — shared with the local path, where capping output introduces a truncation risk on long documents that does not exist today. That is a real behaviour change to a working feature, made in service of a cloud feature. The alternative is to cut scope to the attended cloud route alone and defer the unattended half to M5.

The answer, and the honest caveat

The truncation risk is manageable — assertNotTruncated already exists on this path and a cap can be set from the measured maximum (8,961 chars) with headroom. And the smaller cut does not escape the problem: the attended route alone still needs the call capped and metered, because that is precisely where an unbounded paid call would sit in an HTTP handler.

The caveat I want on the record: this is the second time today I have recommended growing the scope after a smaller version failed review. That was the right call for M1 and it might be motivated reasoning here. The check is that the growth is forced by a code fact rather than by a judgment — fixSummary's signature either takes a billing latch or it doesn't, and it doesn't.

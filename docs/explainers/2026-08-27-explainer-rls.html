1. The short answer

Every one of the 18 tables in public has RLS enabled and forced. Only 11 carry a policy; the other 7 carry none at all, which is deliberate — forced RLS with zero policies means no session client can read or write a single row, and those tables belong exclusively to the trusted server.

The policies themselves are almost boringly uniform. Nearly every one says a version of “the row is yours if you own it”, and there are exactly three ways this codebase spells that. The interesting material is not in the policies — it is in the four mechanisms that route around them, all of which are live in this database right now, all of which are known and filed, and all of which you need in your head before you touch a migration.

Measured, not recalled

Read 2026-08-27 from pg_class, pg_policies, pg_proc and information_schema.role_table_grants on two subjects: the local Supabase container, and production over the read-only claude_ro role. They agree on the table state and disagree sharply on function exposure — §7.

2. The cast: three roles, and which of them RLS can even see

Supabase issues every browser request under one of two Postgres roles, chosen by the JWT the request carries. A third role exists for trusted server code. RLS is only a meaningful control over the first two.

RoleWho arrives as itBYPASSRLSWhat actually confines it
anon An unauthenticated browser — and, by design, a real anonymous guest session on the /try path no RLS policies. With no session, auth.uid() is NULL, so owner_id = auth.uid() evaluates to UNKNOWN → the row is denied. Denial-by-NULL is the workhorse here.
authenticated A signed-in browser, via lib/supabase/client.ts or server.ts — both use the anon key plus the session cookie no RLS policies, keyed on auth.uid().
service_role The worker and trusted server routes, via lib/supabase/service.ts YES Not RLS at all. It walks through every policy. Its confinement is an import-graph scan in CI (§8), plus import 'server-only' and a runtime typeof window throw.

Two subtleties in that table are worth stating outright, because they are the ones people get wrong.

force row level security is not decoration

Plain enable row level security exempts the table’s owner. In Supabase the owner is postgres, and various maintenance paths run as it, so an owner exemption is a real hole. Every table in this repo therefore gets both lines, together, in the same breath:

alter table videos enable row level security;
alter table videos force  row level security;

But force does not touch BYPASSRLS. Measured on the live cluster: postgres and service_role both have rolbypassrls = true; anon and authenticated do not. So forcing RLS closes the owner path and leaves the service path wide open — which is intended, and is why the service path is guarded somewhere else entirely.

RLS filters; GRANT admits. You need both

This one is written into 0006_grants.sql as a comment, because it cost real debugging time. RLS only narrows the rows a role can already reach. Without a base-table GRANT, PostgREST returns 42501 permission denied — a hard error, not an empty result. The two gates compose like this:

request ──▶ GRANT on the table ──▶ RLS policies ──▶ rows (may I touch it at all?) (which rows are mine?) no GRANT → 42501 permission denied ← an ERROR, loud GRANT, no policy → 0 rows ← SILENT, and safe GRANT + policy → the rows the policy admits

Read that middle line again: a granted table with forced RLS and no policy returns zero rows, quietly. That is a legitimate design (it is exactly what the seven deny-all tables do) and it is also a trap — §6 has the case where it silently broke a working feature.

4. Two families: policied, and deny-all

  1. The eleven policied tables — user data

    Playlists, videos, jobs, quotas, and the whole 0027 artifact stack. A signed-in user reaches their own rows and nobody else’s. This is the part RLS is genuinely doing the work for.

  2. The seven deny-all tables — money and infrastructure

    Forced RLS, zero policies, and GRANTs only to service_role. Every one of them is a spend ledger, a budget, a rate-limit config, or a share-token secret. A browser cannot read one byte of any of them, no matter what JWT it presents, because there is no policy that could ever admit a row. The migrations say so in-line:

    alter table ledger_audit enable row level security;
alter table ledger_audit force  row level security;   -- no policies → no session-client access at all
grant select, insert on ledger_audit to service_role;  -- the ONLY grant; mirrors spend_ledger

    This is the strongest shape in the schema, and it is worth recognising: when a table has no legitimate client reader, the safest policy is no policy.

5. The three policy shapes, in the order they were written

Shape A — direct ownership (2026-07, 0002 and 0008)

create policy playlists_owner on playlists for all
  using (owner_id = auth.uid())  with check (owner_id = auth.uid());

using governs which existing rows you can see (and therefore update or delete); with check governs what you are allowed to write. Both clauses matter, and the pairing is what stops the classic attack: without with check, a user could UPDATE their own row and reassign owner_id to someone else, handing their data away — or worse, hand themselves someone else’s. The integration suite exercises exactly that (tests/integration/rls-isolation.test.ts).

Note these have no TO clause, so they apply to PUBLIC — including anon. That is safe because anon’s auth.uid() is NULL and owner_id = NULL is UNKNOWN, never true.

Shape B — ownership through the workspace (2026-08, 0027)

create policy video_artifacts_owner_read on video_artifacts for select to authenticated
  using (workspace_id in (select id from workspaces where owner_id = (select auth.uid())));

Three deliberate differences from Shape A, each of which you should copy if you add a table here:

  • for select, not for all. Clients read this stack; only service_role writes it, through RPCs. Writes are not merely unpoliced, they are ungranted.
  • to authenticated. Explicitly excludes anon from the policy even though anon holds the SELECT grant. The grant admits; the policy then produces zero rows for anon.
  • (select auth.uid()), wrapped in a subquery. Not cosmetic: the wrapping lets the planner evaluate it once per statement instead of once per row. On a table scanned per artifact lookup that is the difference between a fast and an unusable query. Shape A’s bare auth.uid() is the older idiom.

Ownership is indirected through workspaces.owner_id rather than compared to a path segment. The migration is emphatic about why: the workspace id currently equals the owner id by construction, and nothing is permitted to depend on that, so that multi-workspace users can ship later without re-authorising anything.

Shape C — the storage path segment (0007)

create policy "artifacts_owner_rw" on storage.objects
  for all to authenticated, anon
  using      (bucket_id = 'artifacts' and split_part(name, '/', 1) = auth.uid()::text)
  with check (bucket_id = 'artifacts' and split_part(name, '/', 1) = auth.uid()::text);

Blob keys look like <owner_id>/<playlist_key>/<key>, so the first path segment is the tenant. anon is listed intentionally — guest sessions write under their own anonymous uid, and an unsigned request still fails on the NULL.

⚠ This policy is pinned, and a money guard depends on its width

An object hidden by RLS returns a 404 byte-identical to one that was never there. The serve path decides whether to pay for a fresh model by asking storage whether the cached one exists — so an over-narrow policy makes a present object look absent and the code re-pays. Measured: 6¢ → 12¢ and a second live Gemini call, with every test green. scripts/check-storage-grant-pin.py is a tripwire on the policy text; if you edit it, the check fails and asks you to read docs/adr/ ADR-0008 first. It cannot tell a widening from a narrowing — that judgement is yours.

6. ⚠ Four ways past RLS that are open in this database

This is the section that matters. None of these is a secret or an unreported bug — all four are filed, bounded and understood. But every one of them is a path where a correct-looking policy provides no protection at all.

  1. SECURITY DEFINER functions do not run RLS — and anon can call most of them

    A security definer function executes as its creator, so policies do not apply inside it. It must do its own authorization. This repo has 22 of them.

    Now the sharp edge. Every migration in the repo writes this pair, which reads as “anon excluded”:

    revoke all on function f(...) from public;
grant execute on function f(...) to authenticated, service_role;

    It is not. PUBLIC is a pseudo-role; anon is a named role, and Supabase grants it EXECUTE separately at CREATE FUNCTION time through pg_default_acl. Revoking PUBLIC leaves the named grant untouched.

    Measured on production, 2026-08-27: 26 of 44 functions in public are anon-executable — 10 of them SECURITY DEFINER.

    What keeps that safe today is that 8 of those 10 check auth.uid(), which is NULL for anon, and the remaining two (handle_new_user, reserve_serve_model_meta) were read in full and are benign. That is a safety record, produced by eight authors independently remembering — not a mechanism. Filed as backlog #33 (the one-time revoke) and #54 (the durable default). scripts/check-anon-exposure.py is the detection half.

    The fix pattern already exists and is visibly working. Every 0027 function writes revoke all … from public, anon, authenticated, service_role — and not one of them appears in the production exposure list.

  2. TRUNCATE walks past RLS and past row triggers

    Supabase’s pg_default_acl hands the session roles arwdDxtm on every table postgres creates in public. The D is TRUNCATE, and a bare grant select afterwards is additive — it narrows nothing.

    Measured, identical on local and production: anon holds TRUNCATE on 13 of the 18 tables — including spend_ledger, ledger_audit, serve_model_charge, share_tokens and correction_spend.

    TRUNCATE fires neither RLS nor a row trigger, so it would walk straight past both the policy and the append-only trigger that is 0027’s central invariant. During review, anon truncated video_artifacts to zero rows in a test.

    The bound — state it whenever you state the hazard

    PostgREST exposes no TRUNCATE verb. Reaching this needs a direct Postgres connection with the anon role, which the Data API does not provide. It is a latent privilege, not a reachable exploit — which is why it is an orange backlog row and not an incident.

    The remedy is the revoke-before-grant discipline, and you can see it land in the catalog: the five 0027 tables carry SELECT and nothing else; the thirteen older ones still carry TRUNCATE, REFERENCES and TRIGGER.

    -- 0027, and this is the pattern to copy:
revoke all on video_artifacts from public, anon, authenticated, service_role;
grant select, insert, update, delete on video_artifacts to service_role;
grant select on video_artifacts to authenticated, anon;

    Revoking first makes the resulting privileges a property of the migration file instead of a property of whichever cluster it happened to run on.

  3. service_role bypasses everything, and the database does not stop it

    service_role has BYPASSRLS. It reads and writes every row of every table, including the seven deny-all ones. BYPASSRLS does not bypass table GRANTs, which is why 0006 grants it explicitly — but it does bypass every policy on this page.

    So the boundary is not in Postgres. It is that the service key must never reach the browser, and that is enforced by three things in the application: import 'server-only' at the top of lib/supabase/service.ts, a runtime typeof window !== 'undefined' throw, and an import-graph scan in CI (npm run check:confinement) that walks every import edge — including side-effect imports, re-exports, dynamic import() and require() — to prove no client-reachable module can pull it in.

    When you are reasoning about whether some code path is safe, the first question is not “what does the policy say?” but “which client is this — createClient, createServerSupabase, or createServiceClient?” Only the first two are subject to RLS at all.

  4. A security_invoker view needs a policy on every base table it touches

    The three current views (video_summary_current, video_artifacts_current, video_generations_collectable) are all security_invoker=true, meaning they run as the reader, not the view owner. That is the safe setting — but it has a cost that is easy to miss.

    The reader now needs SELECT and a policy on every base table the view joins. During review, adding force row level security without adding the matching policies produced permission denied for table workspace_videos: the security fix made the serve path unusable.

    The subtler version is worse, because it does not error. On video_artifact_sources, a missing policy would have made a not exists probe inside the view vacuously true for an authenticated owner and false for service_role — the same manifest ranked differently depending on who asked. The migration says it plainly: “force RLS plus zero policies is the shape that produces it.”

    So: forced-RLS-with-no-policy is safe as a table-level decision and dangerous as an accident. If a client-readable view reads the table, the table needs a policy.

Not in CI

The integration suite and the schema gates both need a live database, so CI does not run them. CI runs tsc --noEmit, the unit suite, and the service_role confinement scan. If you change a policy, the isolation tests are on you to run locally — a merge can go green without them.

9. If you change anything: the checklist

  1. Adding a table

    enable and force RLS. Then revoke all … from public, anon, authenticated, service_role BEFORE any grant — otherwise the platform’s defaults survive and your grant select narrows nothing. Then grant exactly what is needed. Then decide, explicitly, whether this table has a legitimate client reader; if not, write no policy and say so in a comment.

  2. Adding a policy

    Prefer Shape B: for select to authenticated, ownership indirected through workspaces.owner_id, and (select auth.uid()) wrapped. If the policy admits writes, it needs with check as well as using — and a test that a user cannot reassign owner_id.

  3. Adding a function

    Ask first whether it needs security definer at all — security invoker lets RLS do the authorization for you, and most of this repo’s functions are invoker for that reason. If it must be definer, it does its own ownership check, and you write revoke all … from public, anon, authenticated, service_role, naming anon explicitly. from public alone does nothing to anon.

    Also pin set search_path. An unpinned helper reached from inside a security definer set search_path = '' function fails at runtime, from a constraint, three files away.

  4. Adding or editing a view

    Set security_invoker=true, then confirm every base table it joins has both a SELECT grant and a policy for the reading role. Check specifically for not exists / not in subqueries: those go vacuously true when RLS hides the rows, and they fail silently rather than erroring.

  5. Before you believe it works

    Run ./scripts/check-schema-gates.sh and npm run test:integration locally. Then ask the question this project keeps having to re-learn: a privilege is not a capability. has_table_privilege saying INSERT is granted has already coexisted with the insert failing, because a CHECK runs as the writing role. Assert by performing the operation as the role in question, not by asking the catalog whether it is allowed.

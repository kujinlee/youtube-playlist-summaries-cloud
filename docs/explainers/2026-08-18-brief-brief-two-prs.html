The shape — why "unmerged" means nothing here

Eleven local branches. git branch --merged calls ten of them unmerged. Only two are actually alive.

A squash merge replays the branch as one new commit, so the branch tip is never an ancestor of master. Git therefore reports every squash-merged branch as unmerged, forever. The signal is not git — it is the PR state.

Checked each one: PRs #52, #53, #54, #55, #56, #57, #65, #67 are all MERGED. docs/premise-discipline backs PR #102, which was CLOSED unmerged — that one is abandoned work, not shipped work.

↩ Asked from this page: so was it fixed by checking PR state?

Yes for the deletion — no for the recurrence. Two different meanings of "fixed", and it is worth separating them because this is the second time today the same distinction has come up.

What was actually done. Every branch was re-queried at the moment of deletion with gh pr list --head <branch> --state all — not from the earlier scan, and not from git branch --merged, which is the thing that lies here. Each branch's SHA was written to a recovery file first, so every deletion is one git branch <name> <sha> away from being undone. So the decision rested on PR state, exactly as the paragraph above says it should.

But nothing stops it happening again. That was a careful manual pass, and a careful manual pass is precisely what the ✅-marker section of this page just finished demonstrating the limits of — a convention plus a hand check found two rows; a script found three more.

Next time branches accumulate, the same wrong instrument (git branch --merged) is still the one that comes to hand, and the same person has to remember not to trust it. This is an instance fix, not a class fix, and it is recorded that way rather than counted as done.

It is scriptable — enumerate local branches, ask the PR state of each, report which are dead and which are genuinely unmerged. Roughly fifteen lines, and the same argument as the marker ratchet applies. Not written yet, and deliberately not written silently: the stakes here are clutter rather than money or a misleading status, so whether it earns a place among the repo's gates is a judgement call that belongs to the reader, not to me.

↩ Asked from this page: if the roadmap-refreshing mechanism used PR state, would the roadmap checks then be accurate?

It would fix one layer of three, and the layer it fixes is not the one that has cost this project money.

First, two things checked just now rather than assumed. check-roadmap-consistency.py does not read git, GitHub, or anything outside the document — its stated job is that "the roadmap's summary block must not name work that is already ticked done." It compares the roadmap against itself. And across every script in scripts/, nothing queries PR state at all. So yes: wiring PR state in would be strictly more than exists today.

The third layer is the expensive one, and today proved it twice. Merged ≠ deployed — backlog #36 was merged while production still ran v6, and nothing would have said so. Deployed ≠ working — v7 was live, but "the encoder is in the running image" stayed an inference until a Korean-titled video was actually ingested. And the precedent that made all of this worth doing: production once ran eight days behind on a migration while every file on disk looked correct.

A PR-state check cannot see any of that. It would have reported ✅ for all three.

There is also a reason the roadmap does not store PR state today, and it is not an oversight. It used to carry a master = the merge of PR #N field, deleted 2026-08-12 after being wrong four ways. The conclusion drawn then was not "derive it more carefully" — it was don't store a derivable value at all; point at the source. Adding a script that re-derives PR state into the document would re-create the cache, just with a fresher fill. The better shape is a check that compares the claim to the source and fails on drift — which is exactly what check-test-counts.py does for test numbers, and what nothing yet does for merge or deploy state.

↩ Flagged from this page: "is there any falsifier on a deploy claim at all? Right now, no."

The obvious design is the wrong one, and noticing why is what makes a cheap version possible.

The trap: a check that asks production directly. It needs credentials and a network, so it will often be unable to run — and this project's own rule is that "cannot run" is a FAILURE, never a pass. A gate that goes red every time someone is offline is a gate that gets commented out. That is the unfalsifiable-guard family arriving from the opposite direction: not a check that can never fail, but one that fails so often it stops meaning anything.

The cheap version needs no credentials and no network. Staleness is detectable from git alone, provided the roadmap records which commit the live release was built from — not just its version number.

FAILS IF the roadmap names a deployed release, and master has advanced past the commit that release was built from, while the surrounding text still reads as though production were current.

That catches the exact failure this project has already paid for — production running eight days behind while every file on disk looked correct — and it catches the milder version from this morning, where master carried the #36 fix and production did not. It says nothing about whether the deployed image works; that still needs the kind of run a Korean-titled video provided. But "the claim is now older than the code" is mechanically decidable, and it is the half that goes stale silently.

One prerequisite, and it is small: the roadmap currently records "Deployed: release v7, 2026-08-18". It would also need the SHA that release was built from — which is the one thing about a deploy that is not derivable after the fact, and therefore the one thing genuinely worth writing down.

↩ Asked from this page: are you suggesting this as a solution? Why not implement? Is it the best solution or a fragile one?

Suggesting it: yes. Best: no — it is fragile, in two ways that should have been named before proposing it.

Fragility 1 — its prerequisite is "remember to write something down." Recording the SHA at deploy time is a manual step in the loop, which is precisely the failure class this page already documents three times over: the roadmap's PR field, the severity markers, the stale task subject. A fix founded on a human remembering to record state is the same defect one level up.

Fragility 2 — "master has advanced" is a noisy signal. Master moves on doc-only commits constantly; several did today. A gate that fires on every docs PR gets ignored, then disabled — and it teaches people to ignore its neighbours too.

Two things found by checking rather than assuming. scripts/check-deployed-bundle.ts already reads the live deployed app — it fetches /login and scans the served bundle for leaked credentials. Its docstring exists to make exactly this point: a static check "emits byte-identical output everywhere… someone sees OK and ticks a box believing production was verified." So reading the running system over the network is an established pattern here, not a new risk. And a grep of Dockerfile and fly.toml finds no embedded commit SHA — nothing to derive from today.

The better design: embed the commit SHA at BUILD time, serve it from the deployed app, and let the check derive both sides. No manual step, and the comparison becomes exact — "prod runs commit X, master is Y" — rather than the proxy "master moved". That removes both fragilities. It costs a Dockerfile and deploy-path change, which makes it a genuine fork rather than a cheap add.

Why it was not simply implemented. The reason given in chat was context pressure, and that was weak — this reader has already said not to hesitate on decisions that are mine. The real reason only appeared on checking: the cheap version is the wrong one, and shipping it would have added a noisy gate to a repository whose entire discipline is that gates must be trustworthy. Pausing was right; the reason first offered for pausing was not.

↩ Asked from this page: how did you find the roadmap was out of sync? If you can find it whenever you need to, that may be just enough.

That is right, and it dissolves the gate entirely. Shipped as a three-line skill step instead of a script.

How the drift was actually found: one command. flyctl releases, compared by eye to the roadmap's "Deployed: release …" line. No credentials beyond a CLI that is already installed, no new infrastructure, no bookkeeping.

So the capability was never missing — only the TRIGGER was. The briefing's ground-truth list did not mention production at all, and every check it did run is blind to that layer: the ratchets compare documents to documents, and check-roadmap-consistency compares the roadmap to itself. Production got checked in both of today's briefings only because a memory says Session Resume must read git, files and the running system — and a memory is not a step list.

The fix is the two commands, added to the briefing's ground-truth list, with the mismatch named as the finding. It runs exactly when someone is about to trust the roadmap, costs nothing when nothing has drifted, and cannot rot the way a hand-recorded SHA would.

The rule this yields is the inverse of one already in the spine. dev-process.md says "before adding a rule, ask whether it can be a script." The complement, learned here: before adding a script, ask whether the check already exists and merely lacks a moment to run.

Bounded honestly: this catches version drift (live release vs the claim), not commit drift (a release built from a stale tree). Version drift is what has actually happened — twice.

↩ Asked from this page: what has been done about the stale task subject, is it still stale, and what was the root cause?

What had been done: nothing. It was reported as a finding on this page and left there. That is worth saying plainly — a briefing that surfaces a defect and does not close it has moved the problem, not solved it.

Was it still stale: yes, until this question arrived. Re-checked: the subject read "PR #67 OPEN … MERGE IS THE HUMAN GATE", the description opened "NOT MERGED; merging is the human gate", and status was completed — the entry contradicted itself in two fields while PR #67 had been merged since 11 August as squash 0aac16d. Now fixed: the subject describes the work, and the description opens with the merge and its sha.

Root cause: transient state was written into a field nothing re-reads.

status is the field designed to change, and it was updated correctly. But the subject and description were composed as a status snapshot — "OPEN", "NOT MERGED", "the human gate is next" — so they froze at the moment of writing. No workflow revisits them, because nothing needs to: the machine-readable field was already right.

The fix is not vigilance. It is not putting state there in the first place: a subject should describe the work, and status should live in status. Any subject naming a phase — "PR open", "awaiting review", "next up" — is guaranteed to rot.

This is the third instance of one pattern, and the project has already paid for it twice:

WhereThe stale thingResolution
Roadmap master = the merge of PR #N — a field holding a value that moves every merge DELETED 2026-08-12. It was wrong four ways in a short life; three were omissions or copy-forwards, and the fourth repeated inside the PR that added the warning against it

The roadmap's own conclusion generalises to all three: prose "cannot defend, because a paragraph cannot refuse to be skipped the way a required parameter can." Where a value can be derived — from git, from a PR's state, from a status field — writing it down a second time creates a copy that can only drift.

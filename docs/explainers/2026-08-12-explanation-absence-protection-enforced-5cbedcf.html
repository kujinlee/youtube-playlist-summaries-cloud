1 · Background

Skip if you already know how serving a summary works

When someone opens a summary in the cloud app, two blobs matter. The summary markdown is the source of truth — a Gemini call produced it once and it is never regenerated for free. The magazine model is a structured {lead, bullets} rendering of that markdown, used to draw the page. The model is a derived-cache blob in the glossary's terms: safe to lose, because it can be rebuilt from the markdown.

"Safe to lose" is not "free to lose". Rebuilding the model costs a real Gemini call, so the serve path reserves money against the daily cap before generating one. Both blobs live side by side under the same folder: <owner-id>/<index-key>/<base>.md and …/models/<base>.json.

So the serve path asks one question before spending: is the cached model already there? If yes, serve it. If no, pay to rebuild it. Everything below is about how badly that question can be answered.

The codebase already knew the general shape of the trap. BlobStore exposes two reads: the plain get, which returns null, and tryGet, which returns a tagged result so a caller can tell absent from could not be read. Its own doc comment explains why, and names the incident that bought it:

/** Like `get`, but distinguishes *absent* from *could not be read*.
 *
 *  **Use this instead of `get` before any irreversible or billable decision.** Treating an
 *  unreadable read as "absent" is the defect class that produced a Blocking and three Highs in the
 *  Stage 3 cloud-sync review, and a live double-charge on the serve path: a transient Storage 5xx
 *  made an EXISTING magazine model look missing, so the serve path reserved and regenerated it —
 *  6¢ → 12¢ for a model already in the bucket …

There is also a companion flag, provesAbsence, which a store sets to declare whether its "no bytes" answer is a fact. The local filesystem store sets it true — its get returns null only on ENOENT and rethrows every other errno. The Supabase store sets it false.

That is the world before this change: the trap was known, an instrument existed, the serve path used it. The change is about a belief that instrument was carrying which turned out to be wrong.

2 · Intuition — one 404, two worlds

Supabase answers a request for an object that does not exist with a 404-shaped error. It answers a request for an object that does exist but is hidden from you by row-level security with — the same thing. Not a similar thing. The same bytes:

World A — genuinely absent
{message:"Object not found",
 name:"StorageApiError",
 status:400, statusCode:"404"}
Paying to rebuild is correct.
World B — exists, policy dropped
{message:"Object not found",
 name:"StorageApiError",
 status:400, statusCode:"404"}
Paying rebuilds a model already in the bucket.

↑ byte-identical — RLS makes the row invisible, so the API cannot say more

This is why provesAbsence is false on the Supabase store. But the store's own comment had gone further than the evidence: it concluded "so a 404 IS provable absence" and listed RLS denial among the cases that come back as unreadable. Both halves were false, and the reason they survived is stated plainly in the new comment:

The shape of the mistake

"the original claim was verified only against a missing object, never against a denied one. Checking one direction of a two-directional question is how it survived."

So: was the application losing money? No — and the interesting part of this change is why not. Follow one request:

1
Read the summary markdown — same store, same principal, same folder. serve-summary-core.ts:66 — const mdBytes = await bundle.blobStore.get(principal, mdKey)
2
Bail out if that read came back empty — 409 "repair needed". The request ends here. serve-summary-core.ts:67 — if (!mdBytes) return { ok:false, status:409, … }
3
Call resolveMagazineModel, passing the markdown body it just read. serve-summary-core.ts:105
4
Probe for the cached model; on absent, reserve money and call Gemini. serve-doc.ts — blobStore.tryGet(principal, MODEL_KEY(base))

If your permissions are broken, step 1 fails, step 2 ends the request, and step 4 is never reached. The markdown read is the corroboration that makes the model's absent trustworthy — not because anything checks it, but because it happens first and fails closed.

The actual defect

That protection was ordering. No signature required it, no comment mentioned it, no test pinned it. Meanwhile the blob store's comment asserted the opposite — that a 404 was proof — so a reader consulting the seam would have concluded no corroboration was needed at all.

Measured directly against hosted Supabase with the owner policy dropped: calling resolveMagazineModel re-reserved and re-generated a model sitting in the bucket — 6¢ → 12¢, attempt_count 1 → 2, a second live Gemini call.

So the change adds no new runtime check. It converts an accident into something a future change has to trip over.

The third row is the one worth sitting with. The money guard is a property of a migration, and the migration does not know it.

4 · Decisions this change encodes

Make mdBody required rather than adding a new permission probe

The obvious alternative was an explicit "can I read this folder?" check just before the reserve. It was not taken: the caller has already performed exactly that read, and a second probe would be a second mechanism for the same concern — plus another round-trip on every serve. Instead the existing read is promoted into a precondition carried by the type system. The commit is unusually honest about what that does and does not buy:

REQUIRED as of 2026-08-11. It was optional "for back-compat with callers that pre-date this
signal", which meant a new caller could reach the charging code without ever having read the
markdown, and nothing would fail. Requiring it makes omission a compile error rather than a
silent loss of the protection. It does NOT defend against a caller that passes a body it never
read — a required parameter defends omission, never a wrong value of the right shape.

Correct the comment rather than change tryGet's contract

absent keeps its meaning; what changed is the documented strength of that meaning ("404-shaped", not "provably absent"). provesAbsence was already false on this store, so the type was right and only the prose was lying. Narrowing the contract would have churned every caller to fix one caller's belief.

Pin it with an integration test that asserts the upstream short-circuit

The new test does not assert that resolveMagazineModel is careful — it asserts that loadSummaryForServe returns 409 and that generateMagazineModel is never reached, with the Gemini mock throwing if it is. That tests the ordering, which is the actual guarantee. The test header states the failure mode for whoever meets it later: "If someone later makes the markdown read tolerant of an empty result, the double charge becomes reachable, and this goes red."

ADR CANDIDATE: the serve-path money guard depends on storage-grant granularity

Hard to reverse (a policy change ships in a migration and applies globally), surprising without context (nothing in 0007_storage_and_rpcs.sql hints that a money guard three files away rests on its grant being coarse), and a real trade-off (the coarse owner-segment grant is what makes the corroboration valid at all).

Measured while writing this explainer: grepping supabase/migrations/0007_storage_and_rpcs.sql for serve / money / charge / reserve returns only the words "preserves" and "preserved". split_part appears in that one migration and nowhere else. The dependency is recorded solely in a comment in lib/html-doc/serve-doc.ts — which a migration author has no reason to open. This is ADR-0005's lesson pointing the other way: there, code looked wrong without the ADR; here, the migration looks fine, and changing it would silently disarm a money guard.

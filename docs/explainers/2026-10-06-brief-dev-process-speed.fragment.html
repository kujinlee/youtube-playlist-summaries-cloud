Ten rounds, then two — what the freeze changed

The sharding change was finished early; the review loop was not. The first version of this page argued that a freeze point would end the loop. It has since been declared and measured twice — so the argument is no longer a proposal.

Text style:

What this page is. Why PR #366's review loop ran long, which specific changes shorten it, and what happened when those changes were applied. Measured from two branches in this repository — not general advice about code review.

What changed since the first version. That version was written at 15:14, before round 9 returned. It said "eight rounds" in five places and presented the freeze as a proposal. The loop actually ran to ten; the freeze was declared after round 8 and rounds 9 and 10 came back clean. A second, independent application on PR #365 converged in one round. §3 is new, §8 is new, and the counts below are corrected.

02Why the loop could not end

This is the structural part, and the single most useful thing on the page. Two separate gates both require a tree that stops changing, and every fix resets both.

The first is the convergence rule in docs/review-method.md:

ObservationAnswer
a Blocking or HighCONTINUE
a finding in the deliverableCONTINUE
non-trivial fixesCONTINUE
two consecutive rounds with neither, every finding aimed at the instrumentSTOP

The second is check-review-recorded, which was the only red check on the branch for most of that day, and which states its own complaint precisely:

FAILED — 8 round(s) ran and guarded code was committed after every one of them.
  The closest verdict never saw:
    scripts/check-plan-code.py, scripts/mutations/check-plan-code.json
  Run one more round against the current tree, or put `NO-REVIEW: <reason>` in the body.

Read those two together. "Non-trivial fixes → CONTINUE" means folding a finding resets the convergence counter. "Guarded code committed after every round" means folding a finding invalidates the newest verdict.

So fixing and converging are mutually exclusive. A loop that keeps folding can satisfy neither gate — not because the gates are wrong, but because its own actions keep resetting the exit condition. Nobody declared which of the two activities was happening, so it did both, indefinitely.

The fix is not a new rule. It is a freeze point: a declared moment after which findings are filed rather than fixed, unless they are Blocking or High in the deliverable.

03What happened when the freeze was declared — measured, twice

New · this section did not exist in the first version

The first version of this page argued the freeze would work. It then ran. Both applications behaved as predicted, and the second is an independent branch with a different author-of-record and a different deliverable.

8 → 10rounds on PR #366: freeze declared after r8, converged at r10
2rounds to converge once nothing was resetting the counter

Application 1 — PR #366, the branch this page is about

The freeze was declared after round 8 in one sentence: Blocking/High in the deliverable folds; everything else files as a backlog row. Rounds 9 and 10 then returned zero Blocking, zero High, and zero findings in the deliverable at any severity. Round 9 produced four findings, all filing-class — they became backlog rows #233, #234, #235 rather than folds. Round 10 produced none.

Application 2 — PR #365, a different branch, same day

PR #365 had run ten rounds of its own. After merging #366 into it, one further round was owed because no earlier round had seen the merged tree. Under the freeze that round produced:

  • Codex half: zero findings.
  • Claude half: CONVERGED — one High, one Medium, one Low, and not one of them in the deliverable. The High was a repository setting; the Medium was a projection in a comment; the Low was four stale numbers in prose.

All three were filed or corrected as prose. Nothing was folded into the deliverable, so nothing reset the counter.

The honest limit on this evidence. Two applications is two, not a trial. Both were run by the same coordinator, which is the obvious confound. What makes it more than anecdote is that the mechanism is structural — §2 shows the gates cannot both be satisfied while folding continues — so the prediction was derived before the measurement, not after. A third application that ran long under a declared freeze would genuinely refute this.

A cheaper move than a round, found the same day

When the Claude half of PR #365's round reported a Medium, the finding rested on three laptop timings. It was sent the CI shard durations — one message — and withdrew its own magnitude, re-deriving the figure from the CI numbers and correcting itself from "1.8×–2.5× off" to "1.21× off". That cost one message. A further round costs roughly 25 minutes and a tree reset.

Generalised: a reviewer handed new evidence will correct its own finding. Running another round to achieve the same thing is the expensive way to do it — and it also resets the convergence counter, which the message does not.

04The five levers, in measured order

Lever 1 — File, don't fold

The evidence runs both ways on one branch, which is what makes this the strongest lever.

TreatmentExamplesCost
Filed as a backlog row#230 #231 #232 minutes; nothing broke; the knowledge is preserved and dated
Folded into the PRr6 whitespace, r7 digit-length, r8 collision guard each generated a fresh round, because every fold is new surface the next round reviews

The two groups are of comparable severity. The difference in cost is a decision, not a property of the findings.

Lever 2 — Declare the freeze

Covered in §2 and now measured in §3. Listed separately because it is the lever that makes the gates satisfiable; the others only make the loop cheaper.

Lever 3 — Stop writing structural claims in comments

At least three rounds were generated by sentences asserting more than the code kept. All real, all from one file:

Comment claimedRefuted by
"every string that matches is one int() accepts"a 4,301-digit run
"a third flag is one dict entry, and disagreement is IMPOSSIBLE"a hyphenated key
"this loop and the mode check in main are its only two readers"there were five

Each was plausible, each was false, each was found by the next reviewer — and each cost a round. The pattern predates this PR; the same file records at :4288: "I WROTE 'AND THE OBVIOUS ENTRY IS IMPOSSIBLE' HERE, AND IT WAS FALSE — r14 Medium, refuted by construction."

Lever 4 — Scope each round to the deliverable diff

Not to the previous fold. Rounds 1 and 5 reviewed ci.yml and it held both times; rounds 2, 3, 4, 6, 7 and 8 reviewed the instrument.

Lever 5 — Push earlier, let CI measure

Local sweeps were an unreliable instrument on this machine and cost roughly two hours. check-surface-recall --self-test takes 81 s against a 120 s SUITE_TIMEOUT — a 1.48× margin. When that control tips, the harness voids the entire shard: all 151 mutations report NOT MEASURED, which is correct behaviour over a failed control and useless as evidence. CI's runners never had the problem.

05Two traps worth more than the levers

A test whose cost depends on the mutation it tests

This happened twice in one hour, and both rules were already written in the file being edited.

The constructNormallyUnder the mutation it exists for
main(["--mutate", ".", …])refuses in milliseconds the refusal is severed → it sweeps the whole repo → 120 s timeout → three CI shards voided
main(["--self-test"])raises during parser construction the guard is severed → it re-enters the suite running it → 150 s recursion

After the fix: 120 s → 4.7 s and 150 s → 5.3 s.

The transferable lesson is not "read the comments". It is that a mutation harness deliberately disables your guard rails, so any test whose cheapness depends on a guard rail holding is a landmine — and it detonates only in the run that matters.

The pattern was live in the file, after eight rounds of fixing it

Found while writing the first version of this page, not during any round. A comment at check-plan-code.py:4717 claimed the dict had "only two readers". At that commit there were four, and two of them had been added by round 8's own fold — the fold that repaired the two-readers problem created a fresh two-readers claim. That is Lever 3 demonstrating itself, unprompted, in the tree as it stood.

06What earned its cost — do not cut this

The mutation sweep caught two things a green test suite could not see, and both would have shipped:

  • a survived mutation — a test that compared a value with itself, so it would have passed no matter what the code did. The suite read 175/175 throughout.
  • a test that voided three CI shards — 453 mutations reporting NOT MEASURED rather than a result.

Neither is visible to --self-test, because both only matter under mutation. If this page reads as "do less review", that is the wrong lesson. The part that measures whether your tests can fail is the part that paid for itself.

07The honest counter-argument

Stated as strongly as it deserves, because the case above is one-sided without it.

Every finding was real. Nothing folded was invented, nothing was make-work, and several were serious — round 7 found a documented command that printed 169/169 passed and exited 0 while validating nothing, which is the single outcome that tool exists to prevent. A reviewer that stops reporting Lows is a worse reviewer.

So the question is not whether the findings were valid. It is who decides which are worth money — and that is not the reviewer's job. Dual adversarial review is excellent at generating findings and has no opinion about cost. Without a filing discipline on the other side it will consume unbounded time on an instrument that was already adequate several rounds ago. That decision was available throughout and simply was not made.

08Five more levers, measured on 2026-10-06

New · all five are from the session that merged #366 and finished #365

These are not proposals. Each one is a mistake that was made, caught, and cost something measurable on the same day — which is the only reason they are worth your attention over the general advice you could get anywhere.

Lever 6 — A measurement names the tree it came from, or it is not a measurement

Three wrong claims in one session, all the same shape: right pattern, wrong population.

ClaimWhy it was wrongTruth
"the reference implementation is gone"searched the main tree; the file is in a worktreeit exists, and is tracked
"zero pages carry the switcher"same tree, same reasonone page does
"63 explainer pages, 21 recomposable"counted a working directory, not the tracked base58 and 16 on origin/master

The third was put in front of a human on a decision card. The rule: a measurement that informs a decision states its ref — origin/master, a worktree path, a commit — not just a number. A bare count invites the reader to assume it came from the obvious place.

Lever 7 — A withdrawn claim must be withdrawn everywhere it reached

A review finding cited three laptop timings and concluded a modelled figure was off by 1.8×–2.5×. Within twenty minutes that reasoning was in four places: a backlog row, a dashboard entry, a commit message and a pull-request body. The reviewer then re-derived the figure from CI data and withdrew it — the real answer was 1.21×.

The conclusion the number supported was still correct. The reason for it was not, and a wrong reason sitting beside a right conclusion is the hardest kind to find later, because nothing it touches looks broken. The rule: when a claim is withdrawn, enumerate its sites before correcting any of them.

Lever 8 — Send the reviewer new evidence instead of running another round

Covered in §3. One message beat one round: the half corrected its own magnitude, and unlike a round it did not reset the convergence counter.

Lever 9 — Tree identity has four answers, and the round is the most expensive

review-method.md lists them cheapest-first: land editorial fixes before the final round; keep the last fixes uncommitted so the reviewer sees what ships; declare NO-REVIEW: <reason>; run another round — last. It also says never to spend a round on this before offering the first three.

Measured the same day: after the final verdict, a one-word comment correction (29 of 37 → 27 of 37) — requested by that very round — re-triggered the gate. NO-REVIEW: closed it in a sentence. A round would have cost ~25 minutes to re-review a comment it had itself asked for.

Lever 10 — Grep for the concept's existing spelling before you name a mechanism

A control was reimplemented in shared code under new names — data-textscheme, data-ts, yps-textscheme — while a shipping page already used data-scheme, data-s, explainer-scheme. Shipping both would have put two coordination vocabularies on one concern: this repository's most-measured defect, 17 instances, and the second spelling is always the one that drifts.

The rule: before introducing a coordination name, grep the concept across scripts/ and every worktree — not just the name you were about to use, which by construction finds nothing.

09Six rules you could paste into dev-process.md

The first three were in the earlier version and have now been exercised; the last three are new from §8. Each is written so a reader can tell when it has been broken.

1 · The filing rule

A finding aimed at the instrument and below High is recorded as a backlog row, not fixed in the PR that found it. Only Blocking or High in the deliverable is folded mid-review.

Exercised: rounds 9–11 produced seven findings under this rule and folded none.

2 · The freeze rule

Every PR declares a freeze point. After it, findings are filed rather than fixed unless Blocking or High in the deliverable — because "non-trivial fixes → CONTINUE" means fixing and converging cannot happen at the same time.

Exercised twice: #366 converged two rounds after the freeze; #365 converged in one.

3 · The comment rule

A comment may describe what the code does. It may not assert a universal — every, impossible, only N — unless a case pins that claim. An unpinned universal is a finding waiting for the next reviewer.

Cost at least three rounds, and a fresh instance was live in the file after eight rounds of fixing that exact pattern.

4 · The provenance rule new

A number that informs a decision names where it was measured — a ref, a worktree, a commit, a run. A bare count is read as coming from the obvious place, and three times in one session it was not.

Fails if: a decision card or a backlog row carries a count with no ref beside it.

5 · The withdrawal rule new

When a claim is withdrawn, enumerate every site it reached before correcting any of them, and record the withdrawal rather than silently editing. A right conclusion resting on a withdrawn reason looks healthy from every direction.

Fails if: a corrected figure appears in one document and its original still stands in another.

6 · The second-spelling rule new

Before introducing a name for a mechanism, grep the concept across scripts/ and every worktree — not the name you are about to use, which by construction finds nothing.

Fails if: two names for one coordination concern are live at the same commit. 17 instances measured; check-vocabulary-collisions.py exists for this.

One free speedup that needs no rule. Under a freeze, the two review halves can run concurrently rather than alternating. The method requires alternation "because a concurrent pair never reviews the fixes" — under a freeze there are no fixes, so the reason for alternating does not apply and the round costs one wall-clock half instead of two.

Q: How are these recommended new rules related to the 10 levers in the previous section?

Six of the ten levers became rules; four could not. The test is whether the lever can be written with a Fails if. The mapping is near-verbatim, which is exactly why the page should have drawn it and didn’t — the second time you have found that same gap on this page.

5 · Push earlier, let CI measure— none
8 · Send the reviewer new evidence instead of another round— none
9 · Tree identity has four answers— none

Why that line falls where it does. A rule here has to be checkable by someone who was not in the room, which is why rules 4–6 each carry an explicit Fails if and rules 1–3 cite what they already cost. The four unmapped levers are real and measured, but each is a judgement about effort — scope this round narrowly, push now rather than later, answer the reviewer instead of re-running, pick the cheapest of four tree-identity answers. There is no state of the repository that shows any of them broken. Writing them as rules would produce four checkboxes nobody can fail, which is the thing this project’s own gate policy refuses.

And the free speedup above is a seventh non-rule, for the same reason — running the halves concurrently under a freeze is permission, not an obligation, so there is nothing to violate. It is listed separately rather than numbered among the six.

⚠ Two of the six are now backlog rows rather than prose. The provenance and second-spelling rules describe conditions a script can check, and §11’s candidates became #250, #251 and #252 on 2026-10-07. Where a rule can be a script this project’s own instruction is to write the script and leave a pointer — so expect rules 4 and 6 to shrink to pointers if those rows land.

⭐ And there is now a seventh shape the table does not have, with better evidence than C1. Measured on 2026-10-07, after this page was written:

C4 · The unbound anchor cheap · exact · five instances in one session

A mutation entry names the text it severs. When an edit elsewhere changes that text, the entry stops applying — and the harness then refuses to report on any entry in that file rather than quietly report the rest.

Why it outranks C1: it happened five times in one session. Once from a correct refactor that extracted a shared computation — which cost 14m58s of CI to surface as NOT MEASURED — 175 of 176 on one shard — and four times in my own work, twice inside a commit whose own purpose was to fix the first instance. Every one was invisible to the suite, which stayed green.

The check: for every manifest, assert each edits find-string occurs exactly once in its target, before any tree is staged. Measured over the real repository: 1,414 anchors across 59 manifests, sub-second. It extends to the sibling failure for free — every expect must resolve to exactly one case name, which is how a case rename silently unbinds an entry’s attribution.

⚠ Not quoting a fixed duration on purpose. Drafts said 437 ms, a reviewer measured 63 ms, a later run 289 ms. “Sub-second” is the claim the evidence supports; a precise figure here would be noise dressed as evidence.

Three candidates, with costs — none adopted

C1 · The filing claim cheap · exact

A commit message claiming FILED must add at least one backlog row in the same commit.

Not a new guard. check-backlog-closure.py already reads merged commit subjects and compares them to rows — it catches "this commit closes #N but the row isn't ticked". The filing direction has no checker. Extending it keeps one mechanism per concern. Falsifier pair already measured: one commit claims FILED and adds 0 rows (must fire); another claims FILED and adds 1 (must not).

C2 · The unmutated change highest value

A diff that changes executable behaviour and adds no mutation entry covering it is invisible to a manifest-driven sweep.

This is the one that produced a High. The sweep is excellent at defending what someone enumerated and blind to what they just wrote — and a fix is by definition newly written. Cost: moderate; false positives expected on comments and pure refactors, so it likely warns rather than blocks.

C3 · The number beside the computation recommended AGAINST

Flag a stated percentage or total in prose that the code adjacent to it computes differently.

Listed for completeness and not recommended: it would be expected to false-fire more than it catches, and backlog #56's measured verdict is that a gate which is red without cause gets switched off. Recorded so the next person does not re-derive it as a good idea.

What the data says about "partial review" as a human checklist. It argues against one. Six of the nine review-only defects were in code written in the preceding hour, so the cheap intervention is not a longer checklist — it is a pass scoped to the fix diff alone, asking one question: can each changed line be reverted with the suite still green? That single question would have caught the most expensive defect of the session before a reviewer ran.

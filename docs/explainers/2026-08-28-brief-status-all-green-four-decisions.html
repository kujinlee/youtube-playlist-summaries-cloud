The one drift worth knowing about

Production is Fly release v10, deployed 2026-08-24 23:01Z, schema 0027. The roadmap claims release v10 at 2026-08-24 23:01Z. They match exactly — which matters because this specific check has failed twice before, once with production running eight days behind on a migration while every file on disk looked correct.

What did drift is documentation. docs/backlog.md row 54 still prescribes alter default privileges … revoke execute … from anon as its open fix. That mechanism was written as migration 0028, failed its own falsifier twice, and was reverted: stored default-ACL entries are additive to PostgreSQL’s built-in PUBLIC EXECUTE, so anon still reaches a new function through PUBLIC. It would have passed on production — prod’s default ACL happens to carry no PUBLIC entry — and been wrong everywhere else.

The refutation currently lives only in a commit body. The row does not carry it, and the row is what a future session reads. The same file also states this project’s live-schema self-test at 110 cases; running it returns 117.

The decision

Recommendation — one small docs PR

Correct backlog row 54 before anything else

Not to change its verdict — to remove a fix path that has been measured not to work. The PR would carry three things: the alter default privileges refutation, the stale 110→117 self-test count, and a note that the three handoff-XXXXXX.md files in $TMPDIR are pre-gate residue rather than a live failure.

The strongest argument against

Filing and amending backlog rows is explicitly your step, not mine — that boundary exists because I have previously filed things mid-investigation that turned out to be wrong. A “correction” PR touching row 54 while row 54 is itself one of the open decisions edges into pre-empting the judgment you have not yet made. The safest reading is that I should report the refutation and stop.

Why I still recommend it

The two things are separable, and the PR only touches one. Whether #54 is open, closed, or worth doing is a disposition — the PR leaves that untouched. That alter default privileges cannot remove PostgreSQL’s built-in PUBLIC EXECUTE is a measurement, and it is currently recorded nowhere a future session will look. The cost of waiting is concrete and already has a shape: someone picks up #54, writes migration 0028, and rediscovers the wall — after it passes on production, which is the failure mode that makes this expensive rather than merely wasteful.

If you would rather it wait, the alternative costs nothing today and the refutation stays in commit 7ce0fb7’s body, which is where I found it.

What I could not verify

  • Whether the 8 SECURITY DEFINER function bodies are actually correct. The measurement establishes that they reference auth.uid() — a proxy for enforcing ownership, not a proof. Those bodies were not read line by line, so what is known is that a defence is present, not that it works.
  • Whether the 92 SDD briefs are genuinely unique. Three were sampled and returned no matches in docs/reviews/. The other 89 were not checked.
  • Commit drift on the deployed release. The version matches the roadmap claim; whether release v10 was built from the tree its SHA names is a different question, and one this project has an open item for (backlog #53).
  • The integration and E2E suites were not run. They need a live stack and are not in CI. The 14 green ratchets are static and schema checks, not the test suites.

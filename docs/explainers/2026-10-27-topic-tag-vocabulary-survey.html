The idea: not one vocabulary but several axes, flattened into one

The repo's line items are tagged in eleven separate vocabularies, and only three have a closed list that anything enforces. But the deeper problem isn't synonyms. Single tag fields hold several kinds of thing at once: which part of the system, which goal, what kind of item, and sometimes its status. One example: the backlog's severity column has a value ✅ done on 117 of its 333 rows, so that column holds a status, not a severity.

So "common tag names" is feasible, but only if the vocabulary is split into facets, meaning separate axes such as area, goal, kind, severity and status, each with its own small closed list. One flat merged list would give the same words several meanings, and that, not spelling, is what makes today's tags hard to use. Backlog #90 (stories vs tasks, raised 2026-09-03) is the same finding seen from the backlog alone.

The comprehensibility suite is the clearest example. It has five names in four vocabularies: the backlog tag (comprehensibility) (38 rows), the anchors status-visibility / explanation-on-demand / feature-map, the feature nodes status-pages / feature-map / explainer-pages, "goal 1" in the roadmap, and "D2" for the deliverable. Nothing connects them except prose, and the explainer-pages feature claims no backlog tag at all.

The component clusters come from a keyword search, so they're a lower bound on synonyms, and a value can fall in two clusters (dashboard-text is both prose and page). The important number is 146 of 232 component values used in only one review record. A field where most values are used once records a description, not a category. That's fine for the ranker, which only compares within one subject, but those values can't be used to group findings across subjects.

OptionWhat it isCostWhat it breaks or misses

3 — Facetsseveral small closed axes: area (part of the system), goal (= anchor, already a registry), kind (defect / story / task, #90), severity, statusthe largest: a grammar change, plus a retagnothing is overloaded, so each page filters on the axis it needs. Asks one more decision per item, which is friction

Recommendation, and what would make it fail

  1. Treat the anchors registry as the goal facet and stop inventing goal-ish backlog tags. Anchors are the one vocabulary that's registered, guarded, and already read by both the goals and features pages. Let a backlog row name an anchor directly, which backlog #381's multi-tag parser can carry: (tooling) (status-visibility).
  2. Keep area as a small closed list (about 10 values after merging the spellings), registered and guarded. That's option 1, applied to area alone.
  3. Take status out of severity: ✅ becomes a status, so the backlog has two columns where it has one today. This is #90's split.
  4. Leave component: as free text, because the ranker needs exact descriptions within one subject. If it's ever needed across subjects, add an area beside it rather than forcing a closed list onto it.
  5. Glue: the next win is the theme switcher. ~49 inline copies should become the shared control, the way the tray already is. #376 (text-style on by default) is the same move for the second control.
It fails if after the retag, any one concept still appears under two values of the same facet (e.g. cloud/money and cloud / money both in use), or the features page's comprehensibility nodes still miss an open suite row that a keyword search finds, or the area guard has to be widened within a month of shipping. That last one would mean the closed list was guessed rather than derived.

The goal, in the owner's words

"Goal is to have tool for human (me) to understand what you (AI agent) [are doing]. I want to check progresses (goal-tree), pending works (backlogs?), work history (goal-tree?), topics (explainer-topic), goals (goals), features (features) etc. These various pages are interconnected but we haven't defined how they should be related and linked together. The tag vocabulary and tagging should serve the goal." — 2026-10-27 18:02

Restated as a design test: for every question the owner asks about the agent's work, there is exactly one page that answers it, and from any item on that page there is a link to the next thing the owner would want to see. Two pages that answer the same question are a consolidation candidate; a question with no page is a gap; an item with no onward link is a dead end.

A candidate relationship model (a hypothesis to accept or reject)

The pages show different entities, and the links between pages are the relationships between those entities. Naming the entities first makes the linking rule mechanical:

EntityIts identifier todayIts home pageIt should link to
Goal (deliverable D1/D2, programme)an anchor slug (docs/anchors.md)goalsits features, its open backlog rows, its in-flight threads
Featurea node slug (docs/features.md)featuresits goal (anchor), its backlog rows (by tag), its ADRs, specs, reviews
Backlog row (pending work)backlog #Nbacklogits feature (by tag), its goal (by anchor), the PR that closes it, the explainer about it
Thread / PR (work in progress and history)PR #N, branch namegoal tree / work linesthe backlog row it serves (tail (backlog #N)), its review rounds, its merge SHA
Change (what landed)a dashboard entry (date, PR)dashboardits PR, its backlog row
Topic (an explanation)an explainer slugexplainersthe row, PR, goal or feature it explains

Where tags come in. A tag is a join key between two entities. Under this model the vocabulary needs only as many facets as there are links: goal (anchor slugs, already registered), area/feature (the (…) tags, #381), kind (story / defect / task, #90), status (open / parked / needs-you / done, split out of severity). Every other identifier — backlog #N, PR #N, a SHA — is already unique and needs no vocabulary, only a rule that every page renders it as a link.

Spec ideas collected so far

  1. One question, one page. Every page states the single question it answers in its header; a second page answering the same question is merged or demoted to a view of the first.
  2. Every identifier is a link. backlog #N, PR #N, an anchor slug and a feature slug render as links to their home page wherever they appear, on every page, by one shared function (the way the chrome is shared today).
  3. A persistent progress page. The goal tree becomes a generated page (backlog #363) rather than chat output, so progress can be opened later and linked to.
  4. History in one place. Decide whether the dashboard or the work-lines page owns "what happened"; the other links to it.
  5. Explainers are attached, not dated. An explainer declares what it is about (a row, PR, goal or feature), and that item's page links back to it.
  6. A "needs me" view. One list of every open decision waiting on the owner, derived from the same sources the agent uses, so a decision cannot sit only in a chat message.
  7. Facets, not a flat list — this page's recommendation above, now with a purpose: each facet exists because a link needs it.

Open questions the spec must settle

  1. Is the goal tree a page of its own, or a view on the work-lines page?
  2. Do the dashboard and the work-lines page merge, or does each keep a distinct question?
  3. Does the backlog split into stories / defects / tasks (separate pages), or stay one table with a kind facet?
  4. Should explainers be attached to an item at creation (the skill asks), or discovered later (a search)?
  5. Is there one entry page — a home that answers "what is the agent doing right now" and links out to everything else?
It fails if after the design is built, a reader following one thread (goal → feature → backlog row → PR → explainer) hits a dead end, or two pages answer the same question differently.

1. The question

If several agents work in parallel and they must be serialised around a shared database, the development process slows down. Replicas and separate instances are standard practice for exactly this. So why not give each agent its own database?

The short answer is that it would work, and it would also be paying infrastructure rent to avoid fixing a handful of assertions. The isolation boundary you need is not where the cost is.

2. The finding: parallelism is bought at the assertions, not the database

In this repository, ten integration test files delete entire shared tables in beforeEach — unscoped by owner, playlist or video. That looks like sloppy hygiene. It is not. It is forced by the schema.

Measured — the shape of the ledger

                   Table "public.spend_ledger"
     Column     |  Type   | Nullable | Default
----------------+---------+----------+---------
 day            | date    | not null |
 reserved_cents | integer | not null | 0
 actual_cents   | integer | not null | 0

Indexes:
    "spend_ledger_pkey" PRIMARY KEY, btree (day)

The primary key is (day). One row per day, for the entire system — no owner, no tenant.

So a test that asserts anything absolute about today’s spend is asserting about a row everyone shares. To make that assertion true it must first guarantee nothing else is in the table — which means owning the whole database. The wipe is not carelessness; it is the logical consequence of the assertion style.

The suite says so itself, in reservation-release.test.ts:

// This suite asserts on the three GLOBAL, day-keyed tables — `spend_ledger` (one row
// per UTC day, no owner_id), `ledger_audit` (no owner_id), and `jobs` (claimed by
// video_id, not by owner) — so a fresh `newUser()` per test does NOT isolate it …

And the cure is in the same file, forty lines later. Two assertions on the append-only audit table are scoped to a per-run discriminator instead, and the comment states the result plainly:

// … are instead SCOPED to a per-run discriminator (a fresh uuid note, and the
// `'fail_job '||job_id` note the RPC writes) and are therefore indifferent to how
// many rows earlier runs left behind.

One file, both techniques, side by side. That is the whole lesson in miniature.

The rule

Assert on deltas and on rows you created — never on absolutes. Read the counter before and after; assert the difference. A test written that way does not care what else is in the database, so ten agents can run it at once against one stack. This costs nothing and scales without limit, which no infrastructure answer does.

3. The three layers, cheapest first

Spend at a layer only when the one below genuinely cannot carry the load.

  1. Most agent work needs no exclusive resource at all free

    Review, analysis and search are reads, and reads never interfere with reads. Both interference incidents measured in this project came from agents executing mutating harnesses, never from reading.

    So the first rule is simply: a reviewer reads. If it must execute something that writes, that is a deliberate act requiring its own sandbox — not the default posture of every agent you launch. This one rule covers most of a fleet.

  2. Make the tests isolation-tolerant bounded, one-off

    Delta assertions, plus per-run namespacing of every fixture. This project already defaults to the second half: seedPromotedVideo generates v-${randomUUID()}, and every test creates a fresh user and playlist.

    The global wipes are the exception, concentrated in the money-path files for the one structural reason above. That makes the work bounded and knowable — and it converts the whole suite from serial to parallel permanently, for every future agent, at no recurring cost.

  3. Only then buy environments recurring

    Some things genuinely cannot be shared. Here that set is small: the schema-mutation harnesses — already solved with per-PID scratch clones — and whatever still truly needs the global ledger.

    Keeping that set small is what keeps the bill small. Provision for the irreducible remainder, not for the whole suite.

Why a read replica specifically does not fit

Streaming replicas are read-only, and the interference here is writes — the suite creates auth users, playlists, jobs and videos. A replica cannot absorb them. Replicas are the right tool for scaling reads; they are the wrong tool for test isolation.

Why a second database is not enough either

A schema-only harness can be isolated with create database … template — measured at 3.45 s here. The integration suite cannot, because its state is not only in Postgres: it reaches the DB through the REST gateway and creates auth users. That state is owned by PostgREST and GoTrue.

So the isolation boundary has to be the whole stack, not the database — which is precisely why this option is the expensive one, and why it belongs last.

5. The part I would push back on

Serialisation slowing a shop is a real cost. But look at what is serialised here: the entire integration suite, six to seven minutes, because a handful of assertions demand exclusive ownership.

Turn those into delta assertions and the serialised remainder becomes small enough that the cost largely disappears — without buying anything. Provision environments first and the assertion style stays exactly as it is, so you keep paying for it, per agent, indefinitely.

The trap

Infrastructure makes a symptom disappear without the defect ever being named. The tests still cannot run beside each other; you have simply bought enough isolation that nobody notices. The bill scales with headcount; the fix would have been one-off.

6. For a team that is about to grow

A one-person shop can hold “don’t run those two things at once” in their head. That does not survive the second engineer, and it certainly does not survive agents launched in parallel, which is the case where nobody is holding it in their head.

Establishing this early is much cheaper than retrofitting it, for a specific reason: test isolation is a property of how assertions are written, so every test written before the discipline exists is a test that has to be revisited. The cost of the retrofit grows with the size of the suite, while the cost of the discipline stays flat.

Concretely, three things worth fixing in place before a team forms:

  • Write the rule down where the decision is made, not where the code lives. In this repo the “don’t run these concurrently” rule currently exists only as a comment inside one shell script — so it protects only people who happen to read that script.
  • Make reads the default posture for agents. Executing a mutating harness should be an explicit, sandboxed choice.
  • Treat a global singleton in the schema as a test-parallelism decision, because that is what it becomes. A day-keyed ledger with no tenant column is a legitimate product design here — it caps operator-wide spend — but it silently sets the isolation boundary for every test that touches it.

Recommendation

Target the global wipes, not the database count. The next step is a bounded read across those ten files producing a specific list of assertions that demand exclusive ownership. It needs no spec and no spend, and it is the input that every infrastructure option would require anyway.

You asked

“So full sweep for every commit? I thought sweep is for PR but if it happens every commit, sweep is real drag.”

You are right about the drag, and the chart overstates how often CI pays it

CI does not sweep per commit. The verify job runs per push, so a push carrying five commits sweeps once, not five times. Measured on CI run 35889056587, that step took 8m12s inside a 10m22s job — 79% of the whole gate.

The per-commit column above is me, locally, not CI. I re-ran the sweep after each fold because each fold changed mutation entries, and a sweep verdict only covers the tree it read. That is a choice about how carefully to land a branch that edits the mutation harness itself — not a policy, and not something you pay for on ordinary work.

The drag is already filed as your own backlog row #173, from this exact observation. Its measurement: three of the five PRs merged on 2026-09-22/23 changed no code at all, and when no scripts/** file changed the sweep mutates unchanged code against unchanged suites — it can only reproduce the previous result. The fix is a step-level if:, never a workflow paths: filter, because a filter means the check never reports and a required check that never reports leaves a PR pending forever.

⚠ One caveat worth carrying: round 3 found that the only cheap check which could have caught a broken manifest did not exist — everything else read temp fixtures. Two new cases now read the real manifests in under a second. That matters because of #173: skipping the sweep is sound only if something cheap still notices a manifest that cannot load.

You asked

“‘step level if’ can be a way to know how much the new change can affect. Is this a way to find a blast radius? If we have a reliable way to find blast radius, we just need to sweep within the blast radius, I feel. Or is it the other way around?”

They are two different things, and the cheap one works because it refuses to estimate a blast radius

The step-level if: is not a blast radius. It is one binary question — did any file under scripts/ or scripts/mutations/ change? — and the answer only ever turns the whole sweep on or off. It computes nothing about which mutations could be affected.

What makes it safe is that its rule is a tautology, not an estimate: if no code and no manifest changed, the sweep mutates unchanged code against unchanged suites, so it can only reproduce the previous result. There is nothing to be wrong about. That is why it is row #173 and why it goes first.

The blast-radius version is the other row, #174, and your instinct is right that it is the more powerful lever — but it is measured and the naive form is UNSOUND. A mutation's verdict can change if the mutated file's suite changes, and half the suites read the repository rather than just their own module (POPULATION lists, glob(), subprocess runs over other scripts). Those files carry 488 of 964 mutations — about 51% — so they must be swept whatever changed. Measured cost of each rule: changed ∪ importers → 31% but unsound; adding the repo-reading suites → 51% median for a one-file change. So the sound blast radius buys roughly 2×, not 3×.

⚠ And that 51% is an upper bound on the coupling, not a measurement of it — the detector flags any suite containing subprocess.run, which over-counts, since a suite shelling out to itself is not repo-coupled. Row #174's first task is to measure the real set, because if it is much smaller the payoff is much larger.

So: not the other way around — they compose. #173 removes the cost from PRs that provably cannot differ; #174 shrinks what remains. #173 is smaller, sound, and independent, which is why it is worth landing without waiting for the harder one.

⭐ One caution from this session, which is new evidence for #174. Scoping by changed files assumes a verdict depends only on the code. Today a sweep reported one unattributable kill that a direct reproduction in a staged tree could not reproduce — the same commit, the same mutation, a different answer, with heavy concurrent load the only difference. If a verdict can move without any file changing, a changed-file scope rests on an assumption I have now watched wobble once. That argues for keeping a periodic full sweep even after scoping lands — not for abandoning the idea.

⟳ The re-run settled it: LOAD, not a code defect. With nothing else competing, the same tree swept 981 mutations, 981 killed, 981 attributed, 0 survivors, rc=0. So the harness's capture of a suite's [FAIL] lines can be disturbed by concurrent work on the machine. ⛔ That is worse than a red, not better: an intermittent unattributable kill invites re-running until green, which is how a real one would eventually be waved through. It does not change the merge decision and it is not this branch's subject — it is a finding to file.

The reframe: speed came from less work per PR, not faster work

The switch from Opus 5 to Opus 5.5 felt like a big speed gain, and the transcripts agree it was, but not because the model writes faster. Per message, the two generate at the same rate. What fell is the number of messages it takes to land a PR.

This is an ASSOCIATION, not a measured cause. The two windows held different work: the Opus 5 window included long review episodes. The middle row is the cleanest comparison, because it's Opus 5.5 before the 10-25 merge-when-ready rule and the 10-26 local-sweep change, but it covers only 2 days and 8 PRs. What is solid: per-message speed did not change (97 vs 99 tokens/s), so whatever gain there was came from doing less per PR.

Why this matters for monitoring: the lever is work per unit: how many messages, rounds and gate runs a PR needs. Raw speed is a constant we don't control. A tripwire on "seconds per step" alone would miss the biggest effect on this page.

measured how: model_speed.py over every *.jsonl in the project's transcript directory. For each main-thread assistant message with ≥200 output tokens, it takes the gap from the preceding user or tool-result entry, keeps gaps between 0 and 600 s, and reads usage.output_tokens. ⚠ It uses the first entry per message id, so a streamed message may be timed at its first block, not its last.

Slowdowns that crept in before

Each one arrived as a reasonable change, cost time for days or weeks, and was caught by a person noticing, never by a machine.

  • The full sweep on a local run. A local --mutate . co-scoped every manifest. Co-scoping an unchanged 183-entry manifest cost 4 hours (memory: scoped mutation run). Fix: backlog #208 made a local run partial and refusing past 10 minutes (ba4d2c28, 10-26), and kept the full sweep in CI shards.
  • One guard's suite × its mutations. check-main-drivable.py held 183 entries against a ~30 s self-test, about 87 of the ~90 minutes of PR #360's sweep (ci.yml's comment). Putting a main([...]) call inside a long self-test raised it from 50 s to 209 s, past the 120 s shard timeout (memory: main-drivable cost is per call site).
  • The ffmpeg install hang. 4 of 14 CI attempts hung on the apt install before backlog #358 cached the packages (PR #407). In the 20 CI failures since, none was the ffmpeg step (tonight's tooling audit).
  • Sweep on docs-only PRs. Unchanged code was re-mutated on every docs PR until the step-level skip (ee0e461b). Now a docs PR's CI is 6.5 min instead of 26.

Proposal: a tripwire so the next one is caught when it lands

A proposal, not built yet: filed as backlog #397 (2026-10-29), per the standing rule that a backlog row is filed without asking. Its first slice is the CI log. Whether it ships, and in what order, is still yours to steer: ask on this section.

Every slowdown above was found by a person weeks after it landed. The pattern that would have caught each one: record the cost of every unit on every merge, and compare this week with last.

  1. CI per-job durations, per merged PR, appended to a log. On merge (the hook that already rebuilds every page), read gh run view --json jobs for the PR's final run and append one row per job: PR, job, minutes, and whether it was docs-only. Every number in §1 came from this call, so it is known to work.
  2. An elapsed_s field in every codex-review.py verdict. Today the verdict records model, head and outcome, but not how long the review took, so the costliest instrument in a round is invisible.
  3. A timing wrapper for local gates: one line per gate run (gate, seconds, load average) in a git-ignored log. It would have caught check-selftest-counts at 351 s, and it records contention as a column instead of hiding it.
  4. A budget per CI job: warn, not block, when a job's weekly p50 rises more than 25% over the previous week's. Warn-only follows this repo's measured rule that a blocking gate on a soft signal gets switched off (backlog #56).
  5. Work per PR, from the transcripts: messages and output tokens per merged PR, weekly. This is the metric that moved most across the model switch, and only the transcripts hold it.

All five feed one page section like the baseline above, regenerated on merge, so a reader sees this week against last without asking.

Where we're blind today

  • Codex review duration is not recorded. The verdict json has no elapsed field, so the cost of a review half can only be guessed from commit times.
  • No per-step local timing log. Every local number on this page was taken by hand tonight.
  • Agent CPU contention is not measured. Tonight's local timings were taken at load 18; how much of the 351 s is contention is unknown.
  • No queue time. The gap between the slowest shard (~19.5 min) and the run's wall-clock (26.1 min) is unexplained.

1. What "closure" means here, and how it was computed

A component's closure is everything a stranger must also have installed for it to work:

  • every script it executes or imports;
  • every file its Markdown tells the agent to read or run (e.g. a skill's ../shared/explainer-delivery.md, which in turn names scripts/explainer-serve.py);
  • everything those, in turn, reach.

It was computed with the repository's own edge finders in scripts/check-shipping-sets.py: exec_edges for code, and read_tokens for Markdown, resolved relative to the file's own folder. It was run, not estimated. Closure cost is the sum of the inventory hours of every component in the closure.

Why closure beats per-component cost as the unit: a component is only usable once its whole closure is, so its own cost understates the real price. Two examples:

  • hook-regen-dashboard costs 0.5 h on its own, but its closure costs 16.25 h.
  • Paying for one component pays for part of every other closure it sits in. So the right queue question is: "what does the next wave ADD?"

Q (11-23 17:49): "the soft edges are required and you suggest 'soft edges are cut' — so, how is this achieved?"

Short answer: a cut removes no feature. Each edge is required by the closure check, not by the explain skill's job. The closure check follows every import and every file a script names. It cannot tell "I need this to work" from "I mention this so I can offer more if it is there". A soft edge is the second kind. A cut turns it from must be installed into used if installed, or it moves a small shared piece to a file both sides already load. The code stays. Only the dependency arrow changes.

Each cut, and why it is safe:

  • A — the Refresh route table. REGENERABLE (scripts/explainer-serve.py:223) is a five-entry dict: "if the reader presses Refresh on the dashboard, run gen-dashboard.py". An explain page has no Refresh button of that kind. It is composed once and served as is. So a user who installs only explain-topic never takes those routes. Today the server still names the five scripts, so the closure check makes them ship. After the cut, the server filters the table to scripts that exist on disk, and a press on a missing one answers "not installed" instead of crashing. In our repo all five exist, so nothing changes here.
  • B — one formula. brief-compose.py:606–616 loads all of gen-dashboard.py only to call contrast_ratio, the WCAG contrast formula, a few lines long. Move it into page_chrome.py, which both files already import. The formula still runs, and brief-compose no longer needs the dashboard.
  • C — the goal tree's NEEDS-YOU box. It reads the dashboard's open asks and the backlog's NEEDS-OWNER rows. If those files are absent, the box says "no dashboard installed" for that source instead of failing. With both installed, which is us, it is unchanged.
  • D — a self-test line. gen-features-page.py:704 checks only that the regen hook exists. That is a test about our setup, not something the page needs to render. The check becomes "if the hook is installed, it is wired correctly".

What a user loses: nothing they installed. They lose only the links into parts they did not install, and those come back when they install them (waves 2–6). What we lose: nothing. Every cut is a no-op when everything is present.

Why the page said "cut": the word is graph language, for removing an edge from the dependency graph. "Make optional" would have been clearer. ⚠ Argued, not built: I read each line cited above on origin/master today (A and B quoted, C and D from the inventory's citations), but none of the four cuts has been written or tested yet. That is why section 6 asks you to price them as wave 1's first calibration point.

Why this order:

  • Wave 1 pays for the shared base. Wave 1 buys the page machinery: compose, serve, the Ask tray and the page chrome. Every later page reuses it, so later waves are cheap (1.5–3.5 h each).
  • The order follows your own value ranking. Explain pages first, then backlog, features and the goal tree.
  • Auto-regen comes late. The hooks that rebuild pages on every edit (wave 6) are where the remaining coupling lives. A user gets all of waves 1–5 by running the generators by hand.
  • Treat waves 1–2 as calibration. All costs are argued. Measure what waves 1–2 actually take, then re-price the rest.

6. Decisions for you

Adopt the seven-wave queue (section 3) as the phase-1 order?

Recommend: yes. It puts your four named features first, at 13.25 h, and re-prices after waves 1–2.

Make soft-edge cuts A–D part of wave 1's work, before anything is published?

Recommend: yes. Without them, wave 1 is the whole stack (16.75 h, not 5.25). They are small and they are unpriced, so measure them as the first calibration point.

For a component whose public bar is within 1 h of its next-project bar, pay the public bar?

Recommend: yes. It applies to page-chrome, page-markup, fixture-git (0 h extra), the hook-regen-* hooks (0 h) and the explain-topic and explain-diff skills (0.5 h). Everything else ships labelled "works in your own repo, unsupported".

Goal tree (wave 4): ship it as-is with our coordination conventions documented, or ship it after making the ledger and GitHub parts optional?

Recommend: as-is, documented. A stranger who wants a goal tree is adopting a workflow, and making it optional is unpriced work.

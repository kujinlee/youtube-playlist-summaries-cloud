1. The one confusion, wearing ten costumes

The root cause in one sentence: the guard tried to work out what a YAML file means by looking at one line at a time, and in YAML a line's meaning is not on the line — it is in the lines above it.

So the guard was reading information that was not there, and filling the gap with a guess. The guess was "if it looks like a setting, it is a setting." That guess is wrong whenever a file quotes something that looks like a setting, which YAML files do constantly, because half of what they contain is shell scripts.

Here is the whole problem in six lines. Both sides are character-for-character the same text. The left side installs Python 3.12. The right side installs nothing at all — it writes those characters into a shell script:

Why it went wrong ten times rather than once: each fix taught the guard one more rule about context — where a step ends, which dashes start a new item, which steps: belongs to the job. Every one of those rules was correct. But there is no finite list of them. YAML's context rules are a language, and you cannot reach a language by adding special cases to a regular expression, because the next shape always walks around the last patch.

That is the difference between ten bugs and one bug found ten times. Nobody was careless. The approach could not get there.

For orientation: the guard is scripts/check-python-pin.py, and it answers does every CI job pin the Python version it runs on? That matters because the repo's forty guards all run under python3, so a runner-image bump could silently change every one of them at once. The code names its own root cause, in a comment written at the seventh occurrence:

# guard reads YAML by scanning lines, so anything SHAPED like a step is a step. Each repair has
# taught it one more thing that shape alone cannot tell it — where the step ENDS, which lines
# are CONTENT, which dashes are SIBLINGS, and now which list it is IN.

Say plainly why this case causes an error. What was the root cause?

The root cause: a regular expression can only see one line, and YAML meaning lives across lines. The guard needed information that a single line does not contain, so it guessed — and the guess was wrong whenever a workflow quoted text that looked like configuration.

Concretely, the error in this specific case. The guard looked for the text python-version: to decide "this job pins its Python". That text appears in two totally different situations. In the first, it sits inside the settings of a real setup-python step, and it genuinely installs an interpreter. In the second, it sits inside a run: block — which is just a shell script written into the file as data — and it installs nothing whatsoever. Both look identical to the guard, because the thing that separates them is not on that line. It is two lines higher up, where the block was opened.

So the guard reported a job as correctly pinned when that job had no Python setup at all. That is the error: not a crash, but a confident wrong answer in the dangerous direction — the guard exists to catch unpinned jobs, and it said the job was fine.

And the reason it recurred ten times: every fix taught it one more contextual rule, and each rule was right. But structure is exactly the information a line-by-line scan throws away, so there was always one more shape. The tenth defect was not a new mistake. It was the first one, wearing a different costume.

2. Ten defects, one root cause

Each repair moved a boundary. None changed the mechanism. That is the shape worth recognising — the fixes were individually correct and collectively a treadmill.

2–3a pin inside an unrelated action's with:same, narrower
4a uses: line inside a shell heredoca step existed that did not

10a job id literally named stepsthe job key was read as the step list
Two directions, and only one of them is loud. Defects 1, 4, 5, 7, 8 and 10 are false greens — the guard reports “pinned” over a job that is not. Defects 6 and 9 are misses — a real pin vanishes and the author is told to add a step they can already see, or to add the job to EXEMPT_JOBS. The miss direction is fail-closed and therefore safe-ish, but it has a nasty second-order effect: it routes an honest author toward a permanent exemption.

The guard's own docstring states the standard it kept failing:

and `verdict` returned 0. A guard that can be satisfied by a line of prose is worse than no
guard, because it reports the absence of the thing it was built to find.

3. Why “just parse it properly” is not available here

The obvious answer is to stop scanning lines and parse the YAML. Every defect above is a consequence of not having a parse tree. So why not?

Because of a circularity that is easy to miss and impossible to argue with once seen:

That is not a theoretical objection. It is grounded in four facts, all measured on master 5ffe6017:

$ python3 -c "import yaml"
ModuleNotFoundError: No module named 'yaml'

scripts importing a YAML parser: 0  (of 63 files)
no python dependency manifest in repo root      (no requirements.txt / pyproject.toml / setup.py / Pipfile)
pip install in either workflow: ci.yml:0  schema-gates.yml:0

So a real parse means this repository's first third-party runtime dependency, and actions/setup-python@v5 hands CI a clean interpreter, so an install step would be needed there too. A vendored subset parser dodges the dependency by being a hand-rolled parser again — larger, and with no upstream test suite.

One precise correction, because it cuts the other way. It is tempting to say “every guard here is stdlib-only”. That is false: 17 of the 63 scripts import local sibling modules (page_markup, coverage_verdict, m4_base_db, and three others). The true claim is narrower — no guard imports a third-party package. The imprecise version accidentally argues against the fix chosen below, because local-library imports are not an exception to house style here; they are the house style.

4. Three guards, three standards, one missing primitive

Here is the finding that turns this from a bug report into an architecture review. Three guards read workflow files as text. Each of them independently discovered it needed the same missing primitive — which lines of this file are structure? — and each solved it to a different standard, without any of them knowing the others existed.

GuardWhat it builtCostOn a shape it does not understand
check-python-pin.py a partial reader: comment masking, block-scalar masking, sibling-dash rules, job-key disambiguation 10 defects / 7 rounds fail-closed — except for §5, which is a false green
check-merge-ready.py a different reader, plus a soundness check 4 shapes / 3 rounds refuses — surfaces the line it could not account for
check-ratchet-contract.py nothing. ci.yml is read as flat text — fails OPEN

The middle row is the interesting one, because it reached the right conclusion first and wrote it down:

⭐ THE REAL LESSON, and why the fix is not a fifth regex: this is a hand-rolled YAML parser and
the project is stdlib-only, so `yaml` is unavailable. A hand-rolled parser CANNOT be made
correct. It CAN be made unable to be silently wrong — which is what the soundness check does.

scripts/check-merge-ready.py:130-132

The third guard fails open, and here is what that looks like

check-ratchet-contract.py has a rule called R3: does something actually execute this guard? It answers by scanning a blob of text that includes ci.yml. Run against four different blobs:

R3 SATISFIED  <- a YAML COMMENT describing a REMOVED step
R3 SATISFIED  <- text inside a `run: |` block scalar
R3 SATISFIED  <- a step disabled by `if: false`
R3 SATISFIED  <- a genuine step            (the control)

All four indistinguishable. The function's own docstring says the rule “must not be satisfiable by prose” and cites the finding that a documentation table row was once read as a caller. It excluded docs/ — and prose inside ci.yml satisfies it. The fix went to the directory that had failed, not to the class of thing that had failed.

5. The false green found by reviewing the review

This is the part that changed what gets built, and it was not in the first draft of the review. It was found while the review was being reviewed — and it is a live defect in shipped code on master.

The masking regex that decides where a block scalar begins:

_BLOCK_SCALAR = re.compile(r"^(\s*)[\w.\-]+:\s*[|>][-+0-9]*\s*(#.*)?$")

scripts/check-python-pin.py:298

[\w.\-]+ cannot span the space in - run:. So a step written in the dash shorthand — perfectly ordinary GitHub Actions — never has its body masked, and its content is read as structure.

Here is the minimal pair. Two fixtures identical in every character except where run: | sits, both run against the shipped guard on master 5ffe6017:

### the dash shorthand:   - run: |
jobs seen      : ['verify', 'schema-gates']
  verify         declared_pins -> ['3.12']
  schema-gates   declared_pins -> ['3.12']      <-- from HEREDOC TEXT
unpinned_jobs  : []
verdict        : rc=0
                 python pin OK — every job pins 3.12, and this interpreter is 3.12

### the same thing under a name:   - name: seed / run: |
  verify         declared_pins -> ['3.12']
  schema-gates   declared_pins -> []            <-- correctly sees nothing
verdict        : rc=1
                 FAILED — 1 job(s) pin no Python version:

In the first fixture, the schema-gates job has no setup-python step at all and runs on whatever interpreter the runner image happens to ship. The guard says python pin OK.

Why the obvious framing understates it

There is a second defence, pin_took_effect, built precisely to catch a pin that is present but ineffective. It checks provenance: did the running interpreter come from setup-python? You would expect it to catch this. It does not, and the reason is a seam nobody had looked at:

This is verbatim the defect the whole effort exists to end. The original finding (#137) was that ci.yml ran bare python3 45 times in the one required check. The shorthand hole restores exactly that state while printing python pin OK.

Two things make it worse than an ordinary missed shape:

The test suite appears to cover it and does not. There is a case asserting that a job holding only heredoc text reports as unpinned. It passes — but not because the mask worked. Its fixture contains no uses: actions/setup-python, so the function skips the step before the masking is ever load-bearing. Add the uses: line inside the same heredoc and the case inverts. A test can pass for a reason that has nothing to do with what it claims.

It is latent, and that is precisely why it is urgent. No current workflow uses the dash shorthand, so nothing is broken today latent. But the review's recommendation was to promote this reader — because it is the best-paid-for of the three — into the other guards. Shipping the fix as written would have propagated the false green into all of them. That reordered the work.

6. How it is solved — and what it deliberately does not fix

The decision: extract the reader into one shared library rather than parse or refuse. _structural() moves out of check-python-pin.py into an importable scripts/workflow_structure.py, and the fail-open sibling is wired to read ci.yml through it.

This exact move has already been made here once. scripts/coverage_verdict.py was extracted from check-plan-code.py, and its mutations moved with it — that manifest holds 6 entries and the ratchet declares 6. The reason recorded in the code is the same argument the review makes: “Keeping BOTH would be two mechanisms for one concern.” So the recommendation is not a proposal; it is a repeat of a move this repository has already made and pinned.

What the fix does not do, stated rather than implied

if: false survives it. Masking answers a structural question; whether a step executes is a semantic one. Measured:

                              before      after _structural
comment                       SATISFIED -> VIOLATION
block scalar (`- name:` form) SATISFIED -> VIOLATION
if: false                     SATISFIED -> SATISFIED     <-- unchanged
control (a genuine step)      SATISFIED -> SATISFIED     <-- correct

Sharper still: promoting a structure reader into R3 does not answer “does this guard execute?” — it answers “does this text survive content masking?” Those are different questions, and R3's name claims the first.

The reader still is not correct. A genuinely pinned job written as a flow mapping reads as unpinned:

with: {python-version: '3.12'}        # valid YAML, a real pin
declared_pins -> []
unpinned_jobs -> ['w.yml:verify']
verdict rc=2 -> CANNOT RUN — no `python-version:` was found in any workflow

Fail-closed, so not a false green — but the guard reports the absence of a thing that is present, and routes the author toward an exemption. That is #158.

And risk concentrates. One reader shared by two guards means a future defect in it is a defect in both at once. That is the price of putting the knowledge in one place, and it is the right trade here only because the alternative — three readers of three different qualities — is what this review found.

7. The problem underneath the problem

The review took four rounds. The three repair rounds each caught a defect in the repair before it — and all three were the same class.

RoundThe sentence it caughtWhose inference
r2 “no guard invocation sits inside a conditional step” — two do a reviewer's, propagated without being re-run
r3 “rejecting them would red-line two guards that genuinely run” — both have a second unconditional invocation, so the measured cost is 0 guards the author's own — inside the paragraph repairing r2's
r4 twelve mutation entries listed as #26–#37 — 0-based, so the ordinal reading moves the wrong anchor and drops a needed one the author's own, in the row an implementer would follow

Every one of them is a plausible inference written in the grammar of a measurement.

The obvious lesson is the wrong one. “Verify agent output” was already a written rule in this project, and it was quoted at the start of the task. Having the rule did not prevent any of the three. What produced them is structural: each sentence sat in a paragraph running correction → transcript → inference → recommendation with no seam, so the inference was invisible to its own author while being obvious to the next reader.

Note also what r3 observed about the arguments themselves: all three false claims were supporting figures invented for a conclusion that stood without them. The statically-false-versus-event-scoped distinction was correct on its merits; the “two red-lined guards” was decoration that happened to be false. An argument that suddenly needs a cost figure is worth a second look.

The symmetry

It is worth noticing that this page has described the same failure twice, at two levels:

In the YAMLIn the review prose
Two kinds of thingstructure vs contentmeasurement vs inference
Written inone indistinguishable character sequenceone indistinguishable paragraph
Consequencea scanner credits text as configurationa reader credits a guess as a fact
Fixmark which lines are structurelabel the measurement; separate the sentence

In both cases the repair is the same move: stop relying on the reader to tell two things apart, and mark them.

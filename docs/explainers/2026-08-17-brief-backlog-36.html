Why the fixes keep failing

The plan is a 3,905-line markdown document, 57% of it inside code fences — 1,581 lines of TypeScript across 26 test-shaped blocks. That code is never compiled, never run, never import-resolved. Each fix is hand-typed into prose, which is a fresh chance to mistype. Hence 60%.

The clinching exhibit: round 5’s Blocking was a class missing an interface member — a TS2420. The plan’s own rules require tsc --noEmit on every task. A whole round was spent on a defect the plan itself assigns to the compiler, possible only because the code lives in a file that isn’t a file.

Asked from this page — “what bug is this finding relevant in fixing?”

The encoder fixes backlog #36. The other twelve tasks fix a class that is filed as a bug nowhere — searching docs/backlog.md for unservable, hand-renamed or orphan-adopt returns only #17 (a different, real bug) and #36 itself. There is no recorded incident.

What the guard class actually is. A key Supabase Storage will happily store but the serve path will not serve: a slash (nested/evil.md), .., a control or bidi character, over 131 code points. The serve guard (assert-cloud-summary-md-key.ts:14) allows no slashes, so such a row 409s — the paid summary exists and cannot be displayed.

Where such a name could come from — and it is not the app. Measured: zero slugify outputs fail the predicate, across the whole code-point space. The only entry point is recoverOrphanedVideos (lib/pipeline.ts:129), which does fs.readdirSync(outputFolder) and adopts on-disk filenames verbatim. So it takes a human placing or renaming a file in their own vault, which sync then adopts.

Why this argues for the split rather than against it. That route is open on master today and the encoder neither opens nor widens it. Twelve tasks are currently gating a launch blocker in order to harden a path no user has walked. As its own backlog item it can be prioritised honestly against everything else; welded to #36 it can only be prioritised as “urgent”.

Two things to fold in either way — explained

These hold whichever way the decision goes. Neither is large; both are the kind of thing that is invisible until it costs something.

1 · Re-run the production gate when this merges

The claim. Shipping the encoder requires no migration — nothing already sitting in cloud storage has to be renamed. That is what makes this a cheap, forward-only change instead of a data-rewriting one.

Why it is true. The encoder only rewrites a name containing a character outside its safe set. Five such characters are ones Supabase Storage happily accepts: space, (, ), +, =. So the claim holds exactly when no existing object name uses one. It was checked against production on 14 August, read-only: 19 objects, zero affected, exit 0.

Why that is not enough. That is a fact about the bucket on that day, not a standing property — the spec itself says so. Every ingest since then has added objects nobody re-checked. If one carries a space or a bracket, the encoder computes a different physical key for an object that already exists, and the summary behind it becomes unreachable. Verified: no step in the plan re-runs the query — zero occurrences of psql, claude_ro or supabase db. (check-encoder-gate-sql.py compares the spec's SQL to the encoder; it never touches the bucket.)

The fix. Re-run that same read-only query as part of merging. One line. It turns “we checked once” into a gate that can still fail — which is the only kind worth having.

2 · Rescue one rule before it dies with the plan

The rule. Adopted mid-slice, after round 2, and stated at the top of the plan: every code snippet is either executed and verified, or it is the current code quoted verbatim plus a precise statement of the change. Nothing invented, nothing untested, no snippet that merely looks plausible.

Why it was worth adopting. Rounds 1 and 2 produced four invented identifiers — names that appeared in the plan and nowhere in the codebase. The rule is the method change that answered them, and the plan's 33 EXECUTED markers are what it looks like when followed.

Where it lives: nowhere durable. Checked all five process documents — dev-process.md, process-checklists.md, review-method.md, process-rationale.md, portable-practices.md. Zero hits in every one. It exists at line 24 of a plan document that is currently being proposed for the shelf.

Why that matters here specifically. This project has two deliverables — the product, and the reusable harness. This is harness material of the first order, produced by the most expensive slice yet, and it is one git rm away from being lost. Moving it costs a paragraph.

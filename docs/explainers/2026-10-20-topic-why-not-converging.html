1. The short answer

Three causes, and the third is the one that makes the other two unfixable by more reviewing.

  1. The defects are population choices — over which subjects? which rounds? which corpus? — and adversarial review asks “is this correct?”, which is a local question. A local instrument samples one population error per round. There were at least five.
  2. Several defects were claims rather than code — most of all “all seven triggers re-derived”, asserted twice and wrong both times. A table you fill in has no falsifier, so nothing fails when it is wrong.
  3. Admissibility and liveness are the same switch. Append-only, plus any unusable row making every trigger CANNOT RUN, means a tightening fix can take the whole instrument offline — so each fix creates a new way to be refused, which is what fix-induced counts measure.

And then the corpus run below found a fourth thing, which reframes all of it.

Two consequences follow, and they pull in opposite directions:

  • Non-convergence here is not exceptional. It is the ordinary state of this repository’s review process wherever the process can measure itself. Asking “why is this code not converging” has a partly uncomfortable answer: because almost nothing does, by this definition.
  • A condition that fires on two thirds of its population is a description, not a trigger. dev-process.md says thrashing → convene an architecture review. Of these 8 armed subjects, exactly 1 has an architecture review whose filename names it (architecture-review-2026-10-20-decision-route-escalation.md), out of 20 reviews on disk. inferred — the mapping is by filename, which is not authoritative; a review may cover a subject without naming it.
This does not mean the condition is wrong. It fires at rounds=2 on three subjects — the earliest it mathematically can — while the pre-scheme median is 4 rounds (baseline.json). So either thrashing genuinely is endemic, or the condition is tuned to fire before the process’s own median. This page cannot tell those apart, and that is a real open question rather than a conclusion I am withholding.

4. Cause 1 — the defects are population choices

A pure function has inputs you can enumerate. A world-reader has a population, and the population was wrong five separate times, each caught one round later by somebody else.

Every one of these is the same error: a number that is correct about one set presented as a number about a different set. The repository has a name for it and has measured it twelve times. It is not carelessness — 18% and 13.4% both describe something real. They just describe different things, and the design hung a rule on the wrong one.

And the 14 failures group into exactly two distinct causes, by their own message text:

[ 13]  ValueError: no ```yaml header block

What that one pass bought, against five rounds

  • It reproduced the whole population-error class in seconds, and showed the pinned baseline is already stale — 17 hours after being pinned.
  • It found the disposition='refuted' vocabulary gap, which cost r1 a whole finding (CH1) to discover.
  • It found the 80 subjects that parse to zero rounds — the silent case, where “no header anywhere” is indistinguishable from “a clean round” at the call site.
  • Two things five rounds never found: that t6 cannot see its own pinned counts move, and that thrashing arms on 67% of the readable corpus.
The thesis survives, and with a number attached. One read-only pass found every population defect the five rounds found plus two they did not. It cost minutes.
Where the thesis is INCOMPLETE, stated plainly. The corpus run would not have found the row-lifecycle Blocking, the t3 breakage, or the attempt-identity ambiguity — those are defects in a proposed design, which has no corpus to run against because it does not exist yet. Review found those, and only review could have. So the answer is not “review is the wrong instrument”; it is “review was being used for both jobs, and it is only good at one.”

6. Why review cannot find these

Adversarial review answers “is this correct?”. That question is answerable by reading the thing in front of you — which is why it converged on the pure core in one round. The function’s inputs are visible in its signature.

A population question is not answerable that way. “Is 18% the right readability figure?” cannot be settled by reading the sentence that contains it, or the function that produced it, or even the file it came from. It is settled by enumerating the set — and no amount of care while reading substitutes for that, which is why three different reviewers and the author all read past 18% and the fourth reader only caught it by computing 11 of 82.

So each round samples one population error, because a reviewer notices the one it happens to recompute. With five such errors present, you get five rounds — and the count does not fall, because the supply was never the thing the rounds were reducing.

The repository had already measured this exact shape and written it down: review is the wrong instrument for a SURFACE — 6 rounds ≈ 7 edge cases, one corpus run ≈ 5,287.

7. Cause 2 — claims that cannot fail

The single most repeated defect in this slice is not in the code. It is a sentence:

“All seven triggers, re-derived.”

Asserted in the design’s first version, which had missed t4. Asserted again in the rewrite, which had missed t3 — and that time the rewrite’s own fix caused the breakage. Moving outcomes onto observation rows left t3_routes_collapsed reading route off rows that no longer carry one:

attempted routes: ['accrete', 'redesign', 'split', 'defer', 'accrete']
t3 -> "all 5 scored rows took route None — the routes are not discriminating,
       so this is a conveyor wearing a decision's clothes"

A false FAIL over maximally varied routes. Both times what caught it was somebody constructing an input and running the function; both times what failed to catch it was everybody reading the table, including the person who wrote it.

The lesson is about the shape of the claim, not about diligence: a table you fill in has no falsifier. There is no observation that makes “all seven re-derived” go red, so it is not a check — it is a hope with a tick next to it. This is the same reason the first version’s self-imposed gate was worthless: it required “3 of 3 labelled subjects”, where one subject raises and the other two have unique winners that a tie-break cannot move. It could only ever pass.

8. Cause 3 — admissibility is liveness

This is the cause that makes the first two unfixable by more reviewing, and it has a clean demonstration. Three facts, each independently true and benign:

  1. the log is append-only, so a row cannot be corrected;
  2. validate_row refuses a row whose route is not the next rung;
  3. main() treats any unusable row as CANNOT RUN for every trigger.

Together they mean a tightening of (2) can silence the whole instrument via (3), permanently via (1). Here is that state, driven through the real main() four times — the only variable is which row gets written about this very design review:

statethe row writtenrcverdict
Anone — as committed1FAIL trigger 1 NOT FED
Bthe truth: redesign2CANNOT RUN — no trigger was evaluated
Cthe route the ladder prescribes: split2CANNOT RUN
Da dishonest accrete0all triggers quiet
The mechanism cannot be in a green state about its own design review by any honest row. The only green state is the dishonest one.

Note what makes this more than an irony. In state A the guard fired correctly — two review rounds had run and no decision was recorded, which is exactly what trigger 1 exists to catch. Trying to obey it produces states B and C. So the instrument is right, and obeying it is impossible, and the only way to a green tree is a false durable record. That is what “the fixes generate the next round’s defects” looks like from the inside: not carelessness, but a structure where every honest move is refused.

check-decision-scheme.py is therefore red on purpose right now, and left that way. Its own failure text is the instruction: “a failing trigger is not a bug to patch; it is the promise saying the scheme no longer earns its place.”

9. What this implies for the pending decision

The SPLIT-vs-DEFER choice is yours and I am not pre-empting it. But the corpus run puts a third option on the table that neither review proposed, and it is cheap:

optionwhat it buyswhat the evidence here says
SPLIT the confirmed-closed corrections land; the row model becomes its own subject the ladder’s own next rung, and the only route with positive evidence (relocation 5 → 0 → 0, n=1). ⚠ but most of the “stable half” is corrections to false statements, not working mechanism
DEFER stop, file it five rounds, zero measured benefit, and rounds-to-termination uncomputable because no unit has terminated
MEASURE FIRST not proposed by either review run the readers over the whole corpus before deciding anything about the design one pass already answered two questions five rounds could not. It is read-only, costs minutes, and it would tell you whether the mechanism has a design problem or a population problem — which is the thing nobody currently knows

The strongest single argument for MEASURE FIRST is section 2. If thrashing arms on 67% of the readable corpus, then the finding that armed this slice’s architecture review is not evidence about this mechanism at all — it is the base rate. Deciding SPLIT or DEFER on a signal that fires two thirds of the time is deciding on noise, and that is answerable in an afternoon.

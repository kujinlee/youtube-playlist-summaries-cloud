The product is a YouTube playlist summariser. None of this work was about summarising YouTube playlists. Every one of these PRs was about the machinery that checks the work — guards, review rounds, mutation testing, the rules governing how claims get made.

That is the frame. Read these PRs as product progress and they look like nine days of nothing. Read them as the verification system being tested against itself and they are something else entirely.

Theme 1 — documents that broke their own rules

Four PRs (#345, #346, #347, #348) concern one document, docs/development-velocity.md, and its migration. The pattern is almost comic and entirely serious.

#345 adopted a set of rules whose whole subject is do not state a number you did not measure. Review found three unmeasured numbers inside it. The clearest:

the only evidence offered for adopting the draft-PR practice was “it caught backlog #176 r2's Blocking on its first use.” False, and the document it names says so — review-identity-176-r2-claude.md:156-158 records verify pending.

The round did not just repair them. It improved the rule: rule 1 gained clause 1b, say what you counted, not just that you counted. A number carries its population or it is not a measurement.

#346 is the sharpest of the four. The paragraph introducing those rules opened with “Four rules came out of this” and closed four lines later with “five rules, not four”. The cause is the interesting part: an earlier round found the count stale and appended a correction rather than editing the wrong sentence — which is precisely what rule 2 forbids.

So the fix for rule 1b's count violated rule 2, inside the paragraph that introduces both.

The resolution is worth stealing: the counts were removed, not corrected. The outline now lists the rules — 1, 1b, 2, 3, 4 — with no total. A list cannot disagree with its own contents.

Theme 2 — green checks that meant nothing

Three PRs found a passing check that was accurate and worthless. This is the most transferable finding on the page.

#350 — a check that cannot see absence

A review document of 32,331 bytes was destroyed by a git reset --hard and merged away. The gate that exists to catch missing reviews returned rc=0, “0 silent gaps”, on both the branch and master.

Why: check-review-rounds.py asks whether a round has both halves. When every document of a round is gone, there is nothing to check — so it reports clean. The author then quoted that green tick as evidence the review was recorded.

The deeper error, and it generalises: after restoring, the check run was “are those 8 files back?” — a question that can only confirm what you just did, and can never report what your action removed.

#354 — a declaration nobody could see

Two gates each accept an escape token in the PR body: NO-ENTRY: and NO-REVIEW:. Replaying the real bodies of #351 and #352 found both declarations present and not granted — they had been wrapped in backticks, so they were never line-initial and no gate ever saw them. The review gate passed for an unrelated reason, so the declarations were inert and silent.

That state is now reported by name: INERT-OTHER. It exists because a falsifier was run against real data rather than imagined data.

#359 — a condition that fired into nothing

A PR was parked with an explicit unblock condition. The condition was met on 2026-09-15. Twelve days passed with no signal. It surfaced only because a human asked what was still open.

The condition had been recorded correctly — in a memory file, filed where nothing points at it.

Theme 4 — the repair that generated the defect

#360 is the largest of the seventeen and the only one whose finding is structural. Nine adversarial review rounds kept finding the same class of defect: a rule's result computed, then discarded at the point it is used, with every named test still passing and the guard printing OK over a real violation.

Rounds 5 through 9 each fixed their instance correctly. Each fix created the next one.

The part that makes it more than a bug

The fix was already in this repository, in one file, written before round 1 of the nine:

scripts/check-ci-watched.py:860

def main(argv: "list[str] | None" = None, stream=None) -> int:
    """...Extracting `payload_from` was only half the repair; the line that
    CALLS it was still unreachable, which is the same "unit coverage does not
    compose — mutate the CALL SITE" lesson this file already records, at the
    next layer out again."""

It is the only one of 36 guards built that way, and the only one this defect class has never touched. It reached zero siblings. Nine rounds re-derived fragments of a complete sentence sitting 900 lines away.

So the class regenerates at the rate at which a solved problem fails to travel between files.

That is why the PR's main artifact is ADR-0014 — an architecture decision record — rather than only a code change. A docstring is read by whoever opens that file; nothing carries it to a neighbour. The ADR creates a venue where such a decision can be decided rather than privately discovered.

What would make this “implemented”. D1 across the remaining two guards closes the three open Highs in this fold. D2 — once it admits argv-as-world — turns the other 28 from invisible into pinned debt that can be paid down one guard at a time. Until D2 exists, nothing stops guard 37 from being written the old way, and the review that found all this would have bought a fix for three files and no rule.

The honest risk. The architecture review staked a falsifiable prediction on exactly this: apply D1 and D2 to the three files, and the next instance of the class appears in one of the other 28 — because that is where the exposure is and nobody has looked there. That prediction is currently untested, because only one of the three files is done.

↩ Asked from this page: “I want more informative titles so I can grasp what is in there”

Agreed, and this is a fair hit on me rather than on the repo. The essayistic title states the finding and omits the scope — so it tells you what was learned and not what was touched. A reader scanning git log to answer “what changed?” gets nothing, which is the commonest reason to read a log at all.

The change, from the next title onward: put the concrete subject first, then the finding, separated by an em dash. The insight is kept — the complaint was never that it is there — but it stops being the only thing present.

What I wroteWhat it should have been
Nine rounds found the same defect, so the tenth asked why instead ADR-0014 + D1 on check-ratchet-contract.py — nine rounds, and each fix was generating the next instance
The CI budget was set before the guards that blow it existed verify timeout 15→30, backlog #217 — two subprocess-heavy guards add ~13 min to the sweep
The checkboxes were a claim; #360 merging made three of them false Reconcile roadmap + memory after #360 — three checkboxes went stale at merge
Two rows said LIVE about a branch that no longer exists Close backlog #201/#202, file #219 — the closure guard's token grammar is single-id only

Why it drifted this way, stated rather than excused. The house style across this repository's backlog rows, commit subjects and review documents is deliberately essayistic — a row is supposed to argue, because a row that merely labels gets skimmed and re-litigated. I carried that into titles, where it does not belong: a backlog row is read, a title is scanned. The same sentence cannot serve both, and when they conflict the scanner wins, because nobody reads a title on purpose.

What this does not change. The body still argues. Dropping the finding from the title would trade one failure for another — a log of fix guard and update docs tells you the scope and hides every reason, which is the shape this project's own commit messages exist to avoid.

A correction this page makes to its own source. #360's architecture review states that “all thirteen prior ADRs govern the product”. Checked one by one, that is slightly overstated: ADR-0010 — “A document declares the goal it belongs to; the index over documents is derived” — governs documentation structure, not the product. The defensible claim is narrower: ADR-0014 is the first about the verification stack (guards, ratchets, mutation testing). The review's conclusion is unaffected; its count is not exact.

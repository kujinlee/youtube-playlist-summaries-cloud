Where these came from

Release v8 shipped backlog #23 slice A — corrections in the cloud — on 2026‑08‑24 with twelve tasks, four green gates, five spec rounds, dual adversarial review and 25 of 25 mutations caught. The first time anyone actually pressed the button in production, it returned HTTP 500.

Fixing that (releases v9 and v10) took two code changes, and along the way the exercise turned up three further things. None of them is fixed. The question on this page is only whether each becomes a row in docs/backlog.md, and at what severity.

The one rule this page follows

Every claim carries its own verification status, inline, next to the claim. Not in a footnote, not in a trailing “limits” section. Finding 2 is exactly why: it read as solid, it was in my recommendation to you, and it dissolved the moment I opened the one file that consumes the field it was about. A page that presents an argued claim with the same confidence as a measured one is doing the opposite of its job.

Measured, not inferred

After the failed press against v8, read from production through the read-only claude_ro credential:

correction_spend — 0 rows.  ·  spend_ledger — still 2298¢. Both read after a Gemini call that completed and was billed.

For contrast, the press that later succeeded produced correction_spend = 1 row (calls=1, cents=1) and moved the ledger 2298¢ → 2299¢.

Why this is more than bookkeeping

record_correction_spend is not merely a log. It is the function that increments the per‑owner‑per‑day counter — the one migration 0026 sets to ceiling=12, N=8, i.e. 96¢ — and the write that moves the global spend_ledger that the 5000¢ daily cap watches. Both of them only ever count successes.

So a press that fails costs real money and moves neither number. And a correction can be made to fail on purpose: ask it to delete a section, and the structural validator refuses it every single time. That is a loop which spends without limit while every guardrail reads zero.

The shape you have already treated as a defect

This is backlog #129 again — the 20 × 25¢ POST that could reach a 500¢ cap. Same family: a bound that a caller can walk around because the counter is incremented on the wrong side of the risk.

Verification status of the sentence above

measured the unit cost (≈0.4¢ actual, recorded as 1¢), the empty correction_spend after a failure, and that a structural failure is reproducible.
argued, not executed that a loop would therefore spend unbounded. Nobody ran that loop against production, and this page will not claim otherwise.

Finding 2 — withdrawn, and why that matters

What I told you first, which was wrong

“The corrections text is stored before the correction is applied, so the row carries a correction the document does not have.”

The first half is true and the second half does not follow. Both fields exist, and they say different things:

FieldWhat it actually meansAfter the failed press
correctionsthe instruction the user typed “Fix 'Codeex' → 'Codex'…”
mdCorrectionsHashthe claim that this document carries them null

So nothing ever claimed the document had been corrected. The field that makes that claim stayed null, which is precisely correct.

The consumer that settles it

There is exactly one place that interprets the hash, and it does the right thing with it:

lib/cloud-sync/reconcile-class-a.ts:8unchanged context
8const current = (s: ClassASignals, cur: string): boolean => s.mdCorrectionsHash === cur;

Sync compares the stored hash against the hash of the current corrections text and sets needsRegen when they differ. After the failure it would have concluded: this document is corrections‑stale and needs regenerating. Which is true.

The ordering is fail-safe, not defective

Storing the instruction first means the user does not lose what they typed when the apply fails — the panel is prefilled next time. Stamping the hash only on success means no consumer is ever misled. Write the user's input early, write the system's claim late: that is the correct order, and reversing it would be the actual bug.

Why this belongs on the page rather than being quietly dropped

The finding was wrong in a way that looked exactly like the other two — same phrasing, same confidence, same author, delivered in the same list. Nothing about its presentation marked it as weaker. What separated it was one action: opening the file that consumes the field.

That is the argument for a distinct kind of document. An explainer about a change can put its caveats at the end, because the diff is the ground truth and it is right there. An explainer about findings cannot — each finding is an independent claim, so the verification status has to travel attached to each one or it protects nothing.

The neighbouring 413 case already does this properly — it maps to “This summary is too long to correct” with a machine-readable code. And StructuralValidationError carries a typed reason field (missing-frontmatter, section-title, section-timestamp…) that is ready to be mapped the same way. The mechanism exists; this path just does not use it.

Why 🟡 and not 🟠

Nothing is lost or corrupted, and after the v9 fence fix these responses are rare. But when it does happen, the user has been charged and is then told something they cannot act on. It is a real defect in a paid path, at low severity — not a cosmetic nit.

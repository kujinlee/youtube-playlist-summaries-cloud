1Background

The skippable version

The cloud app charges for generation. Opening a summary for the first time materialises a “magazine model” via a language model, and that costs money, recorded in a Postgres ledger. A browser test that clicks around the app can therefore spend, quietly, on every run.

The previous change (PR #96) built exactly such a test, and its header promised in capitals that no money was spent. That promise was false: the suite reserved 12¢ per run. The fix was to stop promising and start asserting — read the ledger before and after, fail if it moved.

This change is what happened when that assertion was reviewed by someone other than its author.

The narrow prerequisites

Two tables matter. spend_ledger holds a per-day running total; ledger_audit is an append-only log:

supabase/migrations/0020_reservation_release.sql:12unchanged
create table ledger_audit (
  id            bigint generated always as identity primary key,
  day           date        not null,
  kind          text        not null,   -- e.g. 'release_underflow'
  expected_amt  int         not null,
  note          text,
  at            timestamptz not null default now()
);
grant select, insert on ledger_audit to service_role;  -- the ONLY grant

generated always as identity plus no update or delete grant is the property this change leans on: max(id) can only ever go up.

Why that property matters

A sum can return to where it started. A reserve followed by a release nets to zero, and an assertion watching only the total sees nothing happen — while a paid call very much happened. A monotonic sequence cannot be walked back.

2Intuition — three ways a money guard can be absent

The guard shipped in PR #96 looked like this, and it is worth seeing before the objections, because each objection is about when it runs or what it compares — not about whether the comparison is written correctly.

tests/e2e/cloud-journey.spec.tsbefore
let ledgerAtStart = 0;
test.beforeAll(async () => { ledgerAtStart = await reservedCentsToday(); });

// …six rungs later, as the sixth test in a describe.serial block…
expect(await reservedCentsToday()).toBe(ledgerAtStart);

Absence 1 — the window started too late

beforeAll belongs to the cloud project, which Playwright runs only after the setup project has finished. Everything the setup did — creating a user, seeding a playlist, writing blobs — was already inside the baseline. The suite could not detect its own first act.

Absence 2 — the quantity could cancel

Summing reserved_cents + actual_cents answers “is the total the same?”, which is not the question. Reserve 12¢, release 12¢, and the total is unchanged while a language model was called and paid for.

Absence 3 — and this is the one worth the whole page

To prove the assertion could fail, I un-skipped a rung already known to spend. The ledger moved. The assertion never ran.

⚑ The shape

A guard that is skipped precisely when something has gone wrong is absent exactly when it is most needed. A failing run is the run where you most want to know whether money moved, and it was the only run where nobody checked.

Note how it was found. Not by review — the reviewer raised the other two absences and not this one. Not by the suite passing. It surfaced from attempting to demonstrate that the guard worked, which is a different activity from using it.

What it looks like now

tests/e2e/cloud-journey.spec.ts:161after
test.afterAll(async () => {                     // runs even when a rung failed
  const now = await readLedger();
  expect(now.auditMaxId).toBe(fx().ledgerBaseline.auditMaxId);   // cannot be netted
  expect(now.centsTotal).toBe(fx().ledgerBaseline.centsTotal); // weaker, secondary
});

And the baseline now comes from the setup, taken before it touches anything, carried in the fixture file rather than computed in a hook that runs too late.

Playwright lifecycle → the money guard
the finding		 Whether the assertion executes at all. Author: assumed a test in a serial block always runs. Playwright: describe.serial orders tests and aborts the remainder on the first failure — a documented feature, not a bug. The guard vanishes in exactly the runs that failed. Fixed by attaching it to afterAll, whose contract is "runs regardless". The boundary was between a test and its runner — the kind nobody thinks to inspect, because the runner is not code you wrote.
The setup project → the cloud project The ledger baseline, now carried in the fixture file. Cloud project: assumed its own beforeAll was "the start". Playwright: project dependencies run to completion first, so that hook fires after the setup already acted. Anything the setup spent was inside the baseline and undetectable. The setup now reads the witnesses as its first statement, before it creates a user or writes a blob.
The suite → ledger_audit
narrower than it sounds		 A read of max(id), treated as "did any money event occur?". Assertion: treats a stationary max as "nothing was paid for". Schema: writes rows for serve_settle and release_underflow — not for every reservation. A reserve that is later released normally writes no audit row and nets the cents to zero, so both assertions pass. Unreachable in this suite today (it never enqueues), but the guard's name is broader than its reach. Stated in §6 rather than left implied.
Test → the sign-out UI Two exact, scoped locators instead of a .catch() fallback chain. Old test: assumed a fallback selector was a safety net. The DOM: a fallback matches whatever else fits the pattern — any control matching /account|menu|sign/i that navigates. The rung could pass while sign-out was broken. A fallback locator converts "this element" into "something like this", which is a weaker assertion wearing the same syntax. It now also returns to a protected route: reaching /login proves a navigation, not an invalidated session.

4Decisions this change encodes

1 · A cost claim belongs in a hook, not a test

Decided: the money assertion runs in afterAll. Rejected: leaving it as a rung and relying on the suite passing — which is circular, since a failing suite is the case it exists for.

ADR CANDIDATE:

Hard to reverse (moving it back silently restores the hole), surprising without context (a hook is a strange home for the file's central claim, and it no longer shows as a named test), and a real trade-off (hook failures report less legibly than test failures). The general rule is the reusable part: an assertion about a side effect of the whole suite must be attached to something that runs when the suite fails.

2 · Watch an append-only sequence, not a balance

Decided: max(ledger_audit.id) is the primary witness; the cents total is kept as a secondary. Rejected: the sum alone, which cannot distinguish “nothing happened” from “something happened and was undone”.

3 · Spend money to prove a money guard fires

Decided: un-skip a known-spending rung twice and watch the ledger, at 12¢ a time. Rejected: reasoning that the assertion must work because the comparison looks right — which is precisely how the original false claim survived.

The general form: a guard nobody has watched fail is a guard nobody has tested. Where a mutation is cheap this is routine; here it had a price, and the price was worth paying once.

6Assumptions and limits

Verified by reading the code

  • ledger_audit.id is generated always as identity and only select, insert are granted — 0020_reservation_release.sql:12-22. Monotonicity is a schema property, not a convention.
  • actual_cents is never written — 0011_cost_guardrails.sql:15 says "inert in 1D; written by the deferred reconcile". The settle slice remains unbuilt, so the ledger over-counts by design.
  • The sign-out trigger's accessible name is the email — AccountMenu.tsx:56-65 — and the item is role="menuitem" inside role="menu".

Verified by running something

  • The guard fires on failure: mutation → rung 4 fails → afterAll reports Expected 304, Received 305.
  • Money really moved during that mutation: ledger_audit max id 303 → 304 → 305 across two proofs.
  • describe.serial does not share a page — measured directly by comparing the page fixture across two serial tests: SHARED_PAGE=false.
  • Clean suite: 6 passed, 2 skipped. tsc clean; 2703 unit / 267 suites green.
  • ledger_audit locally holds two kinds: serve_settle (278) and release_underflow (27).

Not verified

  • The guard's coverage is narrower than its name. A reservation that is later released normally writes no audit row and nets the cents to zero — so both assertions pass while a paid call occurred. Unreachable in this suite today because it never enqueues a job, but "moved no money" overstates what is checked. This was found while writing this explainer, by reading which kinds exist.
  • The reviewer's Mediums are unaddressed: the ingest rung does not assert exactly one POST was intercepted, nor that no real POST escaped, nor does it wait on the sidebar's refetch; "no reload" is not positively asserted; and every run accumulates users, playlists and blobs that are never cleaned up.
  • No second review round has run on these fixes. Every previous branch this week that fixed review findings had those fixes reviewed in turn, and in three of them the fix introduced the next defect.
  • The quote-stripping change to a shared jest loader is still only argued, not tested — no case covers a value that legitimately begins and ends with a quote.

04What the 09-27 page got right, and its one blind spot

Its promotion rule is the sharpest thing in it, and last night tested that too:

"A memory entry graduates to a hook when its trigger is exactly decidable from the text of a tool call. … Entries whose trigger needs judgement cannot be promoted. 'Measure the population the code actually sees' has no tool-call signature."

It named that exact memory as unpromotable — and that exact memory is the one that failed hardest, at the cost of a High. The prediction held in both directions: the promotable kind can be mechanised, and this one could not be, and it duly failed.

⭐ The blind spot: there is a third option the promotion rule does not consider

The rule offers two outcomes — promote to a hook, or leave as prose. But the wrapped-line miss was not a judgement failure. It was a tool failure: a line-based search cannot see a phrase split across lines, and no amount of remembering fixes that. The memory says "measure what the code actually sees"; the operator did measure, with an instrument that silently could not see.

So the third option is: replace the fallible instrument. That removes the need to remember anything, without the trigger ever being decidable from a tool call. It is filed as #258, and it is the one genuinely new idea on this page.

07The principle: a check that cannot report nothing

#258 is worth the page's last section because it generalises. The measurement, run against a file known to contain two copies of a phrase — one of them wrapped:

methodhitsverdict
line-based grep1the original trap
grep -z + ERE0silently worse — zero reads as clean
rg -U 'a\s+b'2correct
tr '\n' ' ' ∣ grep -o2correct; loses line numbers
Python re with \s+2correct; keeps line numbers

⚠ grep on this machine is ugrep 7.8.4 wearing the name, so GNU's documentation for -z — the textbook fix for precisely this problem — does not describe what runs. A recipe copied from the manual would have been believed.

⭐ The design rule, and why it is a tool rather than a one-liner

A search must be unable to report "nothing found" without first proving it can find something. Give it a control pattern known to hit; a run whose control misses is CANNOT RUN, never no matches. That is this repository's existing law — a check that cannot reach its subject is a failure, never a pass — applied to search, and it is exactly what a shell pipeline cannot have. Precedent exists: the $HOME-literal audit in check-plan-code.py is described there as a control-backed grep.

08The honest limit

Not everything can become a program, and claiming otherwise would repeat the error this page documents.

  • Two of the six new rules stayed prose — the freeze rule (declare a freeze point per PR) and the comment rule (no unpinned universals in comments). Both are judgement calls with no clean mechanical shape, and they are labelled as advice-with-a-price rather than gates.
  • Four of ten candidate levers deliberately became no rule at all — scope the round to the diff · push earlier · send the reviewer evidence instead of another round · pick the cheapest of four tree-identity answers. No state of the repository shows any of them broken. A rule with no falsifier is a decision wearing a checkbox, and writing four of those would have made the file longer and no more enforceable.

09The PDF's MCP proposal, assessed

The question arrived attached to Claude_Code_Memory_Retrieval_Layer.pdf (4 pages; found on the Desktop, not ~/explainers/ as the prompt gave it; text extracted with pypdf in a throwaway venv because no PDF extractor was installed here). Its second half proposes building a local MCP server — fastmcp + chromadb + sentence-transformers, a search_memory tool over ~/.claude/projects/*/memory/, registered via stdio.

Its first half is accurate about the native design and worth keeping: CLAUDE.md always loaded; MEMORY.md as a capped index of short pointers; detail files read only if relevant; grep/keyword lookup; and the instruction to "treat retrieved memories as hints, not authoritative truths".

So the fair verdict: the MCP route would add genuine reach — cross-project recall and no per-plan model call are both real advantages this repo does not have. But it would be a second mechanism for a concern that already has one, which is a shape this repository hunts with a dedicated script (check-vocabulary-collisions.py, 17 measured instances). And on the evidence of §3 it would improve the half that is already at 20/20 and leave the failing half untouched.

Everything above was written on 2026-10-07 and deleted the same morning, about nine minutes after it was composed. The incident is not an aside — it is the cleanest instance of the gap this page is about, because the enforced statement was correct, the prose statement was wrong, and the prose was the one obeyed.

Defect 1 — two documents disagree, and only one of them is read by a program

.claude/skills/shared/explainer-delivery.md states it three times: "It writes nothing inside the repository — page and fragment go to ~/explainers/", "Outside the repository, deliberately". .gitignore:143-145 states the opposite and is the one that is true:

docs/explainers/ is TRACKED: the authored topic/brief pages have no source in git — the HTML IS the artifact, so losing it loses the work.

78 files under docs/explainers/ are tracked today, so the repository had already decided. ⛔ And the contract's own justification inverts: §1 says the page goes outside the repo "so it outlives its session" — but outside the repo means untracked, and an untracked file outlives nothing. A tracked file survives an rm; this one did not. The mechanism defeats the purpose stated for it in the same sentence, and no program could notice, because a skill document is prose read by a model and .gitignore is a file read by git.

Defect 2 — the recovery searched a population the write was not in

The first attempt to recover the page scanned the transcripts for Write calls whose file_path matched the slug, found none, and concluded "I never held that page's content". That conclusion was false, and the reason is mechanical: a heredoc write is a Bash call, so its file_path is empty and the 27 KB of HTML sits in the command field.

This is the repository's most-repeated failure wearing new clothes: measure the population the code actually sees, eleven recorded instances. The content was one grep away for the twenty minutes it was believed gone, and the belief was stated as a measurement.

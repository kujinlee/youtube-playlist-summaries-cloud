What the coupling actually is

docs/superpowers/plans/2026-08-28-project-dashboard-plan.md does not describe the two dashboard scripts. It contains them, in tagged code blocks. The tool's own output:

  python fences: 13 (12 assembled, 1 illustrative)

  scripts/check-dashboard-entry.py  4 blocks assembled -> 46/46 passed · 5/5 cannot-run cases passed
  scripts/gen-dashboard.py          8 blocks assembled -> 103/103 passed

  subject: the plan's blocks, DIFFED against the delivered files:
    identical  scripts/check-dashboard-entry.py
    identical  scripts/gen-dashboard.py

  mutations declared and run: 43, caught 43

PR #174 adds a CI step that runs exactly that:

- name: the plan's code and the DELIVERED scripts are the same, its mutations are
        caught, and its evidence is fresh
  run: |
    python3 scripts/check-plan-code.py \
      docs/superpowers/plans/2026-08-28-project-dashboard-plan.md \
      --compare . --verify-evidence

--compare asserts the delivered files are byte-identical to the plan's blocks. --verify-evidence asserts the plan's pasted results block is exactly what the tool currently produces. So, from the moment this merges:

Fix a one-character bug in scripts/gen-dashboard.py → CI goes red until you make the identical edit inside a 3,170-line planning document and regenerate its evidence block with the right flags.

Scale: gen-dashboard.py is 1,057 lines and check-dashboard-entry.py is 344 — 1,401 lines of production code living, in duplicate, inside a planning document.

Why it exists — it is not gratuitous

The criterion this step enforces has been defeated twice already, and each version is recorded in the CI file's own comment:

VersionWhat it askedHow it was defeated
1 "their mutation checks were run" Satisfied by running them and ignoring the result. A checkbox with no observation that could fail it.
2 Read the result Round 4 found it still passed over a plan that had drifted from the code — without --compare the check never opened scripts/. A green verdict over the wrong subject.
3 current --compare . --verify-evidence Not yet defeated. Names its own falsifier: fails if either script is edited without the same edit landing in the plan.

The reasoning is sound and I am not proposing to undo it. The problem is not the step — it is that the step has no stated end.

What it costs

CLAUDE.md says "a restatement is a second copy that drifts." This step does not remove the duplication. It makes the drift loud. That is a genuine improvement — and a permanent tax that falls on whoever touches the code next, possibly months from now, with no context for why a routine bugfix turned CI red.

There is a second-order problem too. scripts/check-docs.py:46 reads:

FROZEN = ("docs/reviews/", "docs/superpowers/")

CI now hard-depends on the byte-accuracy of a tree the documentation checker is explicitly told to leave alone.

And there is no escape hatch. The tool's full flag set:

--self-test    --evidence    --verify-evidence    --compare DIR

No --allow-drift, no expiry, no bypass. The branch review's prediction follows directly:

the first maintainer to hit this will delete the step to get green — and delete the guarantee with it, silently, in a PR about something else.

Why "retirement condition" and not "keep or delete"

CLAUDE.md's rule for gates is that one must name the observation that would make it fail. This step does that well. The sibling question, never asked, is: what observation makes it no longer apply?

Right now nothing is written. So the honest description of the current state is not "we chose to keep it forever" — it is "nobody decided, and the default is forever." Those are different things, and only one of them is a decision.

That is why the ask is for a condition rather than a yes/no. A gate with no exit is not a gate; it is a tax nobody voted for.

The four options, with honest costs

OptionWhat it meansCost
A — leave it The default. No condition written; the step runs forever. Every future edit to either script pays a documentation tax to a document nobody reads. Highest risk of the silent-deletion outcome, because the person who hits it has no stated rationale to argue with.
B — retire on merge The check protected the review; once merged, code is truth and the plan is history. Delete the step in a follow-up. Loses the 43 mutations entirely. They are the only thing currently proving the guards still bind, and they found four real defects in this slice. Too blunt.
C — retire when the mutations move chosen The step retires when check-plan-code.py's manifest is reimplemented as a normal mutation test against the delivered scripts. Requires someone to do that work. Until then the tax continues — but it is now a known tax with a named exit, not an accident.
D — time-box it "Remove after 90 days." A calendar is not an observation. The guarantee expires whether or not anything replaced it — exactly the unfalsifiable shape this project keeps rooting out.

Recommendation — and why it is an upgrade, not a concession

Retire the byte-identity check when the mutation manifest moves out of the plan and into the test suite.

Written into the CI step's own comment, so the exit condition ships with the thing it governs.

The reason this is not a compromise is worth being precise about. Ask what --compare actually protects. It is not "the plan should be accurate" as a matter of tidiness. It is:

the mutation evidence must describe the code that ships.

That guarantee is valuable forever. But it is currently achieved by an awkward route: keep a document byte-identical to the source, so that mutations run against the document's copy also describe the real file.

The direct route is to run the mutations against the delivered files. Then:

  • the byte-identity requirement dissolves — there is no second copy to keep in step;
  • the guarantee gets stronger, because it is now about the real files rather than a copy that happens to match;
  • the plan reverts to what a Phase-2 artifact should be: a record of how the thing was built, free to go stale.

So the step currently bundles two things with very different lifespans — byte-identity with a planning document (valuable only while the plan is the artifact under review) and 43 mutations (valuable indefinitely). Option C separates them. You do not give the guarantee up; you get it by a better mechanism and drop the tax that came with the worse one.

What I would do if you agree

  1. Add the retirement sentence to the CI step's comment in .github/workflows/ci.yml.
  2. File the manifest-extraction as a backlog item, so the exit is tracked rather than remembered.

Both ride in PR #174 rather than a follow-up, so the condition ships with the coupling. If you would rather keep it unconditional, that is a legitimate answer — it just needs to be written down as a choice rather than left as a default.

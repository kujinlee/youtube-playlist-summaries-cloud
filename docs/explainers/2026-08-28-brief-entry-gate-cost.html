1. The number that changes the decision

I offered you “make it fire only on code changes.” I have now run that variant against real history, and it does not do what it sounds like it does.

Of the 13 merges dated today, the rule as written refuses 12. Narrowing it to code-only refuses 8.

You would be buying back 4 entries out of 13.

And the 4 it lets through are the dashboard spec, the dashboard plan, plan v2, and a backlog fix — the four changes that are hardest to reconstruct from a diff and therefore the ones a “what changed while I was away” page most needs. The narrowing exempts almost exactly the wrong set.

The reason is structural, not a coincidence, and it is section 3.

2. What the rule actually is

A gate here means a check that blocks a merge. This one lives in scripts/check-dashboard-entry.py and runs when a pull request opens. In plain terms:

If your branch changed any tracked file, it must also add a dated block to docs/dashboard-entries.md describing the change in plain words — or the pull request must say NO-ENTRY: <reason>.

Two kinds of file are exempt. That list is the entire dial you would be turning:

EXEMPT_DIRS  = ("docs/reviews/",)
EXEMPT_FILES = ("docs/dashboard-entries.md",)

Review documents are exempt because they are generated evidence, not a change to the project. The entry file itself is exempt so that a branch consisting only of an entry is not required to describe itself.

This is not something I invented while revising the plan. It is the approved specification, section 7, quoted exactly:

Through v4 the rank-1 mechanism was voluntary: an entry existed only if I
remembered, and I would skip it exactly when busy. docs/dev-process.md gives
the remedy: "Before adding a rule here, ask whether it can be a script."

Bind the entry to an artifact that already cannot be skipped. Every unit of
work in this repo produces exactly one: a pull request.

Source: docs/superpowers/specs/2026-08-28-project-dashboard-design.md §7, merged as c5fcb07. The section also states the cost in its own words — “an entry written to satisfy a gate can become a compliance artifact rather than a briefing” — and concludes it is smaller than having no entry at all.

3. Why it catches so much

My instinct — and I suspect yours — was that most of today’s merges were “just documentation”, so a code-only rule would quietly exempt them. That is false, and here is why.

Almost nothing in this repository is a pure documentation change. When a rule gets written down here, it usually gets a script to enforce it in the same branch. So the commit is labelled docs(...) and touches scripts/ anyway.

Every one of those still gets refused under a code-only rule. The narrowing only reaches the handful of merges that touched nothing but docs/ — and in this repo that means specs, plans and the backlog.

5. The escape hatch, and why “displayed” is the load-bearing word

Writing NO-ENTRY: fixed a typo in the pull request body satisfies the gate. So the real question was never “is 12 too many” — it is what stops that line becoming reflex.

The specification already answered it, and version 1 of the plan quietly dropped the answer. Section 7, exactly:

Exemptions must be explicit and visible: a branch may declare
NO-ENTRY: <reason> in its body, which the check accepts and the
dashboard DISPLAYS, so a skipped entry is a recorded decision
rather than a silence.

Plan v1 built the accepting half and nothing that displayed it. Both reviewers caught it independently. The Claude half spelled out why it matters more than it looks:

  • the exemption is one line, written by the same agent that would have written the entry;
  • nothing displayed it, so nothing counted it;
  • nobody could ever see “eleven of the last twelve branches skipped their entry”;
  • and the page’s own “a day with commits but no entry” alarm could not tell a skipped day from an ordinary one.

Plan v2 builds the display. A section titled “Branches that skipped their entry” reads merged pull request bodies and lists each exemption with its reason and number. If it cannot read them it says so, rather than showing an empty list — because “none” and “could not check” must not look alike.

That turns the reflex self-limiting: three “no entry — typo fix” rows in a week is something you would see and object to.

6. Two things I got wrong when I told you this

Both are small, and this project has a rule about exactly this shape of error, so they belong on the page rather than in a footnote.

I saidActually
“all eleven merges from yesterday”They are from today — 2026-08-28, between 03:52 and 19:25. I resumed at 19:07 and treated the earlier ones as prior.
“eleven”12 of 13 now. The reviewers measured 11 of 11, correctly, at 18:20. Two more merges have landed since — including my own plan-v2 commit at 19:25.

The count moved by two in under an hour. That is the repo’s own rule — a count in prose is a claim about a moving number — catching the person who wrote it down this morning. The rule’s advice is to name the command instead of the number:

git log --first-parent --since="2026-08-28 00:00" --until="2026-08-29 00:00"

Nothing about the decision changes. The ratio is the same and the four exempted merges are the same.

Recommendation — keep it as specified (option A)

Not because 12 of 13 is comfortable, but because the alternative buys back four entries and they are the four worth writing. The spec, the plan and the backlog fix are precisely what someone returning after a week cannot reconstruct from a diff.

The thing that actually protects you is the display, which v1 omitted and v2 builds. With it, a habit of skipping is visible on the page within a week and you can overrule it then, with real data instead of a prediction.

If you disagree, the change is trivial and reversible — one string in the exempt list, in either direction, at any point. Nothing about this decision is expensive to undo.

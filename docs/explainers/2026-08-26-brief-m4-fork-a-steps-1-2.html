Fork (a), steps 1 and 2

step 1  The assertion suite runs, and catches round 7's Blocking

The first @RE-RUNNABLE marker went on the block that proves anon cannot TRUNCATE the paid manifest — a bypass that fires neither row-level security nor row triggers. Measured three ways:

correct schema                      assertion exit 0   GREEN

That third line is the point of fork (a). The fingerprint stays blind to TRUNCATE on purpose, because the assertion covers it — rather than growing the fingerprint a fifth time.

step 2  Argument defaults enter the function digest

record_artifact takes seven defaulted parameters. Changing one of them — p_md_hash text default null to default 'r7-default' — moved nothing the gate could see, while every caller that omits that argument then writes a different value. One term fixes it, in the payload rather than the symbol, so the manifest key stays stable.

I reproduced the exact defect I was fixing

Round 7's finding was "a written exclusion reason is false." My replacement reason said identity arguments render "types only". Measured on a two-argument probe:

identity: a integer, b text
full    : a integer, b text DEFAULT 'x'::text

They render names and types; what they omit is defaults. Both statements sound true and are about the same object, and only a measurement separates them. Corrected in all three places before the commit — but it is evidence for Phase 6 #2's thesis, not against it: a mechanism whose correctness rests on prose being true keeps producing false prose.

And a false green, caught in the same run

The new mutation reported ✓ on its first execution without running its own check. Its narrowness probe concatenated two "char" columns without casts, died with operator is not unique, returned empty for both before and after — and empty equals empty, so the check passed. Casts added, plus a guard that fails closed on an empty probe. Without it the ✓ would have been unearned, which is worse than a ✗.

5 · A disagreement between layerscheckboxes vs git

The plan says nothing is done. Git says Task 3 shipped.

The M4 v2 plan has 10 tasks and 49 open steps, and zero are ticked. But Task 3 — "the gate that reads the deployed catalog" — demonstrably exists: check-live-schema.py passes 68 self-test cases, its manifest covers 161 objects, and 22 sabotages of a live database all go red against it.

This is the failure mode dev-process.md names directly: checkboxes are a claim; git is the truth. Nothing is wrong with the code — the bookkeeping simply never caught up while seven review rounds rewrote the task underneath it. I will reconcile it when fork (a) closes, because ticking boxes on a task the next two steps still modify would be recording a state that is about to move.

6 · The standing recommendationno answer needed — read if you want the reasoning

Finish fork (a), then round 8, then a PR

You decided fork (a) yesterday and nothing since has argued against it. Steps 3–6 are mechanical compared to what came before: three of them remove code.

The strongest argument against continuing

Phase 6 #2 asked it as its fifth question, and it has never been properly answered: seven rounds and roughly 3,400 lines of gate code and reviews, for a migration that does not exist and a schema that has never run in production. A reasonable person could say the instrument has become the project, and that writing 0027 first — then verifying whatever it actually does — would have cost a fraction of this.

My answer, and I want to be honest that it is only partly satisfying. The disproportion is real and I would not defend how we got here. But two of the findings this instrument produced were not instrument defects at all — they were defects in the schema M4 is about to ship. Round 6 found that workspaces, the tenancy root, had grants and no revoke, so M4 would have shipped anon INSERT, UPDATE and DELETE on it in production. Round 7 found service_role holds INSERT on video_artifacts but cannot use it. Neither was reachable by reading the spec; both came out of executing it.

So the cost was not spent purely on the instrument. It was spent finding out that the schema was wrong in ways nobody had noticed in eighteen prior rounds of reviewing it as text. That is also the argument for fork (a): keep the executing, drop the fingerprinting.

What would change my mind

If steps 3–6 turn up a third round of instrument-only findings — defects in the gate rather than in the schema — then the instrument has stopped paying for itself and M4 should go straight to writing 0027 with the assertions as its only guard. That is a falsifier, not a feeling, and round 8 is where it gets tested.

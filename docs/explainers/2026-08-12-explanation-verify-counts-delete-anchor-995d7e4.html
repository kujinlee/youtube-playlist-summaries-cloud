1Background — two fields on one line

The skippable version

docs/roadmap-to-launch.md opens with a block titled ▶ NEXT ACTIONS, written to be the first thing a fresh session reads after a context reset. Its first bullet described the state of master. Two facts lived in that one sentence: which pull request had most recently landed, and how large the test suite was.

Both were typed by hand. Both drifted. This change treats them completely differently, and which one gets deleted is the whole point.

The narrow prerequisites

Before this change the line read, in full:

docs/roadmap-to-launch.md:1161before
- **`master` = the merge of PR #93**, clean, tsc clean, **2703 unit / 267 suites** green
  (unit count re-run 2026-08-12 on this branch; **491 integration** is the 2026-08-12
  figure and was NOT re-run — this branch touches no integration surface).

One check already policed the first half. scripts/check-roadmap-consistency.py extracted the number and compared it to the pull request in HEAD's squash-merge subject:

scripts/check-roadmap-consistency.py:107deleted by this change
def head_merged_pr() -> int | None:
    """The PR number in HEAD's squash-merge subject, e.g. `... (#81)`."""
    subject = subprocess.run(["git", "log", "-1", "--pretty=%s"], …).stdout.strip()
    m = re.search(r"\(#(\d+)\)\s*$", subject)
    return int(m.group(1)) if m else None
The limitation, stated in the script's own docstring

A squash-merge subject only exists once the merge has happened. On a feature branch there was nothing to compare, so the check printed a note and passed. It could report the mistake only on the first CI run on master — after the field was already wrong and CI was already red.

The second half — the counts — had no check at all. Nothing compared 2703 to anything.

2Intuition — derived vs. measured

The unlock is a single question asked of each field: could a machine compute this without being told?

✗ Derived → delete
master = the merge of PR #N
  • git log -1 already knows, always, for free
  • The written copy can only ever lag the truth
  • A check for it is a second mechanism guarding a cache nobody needed
✓ Measured → verify
2703 unit / 267 suites
  • Not derivable without running the suite
  • It is the claim a reader actually leans on
  • So it earns a real gate, wired to the real runner

Put that way the asymmetry is obvious, but it was not obvious in the moment, because both fields looked the same: a number in a sentence, occasionally wrong. The temptation was to build one mechanism to police both. That would have been the worse outcome, and §4 explains why.

Why the deleted field had to go rather than be enforced

Its failure history is short and unusually complete — four attempts, each a different shape:

v1
wrong valueHeld a raw commit SHA. False the moment it was written: the PR that edits the line is the PR whose merge moves master past whatever SHA it names.
#81
copy-forwardReplaced the SHA with a PR number and wrote #80 — the previous one. Wrong again on the very first merge.
#91
omissionDid not touch the line at all. It still said #90, and master CI went red on merge.
#93
omissionRepeated that omission within the hour — in the pull request that added the warning against it.
⚑ The shape that matters

Three of the four were omissions or copy-forwards, not wrong values. That distinction decides what kind of fix can work. A wrong value can be caught by comparing it to something. An omission cannot — there is nothing to compare, because nothing was written.

A required parameter refuses to be left out; the language will not let you call the function. A paragraph saying “remember to update this” defends nothing — as #93 demonstrated by being the paragraph and the violation, in the same commit.

What replaced it

For the surviving field, the gate reads the test runner's own output rather than anybody's memory. CI now writes jest's machine-readable results and hands them straight to the check:

The comparison, and the reason a failed run cannot be allowed to supply numbers:

scripts/check-test-counts.py:83new
def actual_counts(results: object) -> tuple[int, int]:
    if not isinstance(results, dict):
        raise CannotRun("… did not contain a JSON object. Treat as NOT RUN.")
    if results.get("success") is not True:                # checked FIRST, deliberately
        raise CannotRun(
            "… reports a run that did not succeed, so its counts describe a "
            "failed suite. Fix the suite first. Treat this check as NOT RUN.")
    for key in ("numTotalTests", "numTotalTestSuites"):
        if not isinstance(results.get(key), int):
            raise CannotRun(f"… no integer `{key}`. Treat as NOT RUN.")
    return results["numTotalTests"], results["numTotalTestSuites"]
Proven by making it fail, not by watching it pass

The roadmap was drifted back to the 2690 it genuinely carried that morning, against a real run:

✗ the roadmap claims 2,690 unit tests; the suite ran 2,703

CI workflow → check-test-counts.py jest-results.json, produced one step earlier. CI: assumes the flags it passes keep producing that file at that path. Script: assumes nothing — it verifies presence, JSON validity, the success flag and both integer fields before reading either. Every violation exits 1 saying treat as NOT RUN. This is the asymmetry the whole design turns on: the producer may change, so the consumer refuses to infer a pass from an absence.

A future gate that omits the word is invisible to the contract and may quietly ship an except: return 0. What is lost: nothing detects a roadmap that claims a stale PR number — but the field it read no longer exists, so there is no claim to be stale.

4Decisions this change encodes

1 · Delete derived state rather than build a mechanism to police it

Decided: the PR anchor is removed, along with its regex, its two functions and its four self-test cases. Rejected: moving the existing check earlier so it could run at pull-request time — technically easy, since GitHub supplies the number to the job.

The rejection has two independent reasons, and either alone would be sufficient. First, the field was derived: git log -1 answers the question correctly, forever, at no cost. Second — and this is the sharper one — enforcing it would have been a green tick over the wrong subject. The PR number is the label; the counts beside it are the payload. A gate certifying #94 while the counts silently said 2690 would have made the whole line look maintained, which is worse than an obviously stale line.

ADR CANDIDATE:

Hard to reverse in practice (restoring the field means restoring the habit, and the habit is what failed four times), surprising without context (deleting a check reads as lowering standards), and a genuine trade-off (a fresh session must now run one command instead of reading one line). The general rule — a hand-maintained cache of a computable value should be deleted, not guarded — is the reusable part, and it has now been applied twice in this file: the PR range went first, for the same reason.

2 · Keep the counts in prose at all

Decided: the numbers stay written down, and a gate keeps them honest. Rejected: deleting them too, by the same logic as the anchor.

The distinction: the anchor is derivable from the repository, but the counts require running the suite, which a reader orienting after a context reset will not do. They are stated so that reader knows the size of the safety net before deciding how much to trust it. Verification is what converts that from a decaying assertion into a live one.

3 · The integration figure is labelled, not verified

491 integration stays on the line, explicitly marked as a dated note the gate does not check, because integration needs a live Supabase stack and does not run in CI. Rejected: silently carrying it forward beside verified numbers, which would borrow their credibility.

4 · Opt the gate into the ratchet contract

Decided: the docstring says the word ratchet, so check-ratchet-contract.py discovers it (as the eighth) and will fail if it ever grows a --self-test-less successor or an exception handler that returns 0. Rejected: staying invisible on the grounds that it has no baseline and so is not a ratchet in the counting sense. Being unlisted is precisely how a check stops being maintained.

5Code map

  • The producer. .github/workflows/ci.yml — npm test gains --json --outputFile=jest-results.json. One flag change is what makes the counts measurable rather than asserted.
  • The gate. scripts/check-test-counts.py (new, 243 lines) — documented_counts parses the roadmap, actual_counts reads the runner, compare is the discriminator, and every path that cannot reach its subject raises CannotRun.
  • Two new CI steps immediately after the suite: the comparison, then the gate's own --self-test.
  • The deletion. scripts/check-roadmap-consistency.py loses STATE_PR_RE, head_merged_pr, check_pr_ref, the call site, the check_pr parameter and four self-test cases — replaced by a comment explaining why, since a silent removal reads as an oversight.
  • The prose. docs/roadmap-to-launch.md state block rewritten; docs/dev-process.md enforcement table gains a row; docs/process-checklists.md ratchet count corrected six → eight, with a note to read it from the script instead.
  • Housekeeping. .gitignore gains jest-results.json.

6Assumptions and limits

Verified by reading the code

  • The old check could not run pre-merge — its own docstring says so at check-roadmap-consistency.py:126.
  • package.json:9 defines "test": "jest", so npm test -- --json --outputFile=… passes straight through; jest.config.ts sets no reporters that would conflict.
  • Ratchet discovery is the literal word ratchet in a CI step name or docstring — check-ratchet-contract.py:46-48.
  • check-gate-falsifiability.py:57 restricts itself to the ## M1/## M2/## M3 sections, which is how it and the new gate read the same file without colliding.

Verified by running something

  • Full run as CI does it, then the gate: roadmap test counts match the suite: 2,703 unit / 267 suites, exit 0.
  • Roadmap drifted to 2690 → exit 1, naming the 13-test gap. Absent results file → exit 1, treat as NOT RUN.
  • 17 self-test cases pass. Five mutations: four killed; the fifth (path.exists()) survived as an equivalent mutant — removal still ends in CannotRun via the OSError catch — so the message it produces is now asserted and it dies.
  • check-ratchet-contract.py discovers eight ratchets, new gate included, violations still 4 at baseline 4.
  • All eight gates pass; CI green on the pull request.

Not verified

  • The gate has never run against a genuinely failing suite on GitHub's runner. The success is not True branch is covered by a self-test with a synthetic payload, not by a real red run — and if jest exits non-zero, CI stops at the test step and the gate never executes at all. That branch defends a local invocation, not a CI one.
  • CI step ordering is argued from the YAML, not observed. No run has yet exercised the case where --outputFile silently stops being written.
  • The three-parsers finding in §3 is an observation, not a measured defect. No reformatting has actually blinded a parser; the claim is that nothing would prevent it.
  • Two schema ratchets remain red — check-sentinel-meanings, check-guard-coverage — on master as well, both concerning the parked blob-addressing schema. Untouched here.
  • The 491 integration figure is unverified by construction and labelled as such on the line itself.

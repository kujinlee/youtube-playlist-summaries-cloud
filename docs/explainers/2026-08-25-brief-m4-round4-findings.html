B1 — There is no way back, and the command that looks like one is worse

B1FileBLOCKING

The claim. The plan's entire recovery argument is that 0027 applies as one transaction, so it cannot half-apply. That property is real. It covers the wrong failure — the case that matters is applies cleanly, then is found wrong, and the plan has no answer for it.

Verification, per sub-claim

  • Read The plan has no rollback section. I grepped rollback|down-migration|0028|recover|backup across the whole plan. Two hits, both a different sense of the word: :4 "outside a review's rollback" and :143 describing verify-schema.sh. Confirmed.
  • Read The schema has broken production twice before, by executing. Its own comment at 03_generations.sql:98-107 records it: [23502] null value in column "workspace_id" and a follow-on FK violation — "two independent breakages, one behind the other". Confirmed.
  • Measured "There is no down." FALSE — see below. This is the sub-claim that changed.
  • Argued A down-migration at M4 would be lossless. Every object M4 creates is derived from pre-existing state, and M4 ships no caller. Sound, but it is reasoning over the schema, not an executed rollback — and it expires at M5, the moment record_artifact gets a caller.
The correction makes this worse, not better. The reviewer wrote that supabase migration --help lists no down. On the same CLI version it named — 2.115.0 — I ran it: 
SUBCOMMANDS
  list  new  repair  squash  up  down  fetch
down exists. So does fetch. But down's own help says it "Resets applied migrations" — drop-and-recreate, in this CLI's vocabulary — and it accepts --linked, --db-url and --project-ref, so it can be aimed at production. Unverified deliberately: confirming what it does by running it is precisely the thing nobody should do to find out.

"There is no way back" makes someone hand-write 0028. "There's a down command" invites them to run it on prod and destroy the data it was meant to save.
Why Blocking, not High. Because the recovery path is absent, not merely weak, and the same schema has already taken production down twice on apply.
What would move it down to High: a written 0028 existing anywhere, even ungated. What would move it up: nothing — Blocking is the ceiling.
Ask: ship 0028_rollback_stable_blob_addressing.sql in the same PR, state the lossless property and its M5 expiry, and write down that supabase migration down is not the mechanism.

B2 · H1 · H2 — three gaps between the plan and the machine

B2FileBLOCKING

The claim. The milestone gate list contains no behavioural test suite, for a migration that attaches nine triggers to tables the app writes on every ingest.

Verification, per sub-claim

  • Read No test suite in the plan. The strings test:integration, test:e2e, integration, e2e and test suite return zero hits across the plan. Confirmed.
  • Read Nor in CI. .github/workflows/ci.yml:6-10 says so in its own words — integration "needs a live Supabase stack". Confirmed.
  • Read Nine triggers on live tables. I counted them: 15 triggers across the three promoted files, of which 9 target profiles/playlists/videos/jobs and 6 target new, empty tables. The plan's number is right and its layer split is right. Confirmed.
Why Blocking, not High. After 0027 there is no gate anywhere that would notice the triggers breaking an existing write path — and the schema's own comments record that exact failure happening twice. The six schema gates test the schema against itself; they never call an application RPC.
What would move it down: any executable check that exercises one real write path post-0027.

M2 — the one I am raising to High

M2File HIGH ↑ from Medium

The claim. After M4-β, deleting a playlist orphans the shared body row — including corrections a paid Gemini call produced — and re-adding the same video silently reattaches the old corrections.

The mechanism, every link read

-- videos is the CHILD of workspace_videos      03_generations.sql:96-97
alter table videos add constraint videos_workspace_video_fk
  foreign key (workspace_id, video_id) references workspace_videos (workspace_id, video_id);

-- workspace_videos cascades ONLY from workspaces        03_generations.sql:48
create table workspace_videos (
  workspace_id uuid not null references workspaces(id) on delete cascade,

-- deleting a playlist cascades to videos                0001_core_schema.sql:32
  foreign key (playlist_id, owner_id) references playlists(id, owner_id) on delete cascade,

-- and re-ingest KEEPS the orphan                        03_generations.sql:183-187
    insert into public.workspace_videos (workspace_id, video_id, corrections, corrections_hash)
    values (v_ws, new.video_id, nullif(new.data->>'corrections', ''), …)
    on conflict (workspace_id, video_id) do nothing;

Read Every link confirmed. Deleting a playlist removes the videos rows and leaves the workspace_videos rows standing, corrections and all. The derive trigger's do nothing then preserves the orphan on re-ingest.

Why I am moving this to High, against the reviewer's own Medium. The reviewer filed it as a behaviour change "with no caller". I checked whether a user can reach it deliberately, and they can — it is a button: 
components/cloud/DeletePlaylistDialog.tsx:16   import { deletePlaylist } from '@/lib/client/api'
app/api/playlists/[id]/route.ts:74            await bundle.metadataStore.deletePlaylist(principal, id)
This repo's own severity rule says a finding that corrupts durable data ranks at least as high as the worst thing a caller can reach on purpose. Delete a playlist, re-add the video — that is an ordinary Tuesday, and the content that comes back is content someone paid for.
Transitional or structural? Structural, but not M4's to re-open. The shared-body semantics belong to ADR-0006/0007, accepted at M3, and I am not re-litigating them. What is M4's is that this behaviour arrives with the migration, unmentioned, on the paid path, and no gate in the plan compares corrections values across a delete/re-add.
What would move it back down to Medium: a delete path that also clears the orphan, or evidence that the UI blocks re-adding a deleted video. What would move it to Blocking: the same sequence crossing a tenant boundary — it does not; workspace_id scopes it.

M1 · M3 · M4 — three checks that cannot do their job

M1FileMEDIUM

The claim. T4 gives 05_assert.sql a re-runnable home. Its backfill assertion compares two counts that diverge permanently after any ordinary deletion — the same orphan mechanism as M2 — so its first failure will be a false accusation that a correct backfill lost data.

Read The assertion's own precondition, three lines above it, is "the subject here is the migration's output, so nothing may have touched the table yet" (05_assert.sql:56-58). Confirmed — and it is the same FK asymmetry I read for M2, which is why these two are genuinely one root cause and I am comfortable saying so.

Why Medium. It misleads an operator; it does not corrupt anything. What would move it up: the false failure blocking a real deploy gate.
M3FileMEDIUM

The claim. The plan's strongest safety property — one file, one transaction — is a property of the apply command, and T6 never names it.

Read Confirmed. supabase migration up is documented as applying to the local database. The repo's production path is different: docs/deploy.md:30-31 prescribes supabase db push --dry-run then db push, and docs/roadmap-to-launch.md:162 records the last production apply as supabase db push --linked. T6 says only "the same migration against production".

A psql -f 0027.sql without --single-transaction, or a paste into the dashboard SQL editor, does not have the atomicity the whole plan leans on — and both are natural things to reach for on a hosted project at 2am.
Why Medium, not High. The correct command is written down elsewhere in the repo, so the knowledge exists; the plan just doesn't carry it. What would move it up: evidence that anyone has applied a migration here by another route.

Withdrawn — the sub-claim that did not survive

B1·cWithdrawn

What was claimed. "Measured: npx supabase migration --help lists exactly list, new, repair, squash, up. There is no down."

What re-running it showed. On the same CLI version the reviewer named, down and fetch both exist. The enumeration dropped two subcommands.

Why the parent finding still stands. down is not an inverse migration — its own help says it resets, and it takes --linked. So the conclusion ("no tooling path back; a reversal is a hand-written 0028") is unchanged, and the corrected version is strictly more dangerous than the original.

This is why the withdrawn section exists. A false premise that argues for the right conclusion is the most expensive kind to leave standing, because nobody re-examines a finding they already agree with. Had this page simply relayed B1, the plan would have gained a correct rollback task and kept a sentence that would eventually send someone looking for a command that does the opposite of what they want.

Recommendation

File all eight, at the severities in the table — with M2 raised to High and B1's down sentence corrected rather than repeated.

Then run Phase 6, don't write v5. The trigger fired on its own terms: four non-converging rounds. But the better argument is in the findings themselves — B1, B2 and H1 are not defects in the plan, they are things the plan does not contain: no recovery path, no behavioural gate, no acknowledgement of when its own first step actually executes. Those are shape, and per-round review is structurally blind to shape. A v5 would patch four holes and leave the process that produced four rounds of them intact.

The strongest argument against me. Phase 6 is expensive, and this plan has already consumed four rounds — a fifth pass under a different name may just be round 5 wearing a hat. M4 is also blocking the launch roadmap, and every process step spends days the milestone doesn't have.

My answer. Round 4 is the first round where the findings changed kind — rounds 1–3 were about the SQL, round 4 is about everything around it. That is not the same review running again; it is the review finally looking at the right object, which is exactly what Phase 6 is for. And the cost is bounded: Phase 6 reads CONTEXT.md and the ADRs and asks one question per composition defect. If it returns nothing, you have spent an afternoon and earned the right to ship v5 with confidence — which is not confidence you have today.

One thing to settle regardless of which you pick: the production ACL figure behind H2 is the reviewer's, not mine. If H2's severity is going to drive work, re-measure it first — it needs CLAUDE_RO_DATABASE_URL, which I don't have.

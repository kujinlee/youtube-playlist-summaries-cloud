1Background

The skippable version

The cloud app is one page. On the left, a narrow column lists every playlist you own; on the right sits whatever playlist you are currently looking at. You add one by pasting a YouTube URL into a modal, which starts an ingest: the server creates a playlist row and fans out one summarisation Job per video.

The complaint was simple. You ingest a playlist, it appears in the main pane, you click away to another playlist — and the one you just made is nowhere in the left-hand list. Pasting its URL still works, which is exactly what made it feel like lost data rather than a display bug.

The narrow prerequisites

Three facts about the code carry the whole story.

One — the list comes from a single unfiltered query. No pagination, no cache, no filter that could drop a row:

lib/storage/supabase/supabase-metadata-store.ts:241unchanged

  .order('created_at');

Two — the sidebar fetched exactly once. Its only load lived in an effect keyed on the signed-in user:

components/cloud/PlaylistSidebar.tsxbefore
useEffect(() => {
  backfillFiredRef.current = false;
  listPlaylists().then(/* … */);
  return () => { cancelled = true; };
}, [userId]);        // userId never changes during a session

Three — an ingest navigates, but does not remount. On success the parent pushes a new query string on the same route:

  setModalOpen(false);

    router.push(`/?playlist=${result.playlistId}`);  // same route

The three facts together

The query would always have returned the new playlist. The sidebar simply never asked again. Its state was whatever existed at sign-in, frozen for the life of the tab.

2Intuition — sibling, not parent

The unlock is structural, not about data. PlaylistSidebar and the content pane are siblings inside CloudAppBody. The sidebar is not on the path the URL changes, and it is not keyed by the playlist id — so when React reconciles after router.push, it sees the same component in the same position with the same props, and leaves it completely alone.

The decisive clue was already in the file. Deleting a playlist did refresh the list — handleDeleted calls listPlaylists() again. One mutation path had been wired for freshness and the other never had. The bug was not a missing capability; it was a missing wire.

Measured, not assumed

Against production release v6: three playlist rows, one owner, all three with non-null titles — and a fresh page load rendered all three. The filed report blamed the read path or a null-title filter. One query excluded both. Nothing was ever lost.

Where the complexity came from

Bumping a counter on ingest is three lines. Everything else in this diff exists because two loads can be in flight at once, and the second one is not always the one that finishes last. The + New playlist button renders while the list is still loading, so a user on a slow connection can start and finish an ingest before the sign-in fetch returns.

The obvious defence — a cancelled flag per effect — cannot work, because each flag only knows its own effect. Two effects cannot see each other. What is needed is one ordering shared by every load: the same guard PlaylistLibrary already applies to listVideos twelve lines away (CloudApp.tsx:147, reqSeq).

Why one counter is still not enough

“Newest started” and “newest applied” come apart exactly when a load fails:

So the final shape asks three questions at the moment of the write, not one:

components/cloud/PlaylistSidebar.tsx:107after
async function loadPlaylists(isCancelled = () => false) {
  const seq = ++startedSeqRef.current;
  const requestedFor = userId;                          // whose data did I ask for?
  try {
    const result = await listPlaylists();
    if (isCancelled()                                // does my caller still exist?
     || requestedFor !== currentUserIdRef.current       // same account?
     || seq <= appliedSeqRef.current) return null;      // something newer won?
    appliedSeqRef.current = seq;
    setPlaylists(result);
    if (errorSeqRef.current !== null && seq >= errorSeqRef.current) {
      errorSeqRef.current = null;
      setError(null);                                 // only a NEWER load retires a banner
    }
    return result;
  } catch (err) {
    if (isCancelled() || requestedFor !== currentUserIdRef.current
     || seq !== startedSeqRef.current) return null;
    errorSeqRef.current = seq;
    throw err;
  }
}

⚑ The finding worth remembering

That account guard was vacuous when first written. loadPlaylists is a closure recreated each render, so the refresh effect held the version from the render where userId === 'a'. It compared requestedFor against userId — and both read 'a' after a switch to 'b', because both came from the same stale closure. The condition could never be true.

Neither instrument caught it alone. The mutation run reported only “untested”; the guard itself read as “protected”. It took a test that genuinely reached the path. The fix is currentUserIdRef, reassigned every render, so one operand is actually live.

3Boundaries touched

BoundaryWhat crosses itWhat each side may assumeWhen that assumption is violated
CloudAppBody → PlaylistSidebar
the new refreshKey prop		 A number whose change is the signal. Its value and starting point carry no meaning. Parent: may pass any starting value, and must only ever change it forward. Sidebar: may assume the first render's value means “no refresh requested yet”. If the parent ever revisits the first-render value, that refresh is silently skipped. CloudApp.tsx:82 starts at 0 and only increments — but nothing enforces it. A monotonic counter is a contract, not a type.
Sidebar → GET /api/playlists A call with no owner argument; the owner is resolved server-side from the session cookie. Client: may assume the response is the full list for whoever the cookie names now — not whoever it named when the call was issued. Server: assumes nothing about the caller's UI state. This asymmetry is the entire reason for the account guard. The response cannot tell you which account it belongs to, so the client must remember what it asked for. Without that, one user's library renders under another's.
Sidebar → POST /api/playlists/backfill-titles
found by this explainer		 A repair call, newly reachable from the ingest path as well as sign-in. Route: its own comment states the sidebar bounds call frequency to once per session, calling that “the real backstop against repeated work” (route.ts:8-18). Sidebar: now also calls it once per ingest, bypassing that key deliberately. The route's stated backstop is no longer true. Each call iterates every null-title row with a YouTube fetch per row, so N ingests with an unfillable row cost O(N × rows). Bounded and cheap at real scale — but the comment describes a guarantee the caller stopped providing. Fixed separately in PR #92.
Sidebar state → its own render error and playlists, previously mutually exclusive. Render: may now assume both can be true at once, and must show both. If an error again suppresses the list, a failed post-ingest refresh shows a blank sidebar rather than a stale-but-useful one — trading a visible wrong answer for a visible absence, which reads as data loss.

4Decisions this change encodes

1 · The parent signals; the sidebar does not detect

Decided: refresh is an explicit input from whoever mutated the list. Rejected: having the sidebar notice on its own — polling, refetching on navigation, watching the URL. Nothing observable from inside the component distinguishes “a playlist was just created” from any other re-render, so detection would have to be a heuristic. A test pins this: no refetch on a timer within an hour, nor on plain navigation.

2 · Show stale data and say it is stale

The one place two review rounds genuinely disagreed. R2 argued a newer failed load must not discard an older successful one, or the sidebar strands on a spinner while holding good data. R3 argued that rendering that older result shows pre-ingest data with no sign anything went wrong — the quietly serves stale data failure this project treats as worst.

Both were right. They conflicted only because the render treated {!error && playlists && …} as the natural shape, making “report the failure” and “show the data” mutually exclusive. Decoupling them dissolves the disagreement instead of picking a winner.

ADR CANDIDATE:

Hard to reverse (a UI contract other panes may copy), surprising without context (the natural React idiom is the exclusive one), and a real trade-off (a stale list with a warning can still mislead a skimming user). Worth an ADR if this pattern spreads beyond the sidebar.

3 · Guard the request, not the effect

Decided: the account check lives on the request — compare the userId it was issued for against the one currently mounted. Rejected: adding cancellation to each effect. Round 3 fixed the mount effect that way, and round 4 found the identical defect intact in the refresh effect, whose cleanup is keyed on refreshKey and so never fires on a userId change — patching instances of a class as though they were the class.

Reachability, stated plainly

This scenario cannot occur in the app today. There is no router.refresh() anywhere; sign-out does router.replace('/login'), which unmounts CloudApp; sign-in returns through an OAuth callback — a full page load. So no mounted instance ever sees userId A→B. It is guarded and tested anyway: the distance to reachable is one account switcher, and the failure shows one user's library to another. The cost is a string compare.

4 · Repair a null title on the ingest path too

producer.ts:96-98 deliberately leaves the row untitled when the YouTube title fetch misses or throws, expecting “the backfill route retries later”. Before this change that row was invisible, so the gap never showed. Now it renders as Untitled playlist while the once-per-session sweep has already been spent.

Decided: the refresh path runs its own repair, ignoring the sessionStorage key. Rejected: reusing the session key (it would never fire) and doing nothing (a permanently untitled row for the session).

⚑ Found while writing this explainer — not by any review round

The backfill route's comment claims the sidebar bounds call frequency to once per session, calling that “the real backstop against repeated work”. That comment was made false by this change. Round 2 asked how many backfill calls a user could cause and answered correctly — but neither reviewer opened the route to notice the bound it documents had been the caller's to provide. Not a correctness defect; a stale claim about an invariant, which is the category this project treats most seriously. Corrected in PR #92.

5Code map

Ordered by flow, not by file.

  • The signal. CloudApp.tsx:82 holds sidebarRefreshKey; :87 bumps it in onIngestSuccess; :96 passes it down. This is the entire original fix.
  • The load helper. PlaylistSidebar.tsx:107 — loadPlaylists, the single funnel every load goes through, holding all three guards and the error tagging.
  • The counters. PlaylistSidebar.tsx:90-91 (startedSeqRef, appliedSeqRef), plus currentUserIdRef reassigned each render and errorSeqRef tagging the banner to its request.
  • The refresh effect. Keyed on [refreshKey], skipping while the value still equals the first render's. Carries the null-title repair and now reports its own failure rather than swallowing it.
  • The render. Banner moved above the list instead of replacing it; only the Loading… placeholder is still suppressed by an error, since a load that failed is not still in progress.
  • Tests. tests/components/cloud-app-ingest.test.tsx — eight #37 cases, every one asserting rendered output rather than a call count.

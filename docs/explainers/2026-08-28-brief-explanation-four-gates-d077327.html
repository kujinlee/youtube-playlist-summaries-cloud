1. Background

The skippable version

This repository runs a set of small Python gates — scripts that assert something about the system and exit non-zero when it is false. Some read files; a few read the live production database read-only. They exist because prose cannot refuse to be skipped, and a checkbox cannot notice that the world moved underneath it.

The narrow prerequisites

Three things must be true for the rest of this page to make sense.

  • One gate reads production. check-live-schema.py compares the deployed schema against a derived manifest of 161 objects. Derived matters: a human-written list silently stops matching.
  • That manifest names objects as kind:relation.name@digest. The digest covers the object's definition, so a changed constraint is a changed digest. The name half is what lets the gate say which relation an object sits on.
  • Postgres hands new objects out by default. A newly created function is executable by PUBLIC unless something revokes it — which is the whole subject of PR #165.

The highlighted line is the one PR #166 changed. Before it, that read idx:video_artifact_sources_gen_idx@… — index name only, no table.

Read the shape. table:, view: and type: attach to no parent, so they carry a bare name. fn: carries its signature — () is part of the identity, because an added argument is a different function. Everything else is relation.name: the object and the thing it sits on.

Now the digest, demonstrated rather than asserted. For a constraint it is literally md5(pg_get_constraintdef(oid)). Run against the live database:

-- the real constraint, read from the catalog just nowdefinition     : CHECK ((produced_at IS NOT NULL))manifest line  : con:video_generations.gen_complete_has_produced_at@e365b815…committed file : con:video_generations.gen_complete_has_produced_at@e365b815…   ← identical-- now weaken the guard, which is what an attacker or a careless migration doesdefinition     : CHECK (true)digest becomes : con:video_generations.gen_complete_has_produced_at@96b77c4d…

Same name, different digest. That is the entire mechanism: a gate comparing only names would see a constraint that still exists and pass. Comparing name@digest catches a guard that was quietly turned into true — which is exactly the class of change nobody notices in review, because the object is still right there in the schema.

“Derived” is the load-bearing word. Nobody typed that list. It is produced by cloning the pre-M4 schema into a throwaway database, applying the migration, and taking after EXCEPT before over the whole catalog — so it cannot drift from what Postgres actually creates.

2a — Why the objects exist. They are M4, the stable blob addressing schema (ADR-0006/0007/0011). 2b — Why the manifest exists, which is the question §1 actually needed. The gate used to carry 29 hand-written objects — 18% of the schema: zero views, zero indexes, zero policies, zero constraints. It reported “M4 is PRESENT as expected”, exit 0 over a database with all seven of M4's own-table triggers dropped — every append-only and immutability guard gone. A gate asserting a claim four times wider than what it read. Deriving all 161 is what makes the claim and the reading the same size.

2. Intuition

The four changes look unrelated — a CSS rule, a skill, a CI script, a SQL join. They are one story, and the order is the story: each was surfaced by the previous one's verification step, not by looking for it.

And a bound that had been honestly written down got paid off #166
The live-schema gate's docstring recorded its own falsifier: create unique index rev_uq on video_artifacts (video_id) still passes. It does not any more.

The digest is byte-identical across the change — only the name half moved. A differing digest still means a differing index definition and nothing else.

↩ Asked from this page — how can the digest be the same?

Fair challenge, and I checked it against git rather than re-explaining. All 12 index digests are byte-identical before and after #166 — git show b2f298a:…manifest versus current master, diffed:

before  idx:video_artifacts_free_uq@9c27caa0409d50518001e868889cedc4after   idx:video_artifacts.video_artifacts_free_uq@9c27caa0409d50518001e868889cedc4

The reason: the name is concatenated OUTSIDE the hash. Read the SQL as two halves — everything before || '@' || is the label, and only what sits inside md5(…) is hashed:

'idx:' || t.relname || '.' || i.relname   ← the LABEL. #166 changed this.  || '@' ||md5(pg_get_indexdef(i.oid) || indisvalid || indisunique || …)  ← the DIGEST. Untouched.

⚠ And here is the subtlety that makes the question a good one. pg_get_indexdef() returns the whole statement, which does contain both names:

CREATE UNIQUE INDEX video_artifacts_free_uq ON public.video_artifacts  USING btree (workspace_id, video_id, slot) WHERE (generation_id IS NULL)

So the names are inside the hash — indirectly. The digest is unchanged not because names are excluded, but because #166 renamed nothing in the database. It changed how the catalog reports an index, never the index. Same object, same definition text, same md5.

The useful consequence: had I got it wrong and altered a real index, all 12 digests would have moved and gen-m4-manifest.py --check would have caught it. The digests staying still is itself evidence the change was cosmetic where it needed to be — a label-only edit that touched no schema.

↩ Asked from this page — does an unchanged digest mean i.oid is unchanged?

No — and the opposite is the whole design. The digest does not hash i.oid. It hashes pg_get_indexdef(i.oid) — the text that function returns. The oid is only the lookup key used to fetch the definition; it never enters the hash.

An oid is a per-database internal identifier. It is assigned when the object is created and means nothing outside that one database. Measured just now on the same index:

                    oid       digestLOCAL container :  1288483   9c27caa0409d50518001e868889cedc4PRODUCTION      :  18285     9c27caa0409d50518001e868889cedc4                   ^^^^^^^^  different object ids, IDENTICAL digest

That is not a curiosity — it is the property the gate depends on. check-live-schema.py compares a manifest generated in a throwaway database against production. Those two share no oids at all. If the oid were part of the identity, nothing would ever match and the gate could not exist.

So read the digest as answering exactly one question: is this object still DEFINED the way it was? It is deliberately silent about where the object lives, when it was created, and what internal id it was given — all things that legitimately differ between two databases holding the same schema.

What it therefore cannot tell you

A dropped-and-recreated index with an identical definition gets a new oid and the same digest — the gate sees no change, correctly, because none of what it guards changed. If you ever need to detect re-creation itself (for a rebuild, or to spot churn), the digest is the wrong instrument and you would have to record something else.

↩ Asked from this page — so the digest detects whether the definition text stayed the same?

Essentially yes — with two refinements, and the first is nicer than you would expect.

1 — It is not YOUR text. It is Postgres's normalized rendering.

-- migration source, 0027:449constraint gen_complete_has_produced_at check (produced_at is not null)-- what pg_get_constraintdef returns — the ACTUAL digest inputCHECK ((produced_at IS NOT NULL))

Lowercase became uppercase; single parens became doubled. pg_get_*def() reconstructs the statement from the parsed catalog, never from the file. So reformatting a migration, changing whitespace, or rewriting is not null in another case moves nothing. Only a change Postgres considers semantically different moves the digest — which is what makes the check usable rather than a constant source of false alarms.

2 — For indexes, definition text alone was not enough. Look at what is actually hashed:

md5( pg_get_indexdef(oid)     || indisvalid || indisready || indislive || indisunique     || indisprimary || indisexclusion || indimmediate || indnullsnotdistinct )

Eight boolean flags appended to the text. They are there because validity is runtime state, not part of the CREATE INDEX statement — an index marked invalid renders identically to a healthy one. Without the flags, an index silently switched off would carry an unchanged digest. (Argument from the code's own shape: if the text carried those states, appending them would be redundant.)

So the honest one-line version: the digest detects whether an object's meaning-bearing definition — plus the runtime state that definition does not capture — is still what it was.

Neither half was sufficient alone. Text alone misses a disabled index; flags alone miss a weakened CHECK. The composite exists because someone asked what would this miss? — the same question that produced everything else on this page.

Why the gap mattered

The gate's job is catching objects added to the 8 relations M4 owns. A unique constraint was caught, because con: carried its relation. A unique index — semantically almost the same thing, and equally able to start rejecting writes — was not. Two spellings of one idea, disagreeing.

4. Decisions this change encodes

ADR CANDIDATE: prevention and detection need not cover the same set

pg_default_acl carries two rows granting anon EXECUTE — one for postgres, one for supabase_admin. The migration role is a member of neither the second role nor superuser (measured), so that row is unreachable from here.

Decided: prevent what is inside our boundary, detect everything. Rejected: attempting to alter the platform's own role defaults — not ours, and the blast radius is not ours to reason about. Hard to reverse in the sense that the split has to be stated, or a reader concludes prevention covers the class.

ADR CANDIDATE: a fix to a blind spot ships with a guard against becoming blind again

#166 could be undone by reverting one SQL join — every index would silently stop being attributed while the gate still reported green. Decided: a relation-less idx: is now CANNOT RUN. Rejected: relying on the self-test alone, which would pass over a reverted catalog because it uses fixtures.

Decided, not ADR-worthy

#164 states its own weak justification. The no-guidance control passed, so the skill prevents no measured failure. It shipped for consistency and for a live session to answer questions, and says so in its body — rejected: implying a baseline justified it.

#165 encodes replace-vs-create semantics. CREATE OR REPLACE over an existing function preserves its ACL, so only a first creation needs a revoke. Without this the gate reports six false positives on a correct repo — and a gate red on day one is switched off on day two.

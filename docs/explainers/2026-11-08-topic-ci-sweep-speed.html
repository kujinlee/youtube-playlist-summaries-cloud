1. The one equation every fix attacks

A mutation entry says "break the guard this way, and its self-test must go red". The sweep applies each break and runs that guard's whole --self-test, in a fresh process. So:

total work   ≈  Σ over mutations run  ( self-test time of that mutation's guard )  +  N × floor
time to wait ≈  total work ÷ N shards   (+ the per-shard floor, which N does not divide)

Both factors kept growing: more mutations (every review round adds entries), and slower suites (a suite grows as its guard grows, and one expensive suite multiplies by every entry that targets it). Every fix since 10-24 pulls exactly one lever:

LeverWhat it shrinksFixes
1. Run fewerthe number of mutations a run executesPR #496 (diff-scoped PR sweep), PR #518, PR #526, PR #529 (batch CI)
2. Cheaper eachthe suite time per mutation — the cachingPR #449, PR #534, PR #537
3. Widerwall clock, by dividing among N shardsPR #394 (8→12), PR #445 (→24), PR #484 (→18), PR #533 (→24)
4. Budget rightfalse reds from a limit that did not fit the suitePR #538 (adaptive per-suite limit + shard time budget)

3. Lever 1 — run fewer mutations

  • PR #496 (backlog #330), 11-04 — a PR runs only the manifests its diff selects. The full sweep runs on master and on a schedule. An unreadable or unrecognised changed path selects more, never fewer — the old all-or-nothing skip had a total failure mode (backlog #330).
  • PR #518 (backlog #498) widened selection for correctness: a sibling loaded by filename now counts, so a dashboard-grammar change re-tests compaction-state.
  • PR #526 (backlog #533) — a pin bump no longer forces the full sweep: the counts moved to scripts/mutations/expected_mutations.py.
⚠ But scoping saves less than it sounds. measured PR #539's latest green CI: SELECTION — diff-scoped: 67 of 89 manifest(s) selected. Backlog #534 saw the same on PR #528 (66 of 88). Files like docs/backlog.md and docs/dashboard-entries.md are inputs to many whole-repo guards, so almost every PR touches them. And PR #538 changed ci.yml, so it ran SELECTION — full. Per-PR scoping mainly buys correctness (no all-or-nothing skip), not much time.

PR #529 (backlog #534), 11-07 — batch CI. The owner's design: each PR runs only its scoped sweep; scripts/batch-ci.py merges several READY PRs onto batch/<time> and runs one full sweep for all of them, before they merge. That is lever 1 applied across PRs instead of within one. observed No batch/* run appears among the 20 most recent CI runs, so as of this page it is built but has not carried a merge yet.

5. Is any verdict actually reused? And the trap

Short answer: no mutation verdict is reused today. Every cache above lives inside one process, and each mutant runs in its own fresh process with the mutated file already on disk. So the cache can never hand a mutant the unmutated answer — the gen-backlog-page.py comment says this exactly: "the cache lives for ONE process, and each mutant is its own process." What the caches reuse is work within one suite run, not a verdict.

  • The only verdict reuse that exists is batch CI's (§3): one full-sweep verdict covers every PR in the batch. check-merge-ready.py reports it as an info batch sweep line that never blocks a merge (advisory, backlog #534).
  • A cross-run verdict cache is an open idea, not built: backlog #560 — skip a mutant whose every input is unchanged since a green run, with inputs recorded by observing file opens, failing closed on anything untraceable.
  • And the owner already rejected one form of it. Backlog #534, 11-06: "skip a shard whose inputs are unchanged since a green run" was considered and rejected for PR CI — the safe key (the whole tree) saves nothing, and the useful key rests on a dependency model with holes, so "a skip on a stale key is a green nobody measured."
⚠ The trap — a cache can hide a mutant, and it did. measured, PR #537 round 5 CI's shard 20 reported a survivor: the check-usage-pace mutation "the blank-line skip is removed". The branch's lru_cache on meter_row made 4 MiB of identical blank lines cheap, so the 2 s timing case passed even with the skip deleted. On master, without the cache, the mutant takes 29.3 s. The fix (4935fa11) replaced timing with a spy that asserts only the one real row reaches the parse.

The lesson: a cache does not only risk a stale answer; it can remove the cost that a case was using as its signal. Any case that detects a mutant by "too slow" is a candidate to be blinded by the next memo.

The second hazard is stated in the code rather than hit: _memo_by_node keys on node identity, not content, so its docstring sets a precondition — "A TREE IS NEVER MODIFIED AFTER A MEMOISED HELPER HAS SEEN IT" (check-main-drivable.py:325). And backlog #560 notes that any cache shared across runs must key on the helper's own source, or a mutant reads the unmutated answer.

Why N alone cannot win (backlog #231, #401): each shard pays a fixed floor — checkout, setup, and a control and re-control run of its suites — that does not divide by N (~309 s measured on 10-30). Past 20 shards the jobs queue. Raising timeout-minutes instead would only hide a growing sweep. So N buys headroom while levers 1 and 2 do the real work.

7. Lever 4 — the 120 s limit that turned master red

Every mutant's suite used to run under one flat limit, SUITE_TIMEOUT = 120 (check-plan-code.py:110). As suites grew, one crossed it under a slow runner: measured master's push run on bd1284b4 (11-08 08:13) and the 14:21 schedule run both failed on the check-fixture-variation mutation "deadness is judged over every file rather than the one its exemption names…" with "the suite did NOT COMPLETE" — a CANNOT RUN, not a survivor. Nothing was wrong with the guard; the limit didn't fit the suite.

PR #538 (backlog #558), merged 11-08 as 4d7766f8:

suite_limit(control) = min(600, max(120, 20 × control's per-suite seconds))   # check-plan-code.py:1246

The limit now scales with the suite's own clean (unmutated) run, measured in the same shard. A real hang still dies at 600 s. The same PR gives each shard a total TIME BUDGET read from the job's own timeout-minutes via a YAML anchor, so a shard about to hit the job limit stops cleanly and names what it did not reach, instead of being killed silently. measured The first full master sweep under it (d7a15f82) is green, prints TIME BUDGET — 1680s … (SWEEP_TIMEOUT_MINUTES=30, event 'push'), and its slowest shard took 1,242 s.

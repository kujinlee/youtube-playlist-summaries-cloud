Restructure or tag? I recommend tags, with one change to "detect".

  • Tags, not a re-organisation. Splitting the 345 rows into separate tables would move every row, and rows are referred to by number (backlog #N) from thousands of places: PRs, review documents, memory, other rows. A kind tag (story, task or defect) is additive and reversible, and the multi-tag parser built this week (backlog #381) already reads several tags per row.
  • But relationships should be DECLARED, not detected. A tag says what a row is, not what it belongs to. Inferring "this task is part of that story" from wording is the mistake this whole session kept making: six subjects in two days failed by inferring a fact from free text that the text could defeat (the goal tree's first two review rounds failed exactly that way). The reliable form is an explicit link written on the row, such as part of: backlog #N or epic: <anchor>, read by the same one parser.
  • So the shape is: a kind tag on every row, plus an explicit parent link where one exists. Pages then derive the tree (initiative → epic → story → task) from those two fields and never guess.

⚠ Still unmeasured: how the 345 rows split by kind, and how many already name a parent. A first pass would classify them and show you the counts before anything is retagged.

1 · Background — what the suite promised

The skippable version

This project has two front ends sharing one codebase: a local single-user tool, and a hosted cloud app. The cloud app charges real money, because turning a YouTube video into a readable summary means calling Gemini, and Gemini bills per call.

In August a browser-level end-to-end test was added for the cloud app — a “journey” that signs a user in, lists their playlists, ingests a new one, opens a summary, downloads it, and signs out. The appeal of such a test is that it runs unattended, on every change, for free.

For free is the load-bearing word. A test that quietly spends six cents a run is a test nobody can afford to run on every commit, and worse, it is a test whose cost nobody notices until the bill arrives. So the suite carries a money guard: it reads the spend ledger before the run and again afterwards, and fails if anything moved.

The prerequisites for this change

Three pieces of the system matter here, and the project’s glossary already names all three precisely.

Definitions — from CONTEXT.md

Daily cap — the global (all-owners) dollar kill-switch per UTC day. “The hard money ceiling: once the day’s reserved+actual hits it, every enqueue is refused.”

Magazine model — the structured per-section {lead, bullets} representation the rendered HTML doc is built from, produced by a capped Gemini call. It is lazily materialized and version/drift-gated: regenerated on view whenever it is absent, unparseable, or drifted — defined in the glossary as “its sourceSections no longer match the MD’s section titles.”

Envelope — the stored JSON wrapper {sourceMd, generatedAt, sourceSections, model} whose model field carries the magazine model. Distinct from the model itself.

Hold onto that definition of drifted. The glossary wrote down the exact failure mode of this change a month before it happened.

The other prerequisite is a piece of Playwright’s architecture. A Playwright config declares projects, and a project may declare dependencies on another. Here the cloud project depends on a setup project that creates a fresh owner, seeds their data, signs in, and writes the session to disk.

2 · Intuition — two independent failures, stacked

It is tempting to describe this change as “fixing the money guard”. That undersells it, because there were two entirely separate defects sitting on top of one another, and each one hid the other.

Failure one: the guard kept standing in blind spots

A guard is only as good as the window it can observe. This one moved four times, and each position was blind to something the previous position had made visible. That is not incompetence; it is what happens when each fix is reviewed only against the defect it was written for.

Round 0
a 6th test() in the journey
Blind to: any failing rung. describe.serial aborts the remaining tests once one fails — so the money check was skipped precisely when a rung had spent.
Round 1
test.afterAll in the journey
Blind to: the setup project. The baseline was read in the cloud project’s beforeAll, which fires only after setup finished — so everything setup did was already inside the baseline.
Round 2
baseline in setup, assertion still in cloud
Blind to: a setup failure. Playwright does not schedule a project whose dependency failed, so a setup that spent money and then threw took the guard down with it — the exact window round 1 had moved the baseline to cover.
Round 3–5
globalSetup returning a teardown closure
Outside every project. Survives setup failure, an unscheduled project, --max-failures, -x, and SIGINT. Still cannot see: SIGKILL, a global timeout, a webServer that never starts, or UI/watch mode — and now says so.

The mechanism that makes the final position work is a small, slightly obscure Playwright affordance: a function returned from globalSetup is registered as the run’s teardown. Reading the runner source shows why it survives failures — the teardown task is queued the moment the setup task starts, before anything can go wrong.

Measured, not argued

A mutation made the setup project insert a ledger_audit row and then throw. Result: 1 failed, 7 did not run — the cloud project never scheduled, exactly as predicted — and the guard still fired with ledger_audit max(id) 306 → 307, exit 1. Under the round-1 code it would have been silently absent.

Failure two: the fixture the guard was protecting had never worked

Here is the part worth the reader’s attention, because it is the one no amount of reasoning about Playwright would have found.

The serve path renders a summary as a magazine-styled HTML document. To do that it needs a magazine model, and if one is not present and fresh, it reserves spend and calls Gemini. So the test setup pre-seeds an envelope, precisely so the serve path finds one and returns for free.

Freshness is decided by comparing the envelope’s stored sourceSections against the section titles the serve path derives from the markdown. And deriving those titles is not the identity function:

The circular part

The rung that would have exposed this — opening a video and asserting its rendered summary — was skipped. And the reason recorded in the skip comment was that each attempt to diagnose the regeneration cost 6–12¢ of real Gemini spend, with 24¢ already burned guessing.

So the bug funded its own concealment: it made the rung expensive, the expense justified the skip, and the skip removed the only thing that would have caught it. Meanwhile three comments in three files asserted the protection worked.

The old skip comment even contained the correct hypothesis — “most likely sourceSections not matching the titles its own parser derives” — and then declined to spend a minute confirming it, on the grounds that each attempt cost money. It was three lines in two files. A sibling fixture, share-route.test.ts, had been seeding ## 1. Intro against ['Intro'] correctly the whole time.

Outcome

With the seed corrected, rung 4 is un-skipped and passes with the ledger unmoved — 7 passed. The magazine render is now exercised in a browser on every run, for free, for the first time.

Failure three, which neither reviewer found

One more, discovered by hand while reading the guard rather than by any review round. The ledger read destructured data and ignored error:

An unreadable ledger returns zero for the baseline and zero for the final read. Two unread ledgers compare equal, so the guard reports “no money moved” having read nothing at all. This is the project’s own house rule — cannot run is a FAILURE, never a pass — violated inside the very mechanism written to enforce it.

Measured both ways

With the error check in place, a typo’d table name fails the run. With the check disabled, the same typo yields 6 passed — a completely green suite reading nothing.

Three consecutive rounds of decaying severity from one reviewer is not evidence that the artifact is converging. It is evidence that that reviewer is running out of altitude. The two halves drift in different directions: Codex toward comment precision inside the changed lines and library internals; Claude toward the fixture, the callers, and what the suite does not cover. The Blocking sat in a file Codex had read four times.

And the reviewer corrected itself

Round 5’s first High was that a change made in round 4 — pinning guardrail_config — was a money regression, and that its justification came from the same reviewer’s own round-4 Low, which was wrong. The claim was that a leftover tight cap would make a render rung “go green having proved nothing”. It does not: at_capacity returns 503 and the rung asserts 200 first, so it goes red, and free.

The pin converted a free red into a paid red — and raised the local stack’s daily kill-switch from its $5 default to $50, permanently, with nothing to restore it. A fixture widening a money control, inside the suite built because a fixture caused live Gemini calls.

4 · Decisions this change encodes

Decided: the money guard belongs outside the project graph

Rejected: keeping it as a hook inside the spec, which is the conventional place. The trade is that globalSetup is a less obvious home and its teardown semantics need a paragraph of explanation. Accepted because every in-project position has a window it cannot see, and the whole point of the guard is that it runs when things go wrong.

ADR candidate

ADR CANDIDATE: Run-level money guards for cost-bearing test suites. Hard to reverse (every future cloud suite inherits the placement), surprising without context (a hook in globalSetup is not where anyone looks for an assertion), and the result of a real trade-off (obviousness versus coverage). Four positions were tried; the reasoning is currently preserved only as a comment in tests/e2e/cloud-global.ts.

Decided: identity by construction, not by stamp

The fixture files live outside outputDir so Playwright’s wipe cannot take them — which is what made a stale baseline reachable. Rejected: adding a run-id and checking it. Chosen: delete both files at the start of every run, so a fixture can only exist if this run wrote it. There is no id to check because there is nothing stale to check against.

Open question — the reviewer argued back, and the argument is good

This decision is only true on the CLI. In UI and watch mode globalSetup runs once per session, so nothing is deleted between runs and the suite can pass against a previous session’s owner. The branch answered by narrowing the claim and declaring UI mode unsupported.

The counter-argument, filed as backlog #45(a): detection is the deliverable. A stamp is three lines, redundant on the CLI and the only signal on the path where deletion never happens — and “detect but not prevent” is the standing of every other guard in this suite, including the money guard itself. This one is genuinely undecided.

Decided: derive the fixture’s titles, do not type them

Correcting ['2. Encoder'] to ['Encoder'] fixed the instance and left the class: two literals in one file that must agree under a rule defined in a third, checked by nothing. The seed now runs the markdown through the real parser.

The trade, stated because it is real: the fixture can no longer catch a change in the parser. That is correct here — the fixture’s job is to be fresh, and the parser’s own contract is pinned by the unit suite. A tautological assertion is a defect; a tautological fixture is a fixture that cannot be wrong.

This follows the project’s own recorded rule: sort a check’s config by what happens when it goes stale — hardcode what announces its own wrongness, derive the rest. A stale sourceSections fails expensively and mutely: the rung says “text not visible”, the guard says “the ledger moved”, and neither says “the seed”.

Decided: at_capacity is the brake, not an obstacle

Briefly, a fix pinned guardrail_config to guarantee headroom. Reverted. When the cap is tight the serve returns 503 and the rung fails red and free; with headroom restored the same drift reaches the reserve and calls Gemini. The pin converted a free failure into a paid one, and removed the last fail-closed brake between a fixture regression and a live model call.

Decided: state the guard’s gaps as a list, not as “always”

Four rounds were spent narrowing one sentence. The guard now enumerates what it cannot see: SIGKILL, a global timeout (the teardown inherits the already-expired deadline), a webServer that never starts, a globalTeardown file, in-flight requests, and UI mode. The general lesson is in the distinction it draws: a non-zero exit is not the same as a guard that fired.

6 · Assumptions and limits

Verified by execution

  • The guard fires when the setup project spends and then fails — 1 failed / 7 did not run, ledger_audit 306 → 307, exit 1.
  • The guard fires on a real Gemini call — forced a stale envelope, ledger_audit 307 → 308, spend_ledger 642 → 648. This cost 6¢.
  • The fail-open read: with the error check, a typo’d table fails; without it, 6 passed.
  • The loopback gate fires before deletion — fixture files survived, exit 1.
  • Rung 4 with the corrected seed: 7 passed, ledger unmoved.
  • FullConfig.projects reports ["setup","cloud"] under --project=cloud --no-deps — a partial-run check built on it could never fire.
  • tsc --noEmit clean; 2,703 unit tests / 267 suites green; CI green on master.

Read, not executed

  • All UI/watch-mode claims come from reading playwright@1.60.0’s runner source (runGlobalSetup, runTests, doNotRunDepsOutsideProjectFilter). No UI session was actually driven.
  • The teardown-vs-global-timeout claim is read from TaskRunner.runDeferCleanup passing the same deadline to cleanup. Not reproduced.

Not verified — stated plainly

  • The x-magazine-stale assertion is unmutated. No run has observed that header present, so “always absent” and “never looked” are not yet distinguishable. Reaching the stale branch needs owner_over_budget, not at_capacity; two attempts failed and both are recorded at the assertion.
  • A rung-2 flake. It failed once and passed on an identical re-run. Cause unknown, not investigated — in a serial suite where rung 2 gates rungs 3–6. Filed as backlog #45(c).
  • Round 5 did not converge. Its two Highs were fixed and verified; its four Mediums and seven Lows were filed as backlog #45 rather than fixed, per the process rule that Mediums are presented for a decision. No round 6 ran before merge. The unreviewed delta is: deleting the pin, deriving the seed, one import swap, and four comment corrections.
  • The main pane (PlaylistLibrary, VideoList, delete, share, dig, PDF) is never mounted by any rung — every rung opens / with no ?playlist. Filed as backlog #44.
One thing worth carrying out of this

Backlog #43 already contained the correct diagnosis, in writing, the day before the fix — “the resolver’s titles almost certainly drop the numeric prefix”. It sat unread while four review rounds ran over the same files.

Filing a good diagnosis is not the same as acting on one, and a backlog is not a reviewer.

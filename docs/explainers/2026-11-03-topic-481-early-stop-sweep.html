What a sweep is, and what the harness reads today

A mutation sweep checks that each guard's tests would notice a bug. A manifest entry (in scripts/mutations/<guard>.json) is one deliberate bug, an edit, plus the name of the test case that should catch it, its expect. For every entry the harness, scripts/check-plan-code.py, copies the tree, applies the edit, runs that guard's whole --self-test, and records a verdict: killed (the suite went red), survived (it stayed green), and whether the kill was attributed to the case the entry names.

Apply the edit, run the whole suite, put the file back (scripts/check-plan-code.py:3291-3293):

        (d / fname).write_text(src)
        rc, out = run_suite(d, fname)
        (d / fname).write_text(orig)

The run itself waits for the suite to finish, all cases, and captures everything (:751-753):

        r = subprocess.run([sys.executable, name, "--self-test"], cwd=d,
                           capture_output=True, text=True, timeout=SUITE_TIMEOUT,
                           env=mutation_env(d))

Then the verdict. Killed is the exit code and nothing else (:3320); exit 2 is a timeout and counts as NOT CHECKED (:3307):

        caught = rc == 1

Attribution reads the text: the [FAIL] <name> lines (:3301, fails = parse_fail_names(out)), and every name in expect must match exactly one red case (:3338, :3352-3353, :3360):

        want = mut.get("expect")
        ...
        unnamed = [(w, [f for f in fails if w == f]) for w in wants]
        unnamed = [(w, m) for w, m in unnamed if len(m) != 1]
        ...
                        "attributed": caught and not unnamed, "measured": True})

So today the harness reads exactly two things: the exit code (did it catch?) and the [FAIL] lines (which case caught it?). A kill that is not attributed fails the gate too, with "it was caught by something else".

Case 1: the suite stops but exits 0, so it is recorded SURVIVED (wrong)

Why the early exit must be a failure exit. Take the timeline above, but suppose the stop path printed STOPPED and returned 0, the way a "we are done" path often does.

  • The harness reads caught = rc == 1 (:3320). rc is 0, so caught is False.
  • The verdict is "mutation SURVIVED — the suite stayed green", although A and B both printed [FAIL]. The text is ignored for the catch; it is only read for attribution.
  • The full run would have exited 1 and recorded killed. So the early stop turned a real kill into a false survivor, and the gate goes red for a bug the tests did catch.

It must be exactly 1, not any non-zero: exit 2 is read as a timeout, NOT CHECKED (:3307). This direction of error is loud (a false red), not silent, but it would make every early-stopped mutant look like a coverage hole. inferred from the quoted lines; not run.

Why the SUITE decides, not the harness. A doc is not code, so every path rule in rounds 1-4 had let it through.

So the claim "under #481 the verdict equals the full run's" holds for the third form only. The reason it holds: the code that runs after the stop point in a full run is the remaining cases plus the exit decision. Later cases can only add failures, so skipping them cannot turn a 0 into a 1. The exit decision can, and the third form still runs it. And if a mutant breaks the stop path itself (say the reporter never notices the named failures), the suite simply runs to the end: a full run, the right verdict. inferred beyond the toy run.

One thing the third form still has to settle: a trailer check that assumes every case ran, such as a declared case count (check-plan-code.py's own count_drift), would fire on a stopped run. It has to be skipped or adjusted under the env var, and that adjustment is itself a place where early and full could differ. inferred, not built.

The one suite-side stop that exists already (PR #486)

PR #486 (merged 8552bf69, backlog #427) made scripts/check-main-drivable.py --self-test run its two memo-lifetime cases first and stop if the second one fails (scripts/check-main-drivable.py:2647-2652):

    if fail > _fail_before:
        print("\n  STOPPED — a memo entry does not hold its arguments, so every later memoised "
              "answer may be a dead tree's and every later case allocator noise (backlog #427). "
              f"{ok}/{ok + fail} passed before the stop.")
        return 1

It shows the two properties #481 needs: the stop is the suite's own, and it exits 1. How it differs:

  • Hard-coded, not driven by the harness. It fires for one condition in one suite, on every run, mutation or not. #481 fires only when the harness names the expected cases in an env var, and only once all of them have failed.
  • Its reason is correctness, not speed. After that failure the later cases are noise (recycled memory addresses), so stopping is the right answer even in a plain run.
  • It leaves by return 1 from the suite body, which skips anything after it in that body. That is safe here because the stop is unconditional on a real defect; for #481 the same move would be the sys.exit(1) row in case 3.

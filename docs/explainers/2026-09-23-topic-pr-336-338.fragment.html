Two defects to fix while extracting

1 — the stem match is case-sensitive, and that is a false green. Every stem in the existing list is lowercase, because Postgres column names are. Python constants are uppercase:

stem='warn_log'   -> 0 hit(s)
stem='WARN_LOG'   -> 3 hit(s)

Three files declare WARN_LOG. Someone writing the second adapter with the schema substrate's habits gets zero collisions and a passing gate.

2 — the container round-trip is safe by luck. It rejoins the pair as "{file}.{name}" and re-splits on the first dot. Measured, no symbol contains a dot and no two files share a stem — so it works today, but a check-ci-watched.sh beside the .py would silently collapse two containers into one.

Why this is the whole argument

These four logs have four writers and zero readers. Measured across every *.py, *.sh, *.ts, *.js and *.yml in the repo, the only code that touches each log is the script that writes it. .github/ has zero hits.

A grammar with no consumer has no falsifier. Its columns can invert between two generations and no test, no guard and no reviewer can observe it. That is not a prediction — it already happened, and it took an adversarial search to notice, eighteen days later.

The consequence: the 76 live records and the 6 older ones are not comparable, and nothing anywhere says so. These logs exist precisely to be a denominator for a “should this guard be promoted to blocking?” decision.

This changed the recommendation. An earlier section of the review argued the log consolidation was cheap insurance on a grammar nothing depends on — true, and it reached the wrong conclusion. The case is not the injection hole; it is that the denominator is already unsound, and the fix needs a version marker that none of the four producers has.

What I got wrong

Three claims in this review were wrong and are corrected in the document itself. If you are deciding whether to trust the rest, these are the relevant data.

1 — I told you backlog #164's worked example was wrong. It wasn't.

I claimed the row's example would in fact be caught by the existing guard. That rests on the step number being a parameter. In the real subject it is not:

def decide(texts: list[str] | None, armed: bool,
           steps=_UNSET, edited: bool = False,
           tool_uses: int = 0, paused: bool = False) -> tuple[int, str, str]:

                                    — scripts/check-banner-armed.py:503

The banner rides inside texts. Re-measured against that signature with every other parameter varied, so nothing else can explain the verdict:

findings: []

Non-vacuous — all four parameters discovered and judged — and zero findings. The row was right all along.

The error: I ran the guard against a synthetic function I wrote for the purpose, where the step genuinely was a parameter, got a correct answer about that, and wrote a conclusion about a subject with a different shape. My run was correct about the fixture and silent about the real code. I never opened decide's signature before publishing.

2 — I said no claim rested on agent output. Then the agents delivered.

The review's methodology section stated that three background searches had returned nothing and that every measurement was my own. That was true when written and stopped being true afterwards — three findings (F13, F14, F15) originate as leads from an agent that reported hours late. Each was re-measured before being written down, but the sentence claiming independence was left standing and had to be corrected. A claim about how a review was conducted is exactly the kind that gets believed without checking.

3 — I said nothing stated which duplicate-key rule was correct. Plenty does.

Two parsers of the same sentinel format disagree about which value wins when a key appears twice:

input: 'sha: first\nsha: second\n'

  check-plan-progress.parse_sentinel -> 'second'   (LAST wins)
  check-ci-watched.parse_sentinel    -> 'first'    (FIRST wins)

I wrote that nothing states which is correct. But the code says a great deal:

# STRIP BEFORE APPEND, so a restatement leaves ONE pair rather than a growing stack. Last-wins
# parsing made the stack harmless to READ, which is exactly why it went unnoticed for as long
# as it did — the file was wrong in a way no reader complained about.

                                                      — scripts/begin-plan.py:518-520

So the choice is between two known failure modes, not between a right and a wrong answer. Last-wins masked a real writer defect — recorded, not speculative. First-wins would not have masked it but would pin a stale value. That is a materially stronger argument than “no basis for choosing”.

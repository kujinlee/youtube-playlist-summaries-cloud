Dev speed: where the time goes, and a tripwire for new slow steps

as of master c983a114 · 2026-10-29 03:40 PDT · data from gh run list (1,000 CI runs, 09-06 → 10-29), gh pr list (400 merged PRs, 07-17 → 10-29), all 318 session transcripts of this project, and local timings taken tonight

Reading: dev speed is the wall-clock time from a request to a merged PR. This page is (1) a baseline of what we've measured, (2) where the time goes, (3) remedies, and (4) what to collect so that a new slow step is caught when it lands, not weeks later.

The reframe: speed came from less work per PR, not faster work

The switch from Opus 5 to Opus 5.5 felt like a big speed gain, and the transcripts agree it was, but not because the model writes faster. Per message, the two generate at the same rate. What fell is the number of messages it takes to land a PR.

This is an ASSOCIATION, not a measured cause. The two windows held different work: the Opus 5 window included long review episodes. The middle row is the cleanest comparison, because it's Opus 5.5 before the 10-25 merge-when-ready rule and the 10-26 local-sweep change, but it covers only 2 days and 8 PRs. What is solid: per-message speed did not change (97 vs 99 tokens/s), so whatever gain there was came from doing less per PR.

Why this matters for monitoring: the lever is work per unit: how many messages, rounds and gate runs a PR needs. Raw speed is a constant we don't control. A tripwire on "seconds per step" alone would miss the biggest effect on this page.

measured how: model_speed.py over every *.jsonl in the project's transcript directory. For each main-thread assistant message with ≥200 output tokens, it takes the gap from the preceding user or tool-result entry, keeps gaps between 0 and 600 s, and reads usage.output_tokens. ⚠ It uses the first entry per message id, so a streamed message may be timed at its first block, not its last.

Q (the owner, 10-29 04:54): how did this become possible? Why can Opus 5.5 merge more PRs than Opus 5 by doing less work? Probably Opus 5.5 is doing much smarter work than Opus 5.

A: partly yes, but the biggest measured change is WHERE the work happens, and it corrects this page. The "messages per PR" figure above counted only the main conversation. Counting subagents too (their transcripts sit in each session's subagents/ folder), over the same two windows:

Opus 5 window (10-13..10-21, 9 days, 7 PRs)Opus 5.5 window (10-23..10-28, 6 days, 47 PRs)
output tokens, main conversation9.35 M3.36 M
output tokens, subagents0.41 M (4%)5.14 M (60%)
total output tokens9.76 M (1.08 M/day)8.50 M (1.42 M/day)
total output tokens per merged PR1.39 M0.18 M
tool calls that returned an error217 of 11,477 (1.9%)97 of 8,345 (1.2%)

What this says, and what it doesn't:

  • The total work per DAY barely moved: about 1.1 M against 1.4 M output tokens a day. What moved is how much of it became merged PRs, about 7.7× fewer tokens per PR. So "doing less work" is right per PR, not per day.
  • Work moved off the main conversation: from 4% to 60% of output in subagents. Subagents run in parallel, each with a small, focused context, and the main conversation stays short enough to coordinate, which is how several slices move at once (this very night: five). That is a working pattern, and the model is only part of why it happens.
  • Fewer failed tool calls: 1.9% → 1.2%. That is consistent with "smarter", but small.
  • Not separable from the process changes in the same window: merge-when-ready (10-25) removed the wait on the owner, the local sweep stopped running in full (10-26), and docs-only PRs skip the CI sweep. The 10-23..10-24 sub-window, before both rules, still showed 4 PRs a day. So the model change is likely real, but its share is not measured.

measured how: how.py (scratchpad) over every *.jsonl including */subagents/*.jsonl, counting each assistant message id once, summing usage.output_tokens, and reading is_error on tool results. The subagents' own model was not checked: some may run on a different model.

Q (the owner, 10-29 04:59): 7.7× fewer tokens per PR is a huge difference. We need to understand correctly how this is achieved.

A: it splits two ways, and both point the same direction: about half is SMALLER PRs, and about half is each unit of work costing less. Same two windows, all output tokens (main conversation plus subagents):

Opus 5 window (10-13..10-21)Opus 5.5 window (10-23..10-28)ratio
merged PRs (docs-only / code)7 (3 / 4)47 (13 / 34)
lines changed per merged PR3,0091,2762.4× smaller
output tokens per changed line4631423.3× cheaper
review rounds landed34 over 7 subjects184 over 34 subjects
review rounds per merged PR4.93.91.25× fewer
output tokens per review round287 k46 k6.2× cheaper

Split 1, by size: 2.4× smaller PRs × 3.3× fewer tokens per changed line ≈ 7.8×. Split 2, by review: 1.25× fewer rounds per PR × 6.2× cheaper rounds ≈ 7.8×. Both multiply back to the observed figure.

The largest single factor is the cost of one review round: 287 k → 46 k output tokens. A round is the repo's unit of correction (review, then fold). What the data shows about where that went:

  • In the Opus 5 window, 96% of output was written in top-level sessions and 4% in subagents. In the Opus 5.5 window it was 40% and 60%. Folds and review halves are now handed to fresh subagents with a narrow brief, instead of the coordinator working through them in its own long conversation.
  • ⚠ "Top-level" includes peer sessions as well as the coordinator, because a peer's transcript is a top-level file too. So this shows the shift toward delegated, narrow-context work, but it cannot apportion it precisely between the coordinator and peers.
  • The Opus 5 window held long review episodes: 4 subjects carried 28 of its 34 rounds (two of them 8 rounds each). Long episodes are where a round costs the most, because each fold re-derives context.

What is NOT shown: how much of the cheaper round is the model (better first answers, fewer retries: failed tool calls 1.9% → 1.2%) and how much is the working pattern (delegation, smaller slices, merge-when-ready from 10-25). Both changed in the same week. To separate them, a later window would have to hold one fixed while the other varies. The tripwire log (backlog #397) would make that possible by recording tokens, rounds and lines per PR going forward.

measured how: PRs and their files from gh pr list --json files (docs-only means every changed path under docs/); rounds are review documents added to master per window, from git log --diff-filter=A, counted as (subject, round) pairs; tokens from how.py, as in the answer above.

Slowdowns that crept in before

Each one arrived as a reasonable change, cost time for days or weeks, and was caught by a person noticing, never by a machine.

  • The full sweep on a local run. A local --mutate . co-scoped every manifest. Co-scoping an unchanged 183-entry manifest cost 4 hours (memory: scoped mutation run). Fix: backlog #208 made a local run partial and refusing past 10 minutes (ba4d2c28, 10-26), and kept the full sweep in CI shards.
  • One guard's suite × its mutations. check-main-drivable.py held 183 entries against a ~30 s self-test, about 87 of the ~90 minutes of PR #360's sweep (ci.yml's comment). Putting a main([...]) call inside a long self-test raised it from 50 s to 209 s, past the 120 s shard timeout (memory: main-drivable cost is per call site).
  • The ffmpeg install hang. 4 of 14 CI attempts hung on the apt install before backlog #358 cached the packages (PR #407). In the 20 CI failures since, none was the ffmpeg step (tonight's tooling audit).
  • Sweep on docs-only PRs. Unchanged code was re-mutated on every docs PR until the step-level skip (ee0e461b). Now a docs PR's CI is 6.5 min instead of 26.

Proposal: a tripwire so the next one is caught when it lands

A proposal, not built yet: filed as backlog #397 (2026-10-29), per the standing rule that a backlog row is filed without asking. Its first slice is the CI log. Whether it ships, and in what order, is still yours to steer: ask on this section.

Every slowdown above was found by a person weeks after it landed. The pattern that would have caught each one: record the cost of every unit on every merge, and compare this week with last.

  1. CI per-job durations, per merged PR, appended to a log. On merge (the hook that already rebuilds every page), read gh run view --json jobs for the PR's final run and append one row per job: PR, job, minutes, and whether it was docs-only. Every number in §1 came from this call, so it is known to work.
  2. An elapsed_s field in every codex-review.py verdict. Today the verdict records model, head and outcome, but not how long the review took, so the costliest instrument in a round is invisible.
  3. A timing wrapper for local gates: one line per gate run (gate, seconds, load average) in a git-ignored log. It would have caught check-selftest-counts at 351 s, and it records contention as a column instead of hiding it.
  4. A budget per CI job: warn, not block, when a job's weekly p50 rises more than 25% over the previous week's. Warn-only follows this repo's measured rule that a blocking gate on a soft signal gets switched off (backlog #56).
  5. Work per PR, from the transcripts: messages and output tokens per merged PR, weekly. This is the metric that moved most across the model switch, and only the transcripts hold it.

All five feed one page section like the baseline above, regenerated on merge, so a reader sees this week against last without asking.

The usage limit: the slowdown that costs a whole day

The largest single speed loss is not a slow step; it is a stop. For several weeks the weekly usage limit has halted all work for about a day. On 10-29 at 05:02 it stopped four agents mid-task, and nothing ran again until 10-30 05:02. No work was lost: every commit was intact, both review files were complete, and recovery took about ten minutes from git, the ledger and the agent list. The cost is the idle day. Better recovery cannot buy that back; spending less can.

Where the usage went, over the 24 hours before the halt. Weighted by token type, using API list prices as a proxy because the plan's own weighting is not documented: cache read 0.1×, 1-hour cache write 2×, output 5×.

WhereWeighted shareWhat it was made of
five long-lived, reused teammates69.5%mostly cache writes: 65 full-context rebuilds of 100k tokens or more, after an agent idled past its cache lifetime and was woken
the coordinator25.9%mostly cheap reads; its 1-hour cache rarely expired (3 rebuilds)
fresh subagents4.3%about a 65k-token build each, then they finish

Unweighted, 99% of the raw tokens are cache reads, which made the coordinator look like the problem. Weighting moved the problem to the reused agents. The owner caught that the first estimate had not weighted cache costs or counted the cost of a reset.

What changed (the owner's decisions, 10-30):

  • A fresh subagent means a NEW one: per slice, per fold and per review round. No agent is parked waiting for a "go". This is now in docs/process-checklists.md → Agent lifetime, with the Phase 3 line of docs/dev-process.md pointing to it.
  • The coordinator is not reset per PR. Its re-reads are cheap, and a reset costs a rebuild, about ten turns of re-orientation, and lost nuance while the compaction restore is broken (backlog #396). It restarts only at a natural pause when the owner is present.
  • The statusline shows the 5-hour and weekly usage ([5h:22% wk:3%]) and caches it in ~/.claude/.rate-limits.json. It is the only documented surface that receives that number; hooks, environment variables and the CLI do not. Its parsing was folded from nine processes to two, so it runs in about 58 ms where it took 115 ms, measured under load.
  • Backlog #399 will read that cache: a warning at 80% weekly, and no new subagent spawns at 90% without an override. It waits on the owner confirming that the cached value matches /usage.

measured how: the same transcript scan as above, over 10-28 05:00 → 10-29 05:05 PDT, summing usage.cache_read_input_tokens, cache_creation_input_tokens, input_tokens and output_tokens per assistant message id. "Reused teammate" means the five named long-lived implementers; a rebuild is a single message whose cache write was 100k tokens or more. ⚠ The weights are a proxy: how the plan counts each token type toward the limit is not documented.

Where we're blind today

  • The weekly usage percentage was invisible until 10-30. It is now cached from the statusline; see the section above.
  • Codex review duration is not recorded. The verdict json has no elapsed field, so the cost of a review half can only be guessed from commit times.
  • No per-step local timing log. Every local number on this page was taken by hand tonight.
  • Agent CPU contention is not measured. Tonight's local timings were taken at load 18; how much of the 351 s is contention is unknown.
  • No queue time. The gap between the slowest shard (~19.5 min) and the run's wall-clock (26.1 min) is unexplained.

1. Background — what a schema gate is for

The skippable version

This project is preparing a large database change, called M4. It introduces the Workspace — in this codebase’s vocabulary, the immutable container a video’s artifacts are addressed under — so that a blob’s address stops moving when a title or a serial number changes.

The change is big: five new tables, three views, seventy new columns, fourteen triggers. Most of those triggers are not conveniences. They are guards: they make the artifact tables append-only, freeze a Generation once its run completes, and forbid overwriting a current row. In this system a generation is “one production run of a paid artifact, and everything that run produced” — so “append-only” is not tidiness, it is the property that stops one run’s card from describing another run’s body.

Before that schema reaches production, somebody has to answer one question: did it actually apply? That is what the gate in this PR is for.

The prerequisites for this change

An architecture review in August found that five of the project’s six schema gates never read a live database at all. They rebuild the schema from the .sql spec files inside their own rolled-back transaction. That makes them excellent at one question — is the spec internally consistent? — and structurally incapable of the other: did the migration land?

Structural fact

The project calls this the SUBJECT axis: built-from-source versus introspected-from-live. A gate can be rigorous, fast and green while pointed at the wrong subject entirely.

check-live-schema.py was written to close that gap. It opens a connection to the real database and asks the catalog what exists. It has two polarities: --expect-absent before the migration (and after a rollback), and --expect-present after it.

The defect this PR fixes is not that the gate looked in the wrong place. It looked in exactly the right place — and then compared what it saw against a list somebody had typed in.

2. Intuition — remembering vs. looking

Imagine taking inventory of a warehouse. You walk in with a clipboard listing five crates, and you find those five crates. You write “all present” and leave. The warehouse also contains a hundred and thirty-two other things, and the clipboard has never heard of them. Anything could have happened to those.

That was the shape of the old gate. Here is what it knew about, kind by kind. The dark bar is what it checked; the pale bar is what it could not see.

tables5 of 5
functions13 of 13
triggers7 of 14
columns3 of 70
views · indexes · policies · constraints0 of 58

The trigger row is the one that bites, and it bites for a reason that looked like good design at the time. The old list held a tuple named M4_LIVE_TRIGGERS, and it deliberately contained only the seven triggers that sit on pre-existing tables — profiles, playlists, videos, jobs. That was a considered choice: those seven survive a drop table, so they are the ones that turn a botched rollback into an outage. The other seven sit on M4’s own tables and die with them.

Correct reasoning for the absent direction. Silently wrong for the present one.

Measured, not argued

Take a database with M4 applied. Drop all seven guard triggers — every append-only rule, the generation freeze, the immutability check. Leave every table, column and function untouched. Then ask the old gate:

before the 29-object gate, on a database with no guards
$ python3 scripts/check-live-schema.py --expect-present
live schema: M4 is PRESENT as expected (5 tables, 3 columns,
             7 live triggers, 13 functions, 1 type)
$ echo $?
0

Exit zero. “As expected.” The tables are all there, so writes succeed — and every write the design forbids now succeeds too. This is worse than a missing table, which would fail loudly on first use. It is a database that looks correct and has quietly lost its rules.

The fix, in one sentence

Stop typing the list. Build the schema for real, ask Postgres what appeared, and keep that.

1
Read the baseline. Take the full catalog of the current pre-M4 database — every table, view, column, trigger, function, type, index, policy and constraint.
↓
2
Clone it into a throwaway database and apply the schema that build-m4-schema.py emits. Nothing shared is touched.
↓
3
Read the catalog again, and subtract: after EXCEPT before. What remains is exactly what M4 creates — 161 objects.
↓
4
Write it down as data, one kind:name per line, and drop the scratch database. The gate now compares a live catalog against that.

With the expected set and the live set both plain collections of strings, the whole comparison collapses into two lines of set algebra:

after scripts/check-live-schema.py:82
def verdict(live: set[str], manifest: set[str], mode: str) -> bool:
    if live & ADR0011_REMOVED:
        return False
    if mode == "absent":
        return not (live & manifest)
    return manifest <= live

manifest <= live is a subset test: every object M4 creates must be present. There is no room for a kind to be forgotten, because no kind is enumerated — the manifest is whatever the database said, and the gate compares all of it.

Same database, same mutation, after the change
after mutation 4 of scripts/mutate-live-schema-check.sh
═══ mutation 4 ⭐⭐ r3 B2: DROP EVERY OWN-TABLE GUARD TRIGGER ═══
  ✓ M4 applied to the guard scratch db -> --expect-present passes
  ✓ ALL SEVEN own-table guards dropped -> --expect-present FAILS
     tables and columns are all still there; only the guards are gone —
     that is precisely the state the 29-object gate blessed with exit 0.

3. Boundaries touched

Start here — row 3 is the one to read first. It is the only boundary in the change whose two sides disagree about something, and that disagreement is the reason the whole approach is safe.

BoundaryWhat crosses it What each side may assumeWhen that assumption is violated
1. gate ↔ manifest file 161 lines of kind:name text Gate side: the file exists, is non-empty, and describes the current schema.
File side: written only by the generator; never hand-edited.		 Missing or empty → exit 2, “treat this as NOT RUN”. Explicit, because an empty expected set makes manifest <= live vacuously true — the gate would pass over any database on earth.
Stale → the gate silently asserts yesterday’s shape. Nothing detects this except gen-m4-manifest.py --check, which is not yet run by anything automatically.
2. generator ↔ live baseline DB the pre-M4 catalog, as the subtrahend of a diff Generator side: the baseline has no M4 objects.
DB side: makes no promise at all — it is whatever the developer’s stack happens to be.		 If 0027 is already applied, after EXCEPT before is empty or partial and the generator writes a manifest asserting almost nothing — reproducing the exact bug it was built to fix. It refuses instead, naming the rollback script to run first.
3. ⭐ gate ↔ live database catalog rows, over docker exec … psql Gate side: assumes nothing about the schema. It names no table it expects to query, reads no application row, and requires no ordering.
DB side: must merely be reachable and answer nine selects.		 This asymmetry is the point. The old gate embedded beliefs about the schema; a belief that drifts is invisible. This one holds none — the only way it can be wrong is if the manifest is wrong, which is now a single auditable file with a regeneration command. Unreachable database → exit 2, never 0.
4. generator ↔ build-m4-schema.py the post-ADR-0011 SQL text, on stdout Generator side: a zero exit means the builder’s end-state assertions held.
Builder side: owes a schema with corrections removed per ADR-0011.		 Builder exits non-zero → generator exits 2. The manifest can therefore never be derived from a schema the builder itself rejected. (The builder’s own end-state predicate was found blind to two edits one round earlier; that is fixed and its self-test grew 14 → 22.)
5. gate ↔ its callers an exit code: 0 pass, 1 fail, 2 cannot-run Caller side: would like to treat 0 as “the schema is right”.
Gate side: promises only “the 161 manifest objects are all present / all absent”.		 Today there are no automated callers — see §6. The suite check-schema-gates.sh still chains 1/6…6/6 and does not mention this gate. Wiring it in is a plan step that has not run.

4. Decisions this change encodes

Derive the expected set; never write it down

The alternative on the table was cheaper: keep the 29-object gate, delete the claim that it was sufficient, and separately verify that supabase db push --linked applies a migration in one transaction — which would make a partial apply impossible rather than merely detectable.

That was rejected because the atomicity property is currently unverified. Building the safety argument on an unverified premise is what the project’s own notes call an unfalsifiable guard. Deriving the manifest costs one script and rests on nothing.

ADR candidate

ADR CANDIDATE: Gate expectations are derived from execution, not transcribed from source. Hard to reverse (every future schema check inherits the convention), surprising without context (a committed 161-line generated file looks like duplication), and the result of a real trade-off (a generated artifact must be kept fresh; a hand list must be kept correct — this trades a staleness problem, which a script can detect, for a completeness problem, which nothing can).

Derive it from the catalog, not from the SQL text

“Derived” could have meant parsing the .sql files. That was rejected, and the reason is a measurement rather than a preference.

unchanged the counting problem, measured on the real schema
$ grep -c "^create trigger" <built schema>
13
$ # … but the catalog reports
14

The missing one is art_summary_has_no_source_trg, declared as create constraint trigger. It is a trigger in every sense that matters; it simply does not match a pattern written by someone thinking of ordinary triggers. Any inventory built by reading the text inherits whatever its author’s pattern did not know about. The catalog has no such blind spot — it reports what Postgres built, not what a reader expected it to build.

Fail closed when the baseline is already migrated

A small decision with a large blast radius. Because the manifest is a difference, running the generator against a database that already has M4 would produce a near-empty file — and a near-empty manifest is a gate that passes over anything. The generator checks for workspaces and refuses.

Invariant

An expected-set file may be wrong about which objects. It must never be empty, because emptiness converts the gate from “checks 161 things” to “checks nothing” without changing its exit code. Both the generator and the loader enforce this independently.

Keep a second, separate list that must never appear

The manifest describes what M4 should create. It cannot, by construction, say anything about objects an earlier decision deleted — ADR-0011 removed corrections from the workspace container, and the manifest simply has no line for them. So a small hard-coded set survives, and it is checked in both polarities.

after scripts/check-live-schema.py:58 — the one list still written by hand, and why
ADR0011_REMOVED = {
    "trg:videos.videos_corrections_sync_ins_trg",
    "trg:videos.videos_corrections_sync_upd_trg",
    "fn:sync_corrections_to_workspace_video()",
    "col:workspace_videos.corrections",
    "col:workspace_videos.corrections_hash",
}

A surviving videos_corrections_sync_* trigger is not cosmetic: it fires on every video insert and update, calling a column that no longer exists.

6. Assumptions and limits

What I ran

  • check-live-schema.py --self-test → 20/20, on master after the merge.
  • build-m4-schema.py --self-test → 22/22, on master.
  • gen-m4-manifest.py --check → manifest current, 161 objects.
  • mutate-live-schema-check.sh → 5/5 mutations caught.
  • check-live-schema.py --expect-absent against the real local stack → exit 0, “checked all 161 objects”.

Three things this page asserts that are worth doubting

The gate has no automated caller — verified by search, not by reading

grep -rn "check-live-schema" across the repo returns the plan, the manifest header, the rollback’s comments, its own mutation harness, and scripts/run-schema-assertions.sh — which is itself hand-invoked. scripts/check-schema-gates.sh does not mention it; that suite still prints 1/6…6/6. Nothing in .github/, .claude/hooks/ or package.json refers to it. So the strongest schema gate in the repo currently runs only when a human types its name. Wiring it in is Task 3 Step 7 of the plan, which has not been executed.

This PR left three stale references behind

The rewrite deleted every M4_* tuple, but the plan still cites them at :646 (M4_LIVE_TRIGGERS) and :77, :706 (M4_FUNCTIONS). Harmless to execution, wrong for a reader. It is also the same “fixed at one of two sites” shape the project has now counted four times in a single day — a symbol was removed without grepping for the things that name it.

The bound the coverage number does not carry

161 of 161 sounds total. It is not a proof that a partial apply cannot happen — only that one would now be detected. The one-transaction property of supabase db push --linked remains NOT VERIFIED, and it is the other half of the option that was rejected. Detection and prevention are different guarantees.

Not verified

  • That the manifest matches production. It was generated from this repo’s local baseline. Production is believed to be at the same migration (0026), but no production database was read for this page.
  • Constraint- and index-name determinism. The manifest includes 38 constraints and 12 indexes by name. Postgres derives those names from the DDL, so identical DDL should give identical names — argued from how Postgres works, not measured across two machines.
  • The generator’s behaviour without Docker. The cannot-run paths are written and reachable by inspection; only the reachable-Docker path was executed.
  • Anything about ADR-0011’s correctness. This change consumes that decision; it does not re-examine it.

The one idea: cost ≈ calls × context

Most of our usage is not generated text. It is the same large conversation re-read on every API call. The meter charges a cache read at about a tenth of fresh input, but a 410k-token context re-read 4,929 times still dominates the bill.

So three things multiply cost, and each lever below attacks one of them:

  • How big the context is on each call. Fat coordinator, long-lived agents, and the re-injected floor after compaction.
  • How many calls are made. Wake-ups for notifications, duplicate reports, polling, gates re-run on an unchanged tree, and extra review rounds.
  • Cache rewrites, at 1.25–2× instead of 0.1×. An agent parked for more than an hour, a model switch, or a compaction rewrites its whole context.
Why a cheaper model is not the main lever. The meter study found weak evidence that Sonnet and Opus weigh about the same on the meter: a ratio of 1 fit at least as well as 5/3, and ratios of 2.5 or more were rejected ([M] verdict 3). If that holds, routing work to Sonnet saves little, while cutting calls and context saves a lot. not settled: the burst test was run overnight and was inconclusive (see the burst test); a passive regression replaces it and is waiting for data.

Before and after: did the levers show up in the usage?

Per unit of work, yes; in raw daily totals, not clearly. The cost per merged PR fell from a median of about 11.6M weighted tokens (10-20 to 10-29) to 8.5M (10-30 to 11-01) and 3.7M on 11-02 so far, and the cost per assistant call fell from 48k to 28k to 21k. The raw daily total did not fall until 11-01 to 11-02, and it swings with how much work was done. This is an observation of a period in which the workload also changed, so it does not prove that the levers caused the drop.

How measured. measured Weighted tokens are summed from every assistant message in the transcripts of this project, coordinator and subagents, de-duplicated by message id. Weights: input 1, cache read 0.1, 1-hour cache write 2, 5-minute write 1.25, output 5. Days are Pacific time. Merged PRs per day come from gh pr list --state merged. I chose "per merged PR" as the normaliser because the levers aim at the cost of delivering a change (fewer review rounds, smaller context, fewer wake-ups), and a PR is the unit the owner sees. It is crude: PRs differ in size, and a day with one PR is noisy (10-16: 1 PR, 69M). Per-call cost is in the table as a second view that does not depend on PR counts.

Q (10-31 21:19): what are the work parts and the habit parts of item 1?

Work: things to build, so that a pause can safely be a /clear

  • Restore after a clear. The ledger (.claude/inflight.jsonl) and the IN FLIGHT block already restore in-flight state after a compaction. ⚠ My memory notes say the /clear restore was broken (backlog #396); unverified tonight. Until that works, a clear can drop in-flight work, so I avoid it.

Q (10-31 21:29): explain "gates in one call, plus a last-green ledger".

The problem (measured, 10-30 usage study, rows 3 and 7). Before a push, the main session runs about ten checks: --self-test on each touched script, check-docs, check-review-rounds, check-reference-namespace, check-fixture-variation, and so on. It runs them one tool call at a time. Over 9 days that came to 1,306 gate-type commands that finished in under 10 s, and 3,674 of the session's 4,929 calls carried a single tool. Each call costs the same no matter how small its output, because every call re-reads the whole context (median 410k, about 54k weighted per call). A two-second check costs as much as a large one.

Lever A: gates in one call. One script, for example scripts/gates-for-pr.sh <worktree>, works out which checks apply to the branch's changed files, runs them all, and prints one line per gate (✅ check-docs / ❌ check-review-rounds: 1 silent gap). Ten calls become one, and ten tool outputs in the context become ten short lines. Better still, the agent that owns the branch runs it, so the main session never sees it. Measured: 68M of call cost went on sub-10 s gate commands. Expected saving: 30–50M over 9 days, inferred, and it overlaps with item 1, because a smaller context also makes each call cheaper.

Lever B: the last-green ledger. The same check often re-ran on a tree that had not changed: 152 repeat candidates, plus 44 runs killed at the 10-minute limit, mostly full mutation sweeps (682 wall minutes). The ledger is a small file recording (gate, tree hash) → green. Before running a gate, the script checks whether this exact tree already passed it, and if so prints ✅ (cached, tree abc123) without running anything. The tree hash covers everything, so any change to a file re-runs the check. Expected: about 16M (12.5M + 3.7M, inferred), plus a lot of wall time.

Why it is not built yet. No script exists on master (checked: scripts/ has no gates-for-pr or similar), and no backlog row exists yet. ⚠ One known trap: the gates already differ between local and CI. Mutation runs are partial locally and full in CI shards. So the ledger must key on the mode as well as the tree, or a local partial green would be read as a full green.

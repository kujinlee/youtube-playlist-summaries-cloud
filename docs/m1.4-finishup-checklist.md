- [x] **B1 — Round-trip.** ✅ **PASS 2026-08-11** (staging). Both directions, zero errors.
      - local → cloud: `created: 10`, 10 rows / 1 playlist / 10 blobs.
      - cloud → local: `created: 1, skippedIdentical: 9`; the hydrated body is **byte-identical** to
        the original (7787 bytes, `cmp` clean) — so "readable" is proven by content, not by absence
        of an error.
      - **Blob path shape confirmed** `<ownerId>/<playlistKey>/<key>`, e.g.
        `9e440cb5-…/PLxpwjSdVZQ95OWe3QvkVEcU1f1X-6NDj9/001_wk09-….md`, where segment 1 is the
        **authenticated test user's real UUID** — i.e. a genuine user JWT, which is exactly what the
        Task 12 review flagged (a literal `{ id: 'cloud' }` principal Storage RLS rejects).
      - ⚠️ **OPERATIONAL TRAP FOUND WHILE SETTING THIS UP — a data root's manifest baseline is bound
        to ONE cloud.** Re-pointing an existing root at a different Supabase project makes every video
        "in baseline + absent on the other side", which `sync-run.ts:622` correctly reads as *deleted
        remotely* → no propagation (M2b) → `removed: 10, created: 0`, **forever, with `errors: []` and
        exit 0**. Nothing is uploaded and nothing warns. Correct by design for the case it was written
        for; a silent trap for project restore/recreate/migration. Reproduced twice, then resolved by
        starting from a root with no `.cloud-sync-manifest.json`. **Not filed — raised for triage.**
- [x] **B2 — B1 guard, live.** ✅ **PASS 2026-08-11** — all four criteria, then healed.
      Fault injected by `drop policy artifacts_owner_rw on storage.objects`, which makes owner reads
      fail with a **permission error rather than a 404** — the "failed-to-read vs absent" distinction
      M2a exists for, and the one local (no TLS, no network) cannot produce.
      - error **surfaces**: `report.errors` carried one `cloud MD body unreadable for <videoId>` per
        video, and the CLI exited **2** — not swallowed into a null/absent
      - other replica **byte-preserved**: the edited local md unchanged at 6507 bytes, identical sha
      - **no manifest baseline written**: `.cloud-sync-manifest.json` byte-identical across the fault
      - `docVersion` **not downgraded**: every `videos.updated_at` still from the pre-fault upload, so
        the failed run wrote nothing at all
      - **heals**: policy restored → re-run `errors: []`, exit 0, divergence reconciled
        (`updatedLocal: 1`; the local edit lost to cloud because newer-wins compares *recorded
        signals*, not file mtime — correct, and worth knowing when hand-editing a body).
- [ ] **B3 — serve-doc money re-run (regression already fixed).** The double-charge was confirmed and
      fixed pre-launch (`tests/integration/serve-model-unreadable.test.ts`; 6→6 spend, 0 gemini calls).
      Re-run against hosted Supabase to confirm a **real 5xx** (not simulated) carries a non-404
      `statusCode` and still does not recharge.
- [ ] **B4 — `GENERATOR_VERSION` skew (M-R7-1).** Deploy an image whose `GENERATOR_VERSION` differs
      from the local checkout; run a `copyToCloud` where both sides hold a model for the same body;
      check whether a rendering share starts returning 503.
- [~] **B5 — ⚠️ THIS ITEM ASKS FOR SOMETHING THE NAMED TOOL CANNOT DO. Rewrite it.**
      As written: *"`npm run check:confinement` passes against the real deployed environment, not just
      local."* **`scripts/check-service-confinement.ts` is 100% STATIC** — verified 2026-08-11: no
      `process.env`, no `fetch`, no `createClient`, no network. It walks the SOURCE import graph from
      `process.cwd()` and reports whether `lib/supabase/service.ts` is reachable from a user-facing
      entrypoint outside a 3-entry allowlist. Run "against prod" it emits byte-identical output,
      because it never observes an environment — and it already runs in CI on every push.
      **Ran it anyway on master: `service_role confinement OK`, exit 0.**
      **Why this is worth a line rather than a shrug:** a reviewer runs it, sees OK, and ticks a box
      believing something was verified about PRODUCTION. It is a guard that passes in both worlds —
      this project's most familiar defect shape — except the guard here is a *checklist item*, not a
      SQL predicate. Every instrument built for this (mutation testing, guard classification) operates
      on code; nothing mutation-tests a checklist.
      **Decide, then rewrite:** (a) retire it — the static check is a CI concern, nothing about it is
      deploy-gated; or (b) replace with something genuinely environment-sensitive, e.g. assert the
      deployed web bundle contains no `service_role` JWT. (b) is a real and cheap test that does not
      exist yet.

## A. Prod paths not yet exercised live

> **FORMAT (adopted 2026-08-11).** Every gate carries `FAILS IF:` — the observation that would fail
> it — and every manual gate also carries `VERIFIED AGAINST: vN`, the deployed release it was checked
> on. Enforced by `scripts/check-gate-falsifiability.py`; staleness via `--staleness`.
> **Why the version field exists:** a tick records *that* something was verified and never *what
> against*. A1 and A2 below were ticked on 2026-07-22/23 — the **v3/v4** era — and the app is on
> **v6**. Both were claims about code that had not run in two releases, and nothing in this document
> knew. Same shape as the migration drift found the same morning.

- [~] **A1 — Download paths.** MD + rendered-HTML download (owner).
      **FAILS IF:** an owner MD or rendered-HTML download returns non-200, returns zero bytes, or
      returns HTML when `format=md` was requested.
      **VERIFIED AGAINST: v4** (2026-07-22) — ⚠️ **STALE, re-verify on v6.** Reopened from `[x]`:
      the original check was real, but two releases have shipped since, one of them 45 commits.
- [~] **A2 — Share paths.** Anonymous share URL serves a read-only summary and never charges.
      **FAILS IF:** a share URL opened with **no session** returns non-200, renders owner-only
      controls, or moves `spend_ledger` at all.
      **VERIFIED AGAINST: v4** (2026-07-23) — ⚠️ **STALE, re-verify on v6.** Opened in a genuine
      logged-out **incognito** window; read-only summary rendered.
      Two of the three acceptance points are enforced in CODE, not by the manual check, and those do
      *not* go stale on deploy: no-charge-on-serve by `tests/lib/share/import-guard.test.ts` (the share
      module cannot import charging code or call reserve), read-only by the hardcoded
      `{ dig: false, share: true }` render (`app/s/[token]/route.ts:89`). Only "the link works when
      logged out" needs a human, which is the part to re-run.
      Share serves summary only — no dig-deeper share link exists (backlog #12).
      - *(2026-07-22 first attempt was inconclusive — same-browser tab kept the owner logged in.)*
- [x] **A3 — Prod `daily_cap_cents`.** ⚠️ **This was a DECISION filed as a gate, and rewriting it in
      this format is what exposed that.** A decision cannot fail; asking what would falsify "we chose
      5000¢" has no answer. It becomes a real gate by asserting the world still matches the decision:
      **FAILS IF:** prod `guardrail_config.daily_cap_cents` ≠ **5000** and no newer decision is
      recorded here.
      **VERIFIED AGAINST: v6** (2026-08-11, live read via the read-only `claude_ro` role).
      Not stale — this reads the database, not the app, so it does not expire on deploy.
      **This reframing is load-bearing, not pedantry:** the 500¢→5000¢ change was made by direct SQL
      in an earlier session and the roadmap still said 500¢ for days. A drift assertion would have
      caught that; a decision record cannot. Rationale for the value: real per-video cost recalibrated
      to ~8¢ (PR #33), so at the 150¢ worst-case reservation this allows ~33 jobs/day vs ~3 at 500¢.
      Durable fix remains the settle slice.

## B. Cloud-sync (M2a) live checks — need real Supabase

Run in this order. These reproduce the transient-failure fault class M2a was built to survive, which
local cannot produce.

> **B1–B4 run against a THROWAWAY hosted project, by decision 2026-08-11 — not prod.** Their stated
> requirement is *hosted* infra (real TLS, real pooler, real network); it is not *production*
> specifically. A throwaway satisfies it without revoking a policy on live data or deploying a
> knowingly-skewed image to the live app. Staging project **`neeufoxdbgbpkjukzzuc`** (`yps-m14-staging`,
> us-east-1), all 25 migrations, private `artifacts` bucket with both policies, test user
> `m14-staging@example.com` (owner `9e440cb5-0a70-42b9-998c-40760e1c9bcd`).
>
> **This also independently proved the migration set applies cleanly FROM SCRATCH** — 25/25, 12 tables,
> all 12 `rls_forced` — which prod's incremental history had never tested. **Delete the project when
> B3/B4 are done.**

- [x] **B1 — Round-trip.** ✅ **PASS 2026-08-11** (staging). Both directions, zero errors.
      **FAILS IF:** after a sync, a local-only video is absent from the cloud index; or a cloud-only
      video's hydrated MD body differs byte-for-byte from the sender's; or any blob key does not match
      `<ownerId>/<playlistKey>/<key>` with segment 1 equal to the authenticated user's UUID.
      **VERIFIED AGAINST: v6** — ran against the schema/code at `0aac16d`, on hosted infra.
      - local → cloud: `created: 10`, 10 rows / 1 playlist / 10 blobs.
      - cloud → local: `created: 1, skippedIdentical: 9`; the hydrated body is **byte-identical** to
        the original (7787 bytes, `cmp` clean) — so "readable" is proven by content, not by absence
        of an error.
      - **Blob path shape confirmed** `<ownerId>/<playlistKey>/<key>`, e.g.
        `9e440cb5-…/PLxpwjSdVZQ95OWe3QvkVEcU1f1X-6NDj9/001_wk09-….md`, where segment 1 is the
        **authenticated test user's real UUID** — i.e. a genuine user JWT, which is exactly what the
        Task 12 review flagged (a literal `{ id: 'cloud' }` principal Storage RLS rejects).
      - ⚠️ **OPERATIONAL TRAP FOUND WHILE SETTING THIS UP — a data root's manifest baseline is bound
        to ONE cloud.** Re-pointing an existing root at a different Supabase project makes every video
        "in baseline + absent on the other side", which `sync-run.ts:622` correctly reads as *deleted
        remotely* → no propagation (M2b) → `removed: 10, created: 0`, **forever, with `errors: []` and
        exit 0**. Nothing is uploaded and nothing warns. Correct by design for the case it was written
        for; a silent trap for project restore/recreate/migration. Reproduced twice, then resolved by
        starting from a root with no `.cloud-sync-manifest.json`. **Not filed — raised for triage.**
- [x] **B2 — B1 guard, live.** ✅ **PASS 2026-08-11** — all four criteria, then healed.
      **FAILS IF:** with cloud MD reads failing, ANY of — `report.errors` is empty; the other replica's
      bytes change; `docVersion` decreases; a manifest baseline is written; or a subsequent healthy run
      still reports errors.
      **VERIFIED AGAINST: v6** — ran against `0aac16d` on hosted infra.
      Fault injected by `drop policy artifacts_owner_rw on storage.objects`, which makes owner reads
      fail with a **permission error rather than a 404** — the "failed-to-read vs absent" distinction
      M2a exists for, and the one local (no TLS, no network) cannot produce.
      - error **surfaces**: `report.errors` carried one `cloud MD body unreadable for <videoId>` per
        video, and the CLI exited **2** — not swallowed into a null/absent
      - other replica **byte-preserved**: the edited local md unchanged at 6507 bytes, identical sha
      - **no manifest baseline written**: `.cloud-sync-manifest.json` byte-identical across the fault
      - `docVersion` **not downgraded**: every `videos.updated_at` still from the pre-fault upload, so
        the failed run wrote nothing at all
      - **heals**: policy restored → re-run `errors: []`, exit 0, divergence reconciled
        (`updatedLocal: 1`; the local edit lost to cloud because newer-wins compares *recorded
        signals*, not file mtime — correct, and worth knowing when hand-editing a body).
- [ ] **B3 — serve-doc money re-run (regression already fixed).** The double-charge was confirmed and
      fixed pre-launch (`tests/integration/serve-model-unreadable.test.ts`; 6→6 spend, 0 gemini calls).
      Re-run against hosted Supabase with a **real** blob-read failure rather than an injected one.
      **FAILS IF:** the error is classified as *absent* (a 404-shaped `statusCode`, or none at all)
      **OR** `spend_ledger` moves by more than the single reservation the first serve already made.
      **BLOCKED — needs an explicit spend authorisation:** the serve path calls
      `generateMagazineModelForServe` (`lib/html-doc/serve-doc.ts:9`), a live Gemini call on the
      owner's key. Small (~6¢ reserved, ~1.5¢ actual) but real, and spend is a confirm-first action.

- [ ] **B4 — ⚠️ CANNOT BE WRITTEN AS A GATE UNTIL A PRODUCT DECISION IS MADE. This is the second B5.**
      As written: *"Deploy an image whose `GENERATOR_VERSION` differs from the local checkout; run a
      `copyToCloud` where both sides hold a model for the same body; **check whether** a rendering
      share starts returning 503."*
      **There is no `FAILS IF:` to write, and the attempt is what proved it.** The sentence describes
      an experiment, not an assertion — and the missing piece is not wording, it is that **nobody has
      decided what version skew SHOULD do.** Three coherent answers exist and they contradict:
      - *tolerate* — serve the stale model; skew is normal during a rolling deploy. Then FAILS IF the
        share returns 503.
      - *refuse* — 503 is correct; a model from another generator is not this document. Then FAILS IF
        the share returns 200.
      - *heal* — re-render at the current version on read. Then FAILS IF the response is neither a
        fresh render nor a 503.
      **The same observation is a pass under one reading and a failure under another.** Until that is
      settled the item cannot gate anything, and running the experiment yields a fact nobody can grade.
      **Do not tick this. Decide first**, then it becomes a one-line gate.
      *(Note what this cost: the format did not just document B4 — it converted "somebody should look
      at this someday" into "a decision is missing", which is actionable and was invisible before.)*
- [x] **B5 — ✅ RESOLVED 2026-08-11 by REPLACEMENT (PR #70), not by running the original.**
      **FAILS IF:** the live deployment serves any `service_role` JWT or `sb_secret_*` key in
      `/login` or any same-origin chunk — **or** the scan cannot run (zero scripts found, or any fetch
      error), which is reported as *not run* rather than clean.
      **VERIFIED AGAINST: v6** (2026-08-11) — `npm run check:deployed-bundle`: `/login` + 9 chunks,
      882,742 bytes, exit 0. Verified failing first: a bundle carrying a `service_role` JWT → exit 1
      naming the chunk and offset; a 200 page with zero scripts → exit 1 with the zero-scripts guard
      asserted *by message*; an unreachable host → exit 1.
      Post-deploy gate, deliberately **not** in CI — it needs a current deployment and would fail on
      any PR opened before a deploy.
      **The original item, for the record — it is the reason `FAILS IF:` now exists:**
      As written: *"`npm run check:confinement` passes against the real deployed environment, not just
      local."* **`scripts/check-service-confinement.ts` is 100% STATIC** — verified 2026-08-11: no
      `process.env`, no `fetch`, no `createClient`, no network. It walks the SOURCE import graph from
      `process.cwd()` and reports whether `lib/supabase/service.ts` is reachable from a user-facing
      entrypoint outside a 3-entry allowlist. Run "against prod" it emits byte-identical output,
      because it never observes an environment — and it already runs in CI on every push.
      **Ran it anyway on master: `service_role confinement OK`, exit 0.**
      **Why this is worth a line rather than a shrug:** a reviewer runs it, sees OK, and ticks a box
      believing something was verified about PRODUCTION. It is a guard that passes in both worlds —
      this project's most familiar defect shape — except the guard here is a *checklist item*, not a
      SQL predicate. Every instrument built for this (mutation testing, guard classification) operates
      on code; nothing mutation-tests a checklist.
      **Decide, then rewrite:** (a) retire it — the static check is a CI concern, nothing about it is
      deploy-gated; or (b) replace with something genuinely environment-sensitive, e.g. assert the
      deployed web bundle contains no `service_role` JWT. (b) is a real and cheap test that does not
      exist yet.
